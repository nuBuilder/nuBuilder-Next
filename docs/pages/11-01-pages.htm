Custom pages

PHP apps of your own that run inside nuBuilder Next.

For: Users with rights on: nuform

A custom page is a PHP app of your own (or written by an AI) that runs inside nuBuilder Next. It is stored like a form (a row of zzzzsys_form with the type page), so access levels, start page tiles, the side bar, run buttons and the cloners treat it as one. nuBuilder Next checks the login and the access level's right on the custom page before any code of the page runs, and hands the page one object, $nu, with the user, the context and the database. The page writes no login code and has a completely free look – nuBuilder Next adds no header, menu or CSS to it.

Creating a page

  1. Forms → Add → Custom page, or Add in the list Custom pages (Forms → Tools → Custom pages, the ▾ of the start page tile Forms; it is the forms list showing only custom pages). A short dialogue asks for the description, the code and how the page opens. The code is the folder name: letters, digits, _ and -, starting with a letter or digit, at most 64 characters (names starting with _ are reserved).
  2. The editor of a custom page shows the folder custom/pages/<code>/ and whether index.php is there. Create from template copies custom/pages/_template/ there (when the folder is writable; otherwise copy it by FTP).
  3. A complete example – a pizza shop with a menu, a cart, live order status, a kitchen board, menu management, charts and an Excel export – is in dev/examples/pizza/ of the developer package (its README lists the steps to install it). It uses permission items for the back office, its own tables, the settings JSON, NuPage.fetch() with polling and $nu->notify().
  4. Give access levels the right on the custom page, as for any form (view = may open it; the other rights can be read by the page with $nu->rights() and used as the app's roles).
  5. Write the app in index.php (more files, assets/ for css / js / images). Copy AI prompt puts the guide, this page and the list of your tables into the clipboard – paste it into any AI together with a description of the app.

Settings of a page

  • Open in: New tab (default – menus, tiles and run buttons open it in a new browser tab), Inside nuBuilder Next (the page in an iframe below the top bar and breadcrumbs; Iframe height auto = the page reports its height, or a fixed height like 800px) or Whole window.
  • Settings (JSON): the app's configuration (lists, colours, limits), read with $nu->setting('key') (dot paths). Invalid JSON is not saved. No secrets here – the settings are copied by the cloners. Below the field the page editor lists the keys the page reads (every $nu->setting('key', default) in its files) with the default in the code, the file and whether the key is set, and it names keys that are set but never read. When the page folder has a settings.example.json, Insert example fills the field with it (the template has one).
  • Secrets (API keys, passwords): secrets.php in the page folder (guard line first, return ['key' => '…'];), read with $nu->secret('key'). Never in a package, a cloner copy or the builder (it only says whether the file exists).
  • Content-Security-Policy (optional): added to frame-ancestors 'self', which every page gets.
  • Notes: for the developers.

How a page runs

  • index.php?p=form&f=<code> – the normal form address: an iframe page (mode Inside nuBuilder Next) or a redirect to the page's own address. Every way to open a form works: menus, tiles, run buttons, iframe run objects, nuForm(), bookmarks.
  • index.php?p=page&f=<code> – the page's own output (HTML, JSON for its fetch calls, downloads). r (record id), ps (nuSetProperty values) and the opening form and record (pf / pr, accepted only with the view right on that form) are passed on.
  • index.php?p=pageasset&f=<code>&file=assets/… – files of assets/ only (css, js, images, fonts, json, txt, pdf), with the same login and right.
  • Every POST needs the CSRF token ($nu->csrfField(), NuPage.fetch()). A fetch of the page gets JSON answers: 401 login, 400 csrf, 403 forbidden, 404 not_found, 500 server – error details only for the globeadmin.
  • While the globeadmin views as another user, $nu->user() is that user, $nu->realUser() the globeadmin, $nu->readOnly() is true and POSTs are refused. In demo mode readOnly() is true too.

Besides data and files, $nu writes Excel files ($nu->excel()) and, with the PhpSpreadsheet pack, reads Excel and OpenDocument workbooks ($nu->spreadsheet(), $nu->readSpreadsheet()). The complete list of $nu methods and of the JavaScript helpers (NuPage.fetch, toast, resize, refreshParent, openForm …) is in custom/PAGE_GUIDE.md (also part of Copy AI prompt). Forms opened from a page – links with $nu->formUrl() (with target="_top") or NuPage.openForm() – get a breadcrumb trail: their Back returns to the page, and when the page is shown in a launch form's iframe, to that form (its description in the breadcrumbs). The API has a version ($nu->apiVersion(), currently 1): pages that use only $nu keep working when nuBuilder Next changes inside.

API versions

The page API ($nu and NuPage) has a version number – this nuBuilder Next supports version 1. A page declares the version it is written for with $nu->api(1); as the second line of index.php (the template and Copy AI prompt include it; a page without it counts as version 1).

  • Rule: within one version, methods are only added – never removed or changed. A breaking change raises the version; the older version keeps running (through an adapter) for at least 6 months / 20 releases.
  • Unsupported version: the page does not run; the globeadmin sees which version it needs and what this nuBuilder Next supports, other users a short error.
  • Deprecated methods keep working; each call writes a notice to Debug results (once a day per page and method), deprecated NuPage names a warning in the browser console.
  • Before an update: Check package on the update page lists every page the new version would break (unsupported version, unknown or removed $nu->… / NuPage.… calls) or that uses deprecated ones. The update can still be installed.
  • Page editor of a custom page: the declared version and the problems with this version; the forms list shows a warning next to the type of such pages.
  • Only calls written as $nu->name( and NuPage.name are found – keep the variable name $nu.

Files, updates, copies

  • Pages live in custom/pages/<code>/, uploaded by FTP. $nuConfigCustomPagesDir in nuconfig.php (an absolute path) moves the pages folder, e.g. outside the web root – the safest setup.
  • Updates never touch custom/pages/ and custom/lib/ – only custom/.htaccess, custom/PAGE_GUIDE.md and custom/pages/_template/ come with nuBuilder Next. A rollback does not change them either. Include custom pages (update page, backups) puts a copy of the folders into a backup.
  • Direct requests of files in custom/ are blocked three ways: the guard line defined('NU_PAGE') || exit; at the top of every PHP file (the page editor warns when index.php lacks it), custom/.htaccess (Apache) and the nginx rule in Web server rules. Security check tests that the folder cannot be reached.
  • Renaming the code of a custom page: rename its folder by FTP too (the page editor says so). Deleting a custom page keeps its files.
  • The cloner copies a custom page with its settings, not its files (it shows the folders to copy). The App cloner copies the folders with the files of the installation, but never secrets.php.
  • To move a page to a test or production installation, export the application or a project that holds the page (Development, test and production): the package carries the page's code files, never _data, _draft, _versions or secrets.php. On import the files it replaces are kept as a version of the page, like a publish. In the folder of nucron.php app export the files are plain files below pages/<code>/files/.

Draft and versions

To improve a page that is in use, work on a draft: the users keep the live version until you publish. The card Draft and versions in the editor of the page:

  • Create draft copies the page's files into custom/pages/<code>/_draft/. Change the files there (File Manager, FTP, git) – the card lists the files that differ from the live version.
  • Open draft shows the page with the draft's files. This view is remembered for the page until you click Show live version in the bar at the bottom right (shown on HTML pages). Only designers (save right on the Form form, nuform) see a draft; everyone else always gets the live files, even with &nudraft=1 in the address.
  • Publish draft makes the draft live. The files it replaces are kept as a version in _versions/.
  • Restore next to a previous version copies it back; the current files become a version first, so a restore can be undone the same way. The newest ten versions are kept.
  • Discard draft deletes the draft.
  • The draft works on its own data: Create draft copies _data/ into _draft/_data/, and $nu->dataDir() points there while the draft is shown. Reset draft data copies the live data again. The draft's data is never published.
  • A secrets.php in _draft/ (for example test API keys) wins over the live one; without it the draft reads the live file.
  • Shared by the draft and the live version: the page settings and the database. Where the draft must not write live tables, ask $nu->isDraft() – for example $table = $nu->isDraft() ? 'orders_test' : 'orders';. For real tests against another database, move the page to a test installation (below). A draft that needs new columns should add them so the live code keeps working.
  • Files and folders starting with a dot (.git, .htaccess) stay in the page folder and are never moved. Built-in pages have no draft unless you made your own copy of them in custom/pages/.
  • Every step is written to the log (Page draft created / published / discarded, Page version restored).

Own PHP apps without a custom page

A PHP app that should stay a set of plain PHP files – its own HTML, its own session, its own database code – can still use nuBuilder Next's sign-in. It includes the file nuexternal.php from nuBuilder Next's folder and asks the class NuNextUser who is signed in. This replaces reading nuBuilder Forte's session ($_SESSION['nubuilder_session_data'], zzzzsys_session), which nuBuilder Next does not write.

<?php
session_start();                                        // the app's own session, if it has one – unchanged
require __DIR__ . '/../../nuexternal.php';              // path to nuBuilder Next's folder
$me = NuNextUser::require();                            // signed in – else the sign-in page, then back here
if (!NuNextUser::inTeam('Sales') && !NuNextUser::hasPermission('my_tool')) NuNextUser::deny('No access to this tool.');
$pdo = NuNextUser::pdo();                               // optional: nuBuilder Next's database connection
echo htmlspecialchars($me['first_name'] . ' ' . $me['last_name']);
  • Where the app lives: in a sub-folder of nuBuilder Next's folder, e.g. tools/my_tool/ – the browser sends nuBuilder Next's sign-in cookie only there. Not in custom/ or another folder of nuBuilder Next itself.
  • NuNextUser::current() – null or the user: id, login, name, first_name, last_name, email, team, department, position, code, language, globeadmin, access_id, access_code, access_levels (main and active additional levels: id, code, description), permissions (permission item idents).
  • require() sends a visitor who is not signed in to the sign-in page, which comes back to the same app page afterwards. deny($message) answers 403 (JSON for fetch requests).
  • Checks: isGlobeadmin(), hasPermission(…), inTeam(…), inDepartment(…), hasPosition(…), hasAccessLevel(…codes), canOpenForm(id or code) – each true when any of the given names matches; the globeadmin always passes, except inTeam / inDepartment / hasPosition.
  • Ask on every request: signing out, Sign out in Logged-in users and the session timeout end the access at once. Do not keep an "authenticated" flag in the app's own session.
  • The file only reads: it never starts or changes a session and defines nothing but the class NuNextUser, so it does not clash with the app's own functions. Opened in the browser, it answers 404. Not applied: IP access rules and nuBuilder Next's field and form rights – the app checks what it needs. The class only gets new methods, existing ones stay as they are (NuNextUser::VERSION).

A custom page does more for you (menu entry, rights per access level, CSRF, drafts) – use nuexternal.php when an existing app should keep running as it is.
