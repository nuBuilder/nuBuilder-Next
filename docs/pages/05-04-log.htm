Record log, audit trail and debug results

Who added or changed a record, the full change history and nuDebug output.

For: Users with rights on: nudebug, nunextaudit, nunextlog

Who added / changed a record

  • nuBuilder Forte's record log <table>_nulog (VARCHAR(1000), optional – nuBuilder Forte's "nulog" option, or design mode's Add nuBuilder Forte's record log when it creates a table): JSON {"added": {"user": "<user id>", "time": <Unix time>}, "edited": {"user": …, "time": …}}. NuBuilder Next writes it like nuBuilder Forte (4.x): added for a new record, edited on every save of an existing one (only the last edit; a record from before the column gets added = unknown / 0), also for sub-form rows that are added or changed and in the CSV import; a value posted for the column is ignored. The record's ⋮ menu shows Added by … · Last edited by … (names from the user ids). In SQL: JSON_UNQUOTE(JSON_EXTRACT(customer_nulog, '$.edited.user')).
  • nuBuilder Next's audit columns created_at, created_by, updated_at, updated_by (design mode: Add audit columns, form setting {"nunext": {"audit": true}}): date/time and login name, set by the server on every save of the main record, never taken from the browser; the CSV import fills them too (also nuBuilder-Forte-style nu_created_date / nu_created_by / nu_updated_date / nu_updated_by).
  • Audit trail (see below): every change, one row per column, with a history per record and restore. While the audit trail is on, record changes no longer go to the log ($nuConfigLogRecordChanges = true); older log entries of record changes were copied into the audit trail by the update.

Log

Menu Log: logins, failed logins, 2FA, password changes, changes to users, access levels and forms, exports, deletions in the audit trail, notifications sent. Record changes go to the audit trail while it is on. Filter by event, user, date or text.

Audit trail

Menu Log → Audit trail (globeadmin, admin role right Audit trail, or rights on nunextaudit): every change nuBuilder Next makes to the tables of forms, in zzzzsys_nunext_audit, one row per changed column:

  • Who and when: user id, login, IP address, date/time. What: action (added, changed, deleted, copied = saved clone, restored), source (form, sub-form, CSV import, restore, from the log = copied by the update), table, record id, form, for sub-form rows the parent table and record, column, old and new value (NULL stays NULL, shown as ∅). One save (main record and its sub-form rows) shares a change_id; a CSV import is one change.
  • Captured: saving and deleting in forms (sub-form rows included – a deleted record takes its sub-form rows along), saving a clone, the CSV import (insert / update / upsert, not the dry run). Only columns whose value really changed (numbers and dates compared as values). Not recorded: nuBuilder Forte's own zzzzsys_ tables (the log has users, access levels, forms …), the columns <table>_nulog, created_at/created_by/updated_at/updated_by (the audit row has who and when), and changes made outside nuBuilder Next – nuBuilder Forte itself, phpMyAdmin, PHP code or procedures that write with their own SQL. No database triggers are used.
  • Secrets and size: columns that look like secrets (password, token, secret, …) or hold password hashes are stored as •••; values longer than 4000 characters are cut and marked with a SHA-1 of the full value. Neither can be restored.
  • Settings (button Settings, globeadmin or Audit trail = change, confirmed with the password when the last confirmation is older than the re-login time): Record changes on/off (without a saved setting it follows $nuConfigLogRecordChanges), Keep (for ever or 30 days … 10 years – the housekeeping deletes older rows), Not recorded: tables (customer) or columns (invoice.notes), comma separated.
  • List: list views, filters (action, table, form, user, record, column, date), search in table, record, column and values, print and CSV. A row opens the history of its record.
  • Delete… (globeadmin or Audit trail = change, not in demo mode): a dialog that combines Only the rows of the current search and filters (exactly the listed rows, over all pages – a filter on a column can take part of a save) with an Age: any, older than 1 / 2 / 3 / 6 / 12 months, or before a date (cut by time, so a save goes as a whole). Neither = the whole audit trail, which needs DELETE typed. The dialog shows how many rows and saves will go; Download as CSV first saves exactly these rows with all columns. Deleting asks for the password when the last confirmation is older than the re-login time, works in batches of 5000 rows and is written to the log (Audit trail entries deleted: number, filter, date). For regular clean-up use Keep in the settings.
  • History of a record: the record's ⋮ menu → History of this record (shown while the audit trail is on), or index.php?p=audithistory&f=<form id>&r=<record id>. Rights: view on the form (and the record must be visible to the user while it exists). Newest first, one block per save, sub-form rows included.
  • Restore (, needs Save on the form, not in demo mode): a changed value goes back to its old value only while the column still holds the value shown as new (otherwise restore the later change first); a deleted row (main record or sub-form row) is inserted again with its recorded values only while no row with that key exists. Restoring is recorded itself (restored) and in the log. Entries copied from the log cannot be restored.

Debug results

Log → Debug: messages written by nuDebug() in PHP code (hooks, procedures). Newest first; filter by flag, user, text and date; long messages are collapsed; copy button; delete selected or all; optional auto refresh.
