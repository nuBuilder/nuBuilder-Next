REST API

JSON API for users, access levels, permission items and reports.

For: Administrators (globeadmin, admin roles)

JSON API for users, access levels with their form rights, permission items and reports (PDF): api.php/v1/… (no URL rewriting needed). Switch it on with $nuConfigApi = true in nuconfig.php and set a long random $nuConfigSecretKey. HTTPS only (localhost excepted; $nuConfigApiAllowHttp = true for tests). Access tokens live $nuConfigApiTokenMinutes minutes (default 15).

Create a client – step by step

  1. Switch the API on: Admin tools → API clients shows a notice while it is off – Switch the API on sets $nuConfigApi = true in nuconfig.php. A second notice asks for $nuConfigSecretKey: Generate key makes a long random key and writes it there (without it secrets and tokens are hashed without a key).
  2. Add: give the client a Name (e.g. the system that will call the API); Active stays on.
  3. Service user – one of the two: New service user creates a user on Save (login name – filled with api_ to start with –, display name and access level); Existing user lets you search for a user (login name, full name or access level) and shows that user's access level below the list. The access level decides which records the client may read and change – give the service user its own access level with only the form rights it needs. A user can be the service user of one client only, so users of other clients are not in the list.
  4. Scopes: tick only what the client needs (e.g. users:read for reading users). A request needs the scope and the right of the access level.
  5. Optional: allowed IP addresses or networks, requests per minute, expiry date.
  6. Save – the page shows the client_id and the client_secret. Copy the secret now: it is shown only this once (later it can only be replaced with New secret).
  7. Test it in the API playground (choose the client, GET /v1/me, Send), or fetch a token yourself with the curl request below and call api.php/v1/… with Authorization: Bearer ….

Clients – Admin tools → API clients

  • The list works like the other system lists: list views, search, filters by status (active, inactive, expired) and scope, print and export, cards on phones. The scopes of a client sit behind a small button with their number – a click shows the list.
  • A client has a public client_id and a client_secret that is shown once (copy it right away). Only HMAC hashes of secrets and tokens are stored.
  • Service user: each client acts as its own user (New service user or Existing user). The rights of that user's access level apply exactly as in the browser (view / save / add / delete on nuuser, nuaccess, nupermissionitem). A service user can no longer log in, and neither it nor its access level can be changed through the API.
  • Scopes: what the client may do at all – users:read, users:write, users:password, users:login_link, reports:run, notifications:write, access:read, access:write, permissions:read, permissions:write. A request needs the scope and the right of the access level.
  • Optional: allowed IP addresses / networks, requests per minute (default 120, then 429), expiry date. New secret (the old one stays valid 24 h or ends at once), Revoke all tokens, Delete. Every token and request is logged (Log: API token issued / refused, API read / change).

Access token (OAuth 2.0 client credentials)

curl -u 'nk_…:ns_…' -d grant_type=client_credentials https://example.com/nunext/api.php/v1/token
→ {"access_token":"nt_…","token_type":"Bearer","expires_in":900,"scope":"users:read …"}

curl -H 'Authorization: Bearer nt_…' 'https://example.com/nunext/api.php/v1/users?q=anna&state=active&limit=20'

Credentials as HTTP Basic or as client_id / client_secret in the body; scope may ask for fewer scopes. Ten wrong secrets lock the client for 15 minutes. If the Authorization header does not reach PHP (some FastCGI set-ups), add SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1 to the folder's .htaccess.

Rules: requests and answers are JSON (Content-Type: application/json); unknown fields are an error. Every record has an ETag; PATCH, PUT and DELETE need it in If-Match (428 without, 412 when the record changed meanwhile; * skips the check). Lists: {"data": […], "meta": {"total", "limit", "offset"}}. Errors (RFC 9457): {"type", "title", "status", "errors": [{"field", "message"}]} – 401 token, 403 scope or right, 404, 405, 415, 422 validation, 429 rate limit. Cross-origin (browser) requests are not allowed.

Reports and PDF links

POST api.php/v1/reports/sample_orders/run
{"params": {"customer_id": "C001"}, "filename": "orders-C001.pdf", "expires_minutes": 15, "max_downloads": 1}
→ 201 {"report": "sample_orders", "filename": "orders-C001.pdf", "size": 48211, "sha256": "…",
       "url": "https://…/index.php?p=reportfile&t=…", "expires_at": "2026-10-21T10:15:00Z", "max_downloads": 1}
  • Rights: the scope reports:run and the report right of the service user's access level (Reports → access levels), as in the browser. Data-source procedures run as in the browser.
  • params become hash variables (#customer_id#), like the values a form passes in nuBuilder Forte (4.x) – also RECORD_ID or FORM_ID. The service user's own variables (USER_ID, ACCESS_LEVEL_CODE, TABLE_ID …) cannot be passed (422). Date variables and TABLE_ID are added as for every run.
  • Download link url: opens without a login, so it can be handed to anybody – valid expires_minutes (1–1440, default 15) for max_downloads downloads (1–100, default 1); then 410. Add &dl=1 to download instead of showing the PDF. Only a hash of the token is stored; the PDF waits in the protected temp folder and is deleted after the last download or by the housekeeping. Runs and downloads are logged (Report printed, Report downloaded).
  • The PDF itself: send Accept: application/pdf – the answer is the file (200, header X-Report-Sha256), no link.
  • E-mail: "email": {"to": "…", "cc": "…", "bcc": "…", "subject": "…", "body": "…"} sends the PDF as attachment (nuBuilder Forte's nuEmailReportPDF; subject default: the report's description). The answer has emailed (and email_error). "url": false sends only the e-mail (422 when it fails).
  • Long reports: "async": true answers 202 {"job", "status_url"} at once; ask GET /v1/reports/jobs/{job} until done – the result is the same as above. With PHP-FPM the report runs right after the answer; otherwise it runs when the status is asked for the first time. Jobs belong to the client that started them.
  • Limit: 10 report runs per minute per client (429), on top of the client's request limit.

Playground – Admin tools → API clients → API playground

  • Choose a client (and optionally fewer scopes) and press Send: a token is fetched for the client without its secret (logged with via: playground) and the request goes from the browser to api.php exactly like a real client's. Under you can instead test the real token request with the client secret – it is not stored.
  • Endpoints fills in method, path and an example body. The answer shows status, time, body and headers; curl copies the request as a command line.
  • Variables {{name}} work in path, headers and body: your own (name=value per line) and from the last response – {{last_id}} (its id or the end of Location), {{last_etag}}, {{last_status}}. With If-Match automatically PATCH / PUT / DELETE send the ETag last seen for that resource.
  • Saved requests (name, folder, method, path, headers, body, client and scope) are shared by the administrators; client, scope, variables and the If-Match option are kept per login. Table zzzzsys_nunext_api_request.
  • Requests are real: they change data, count towards the rate limit and must come from an allowed IP address.
