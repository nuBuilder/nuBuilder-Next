Sign-in methods

Advanced Password, two-step login, passkeys, shared login with nuBuilder Forte (4.x), links and tokens – all ways into nuBuilder Next in one place.

One-time login link

nuBuilder Forte's Single-User Password Token: index.php?u=<login name or user id>&p=<token> (with &f= / &r= as for the auto-login link, see Configuration) signs the user in once when the token matches LOGIN_TOKEN in the user's sus_json – like nuBuilder Forte without a second factor; afterwards the token is replaced by a new random one, so the same link never works twice (also not for two clicks at the same moment). Ways to get a token:

  • User form (globeadmin) → One-time login link: validity 1 hour, 1 day, 7 days, 30 days or no expiry; Create link shows the link once to copy, the envelope sends it to the user's e-mail address (in the user's language), the red button removes the token.
  • In a procedure: nuCreateLoginToken($userId, $minutes = 0, $formId = '', $recordId = '') returns the link ('' when not possible).
  • REST API: POST /v1/users/{id}/login-link (scope users:login_link, see REST API).
  • Another system writes the token itself, as in nuBuilder Forte's wiki: sus_json → {"LOGIN_TOKEN": "…"}, at least 20 characters; optional "LOGIN_TOKEN_EXPIRES": <Unix time> (nuBuilder Next only – nuBuilder Forte ignores it).

Differences to nuBuilder Forte (all safer, the links stay compatible): exact comparison in constant time, never the globeadmin or an API service user, the user's expiry date and access level apply, wrong tokens count for the login rate limit, every use is logged (Login with via: token), creating, mailing and removing are logged too. Dangerous actions still ask for the password (the session counts as not confirmed). p with 64 hex characters is nuBuilder Next's signed auto-login hash while $nuConfigAutoLogin is on; anything else of 20 characters or more is treated as a token. Switch it off in the Security check (Accept nuBuilder Forte's one-time login tokens); the Security check also shows how many users have a token (stored in plain text, as in nuBuilder Forte) and removes all of them.

Passkeys

Users add passkeys themselves (Security → Passkeys) – only the user's own device can create one. A passkey can then replace the authenticator code or the e-mail code, confirm dangerous actions instead of the password and, with the second switch on, sign in without a password.

  • Address: browsers offer passkeys only on https (or localhost) and for a domain name, never an IP address. A passkey belongs to the host of the installation's address – set $nuConfigBaseURL (also behind a proxy). Changing the domain makes all saved passkeys useless; users then add new ones.
  • What is checked: the signature with the public key saved when the passkey was added (ES256, RS256 or Ed25519), the site address and the one-time challenge of this sign-in, the user-verification flag (sign-in without a password and confirmations) and the passkey's counter – a counter that does not go up points to a copied passkey and is refused. The maker's certificate is not checked (attestation "none"), as usual for company applications.
  • Admins with the save right on users see a user's passkeys on the user form (Login credentials → Passkeys) and can remove them; deleting a user removes them too. The globeadmin's passkeys and a locked-out user: php nucron.php passkeys off <login name> on the server.
  • Rules: a passkey sign-in is refused like a password sign-in for expired users, API service users and users without an access level; IP access applies; access levels that allow only single sign-on refuse it. Passkey sign-ins skip the password policy and a forced password change, and they count as a fresh password confirmation.
  • Log: Passkey added, Passkey removed, Passkey refused (with the reason), and the login with via: passkey or 2fa: passkey. The Security check shows how many users have one.
  • nuBuilder Forte has no passkeys: the same users sign in there with their password and its two-step login. The passkeys are kept in nuBuilder Next's own table zzzzsys_nunext_passkey.

Rules for every method

  • Expired or locked accounts are refused; a user who must change their password is asked to right after signing in.
  • Failed logins are rate-limited and written to the log; the procedure nu_invalid_login can replace the message, nu_startup runs after every login and can refuse it.
  • Sessions end after $nuConfigSessionTimeout / $nuConfigSessionTimeoutGlobeadmin minutes without activity, when the password is changed anywhere, or when the globeadmin ends them.
  • The globeadmin can reset a user's two-step login (lost phone) in the user form.
  • With IP access switched on, every method – password, passkey, auto-login link, one-time login link, single sign-on – is refused from an address the user's access levels do not allow, and a running session ends when its address is no longer allowed.
