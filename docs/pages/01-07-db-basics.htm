Database basics

Tables, keys, relationships and a little SQL – what you need to know before you build your first form.

For: Everyone who builds forms and reports

An application in nuBuilder Next is a set of forms on top of database tables. If you know spreadsheets, you already know most of it: a table stores information in rows and columns, like a sheet, and the database is a container that holds many such sheets. This page explains the few ideas the rest of the documentation takes for granted. To start building right away, go to Your first application.

Tables, rows and columns

  • A table holds one kind of thing – customers, contacts, invoices. Each row (a record) is one of them; each column (also called a field) is one piece of information about it: name, phone number, postcode.
  • A form shows one table: its list shows many rows, its edit screen one record. The objects on the form are, for the most part, the columns of that table. In short: forms deal with tables, objects deal with columns.

Primary keys

Two customers can have the same name – two businesses called "Bob's Plumbing" are perfectly possible. To tell rows apart, every table gets a column whose value is different in every row: the primary key.

  • Every table should have a primary key. Its values must be unique and never empty; the database uses it to find a row quickly.
  • nuBuilder Next fills it for you when a new record is saved. By default the keys look like nuBuilder Forte's – a text of letters and digits such as 14e49d3d0ef3a701 (stored in a VARCHAR(25) column); a new table can use UUIDs instead. An auto-increment number works as well.
  • Keys are for the system and for your code, not for people: users never type or see them.
  • Do not use a business number (customer number, article number) as the primary key. Businesses change their numbering; a key must never change. Keep such numbers in a column of their own – an nuAutoNumber input can count them (see Automatic numbers).

Foreign keys and one-to-many relationships

A business has several contacts; an invoice has several items. This is a one-to-many relationship, and it is stored with a foreign key: a column in the second table that holds a copy of the first table's primary key.

  • The table with the "one" is the parent (organisation, invoice), the table with the "many" the child (contact, invoice item). Each child row stores the parent's key in its foreign key column – for example con_organization_id in the contact table holds the organization_id of its organisation.
  • A foreign key value appears in many child rows, so unlike a primary key it is not unique in the child table.
  • Like primary keys, foreign keys are never shown to users. On a form you see the other side of them:
    • a lookup on the child's form lets the user pick the parent – it stores the key and shows the parent's code and description;
    • a sub-form on the parent's form lists its children as rows that can be edited, added and deleted.

Naming tables and columns

A naming convention keeps SQL readable and avoids clashes between tables. The one nuBuilder Forte's examples use, and that works well with nuBuilder Next:

  1. Lower case for all table and column names.
  2. Table names in the singular: customer, invoice_item.
  3. Words separated by _.
  4. The primary key is the table name with _id: customer_id.
  5. Every other column starts with a short prefix taken from the table name: cus_name, cus_email, and for a foreign key con_customer_id.

Because object IDs are column names, the prefix also keeps the IDs of different forms apart (#cus_name# and #con_name# are different hash variables). Never create your own tables with the prefix zzzzsys_ – those are the system tables of nuBuilder Forte and nuBuilder Next; leave them alone.

A little SQL

SQL (Structured Query Language) is how programs talk to the database. The four things an application does with data – create, read, update, delete, "CRUD" – are the SQL commands INSERT, SELECT, UPDATE and DELETE. nuBuilder Next writes most of them for you (a save is an INSERT or UPDATE); what you write yourself is mostly SELECT – for a form's list, a select object's options, a display object or a report. Three words go a long way:

SELECT org_code, org_name      -- the columns you want (* = all of them)
FROM organization              -- the table(s) they come from
WHERE org_state = 'SA'         -- only the rows that match
  • Without WHERE you get every row; WHERE organization_id = '58a11df94545f2b' gets exactly one, because primary keys are unique.
  • A value can come from the open form or the user as a hash variable: WHERE org_state = '#org_state#' uses what the user chose in the field org_state.
  • A query inside brackets can deliver one extra value per row. (SELECT COUNT(*) FROM organization WHERE org_state = '#org_state#') AS total adds a column total with the number of matching rows – handy for a report footer.
  • Try a query before you use it: in a database tool (user menu → Database – Adminer or phpMyAdmin, see Admin tools and system status) or with Run in the SQL builder, which also puts queries together for you by clicking tables and columns.

Free introductions to SQL are on the web, for example w3schools.com/sql.

Plan before you build

Write down the things your application keeps (customers, contacts, orders …), give each a table, and draw lines for the one-to-many relationships – that drawing is the database schema. Once it is complete, every table becomes a form, every relationship a lookup on the child and, where useful, a sub-form on the parent. The tables themselves can be created in the New form wizard (New table) or in a database tool.
