Projects

Keep the forms, procedures, reports and tables of one piece of work together – with notes and to-dos – and move them to another installation as one file.

For: Developers (globeadmin, admin roles with the right Projects, users who may change forms)

An application grows: an order system soon has a dozen forms, procedures for its buttons, reports, SQL queries and e-mail templates. A project lists the parts that belong together. The parts stay where they are – a form can belong to several projects, and removing it from a project changes nothing else. Open the projects from the start page tile Projects (index.php?p=projects). The ticket system sample comes with a project to look at.

Parts

  1. Projects → Add: a name, optionally a code (letters, digits, _ . -; made from the name when empty) and a description.
  2. Tab Parts → Add parts: choose the kind – forms, procedures, reports, SQL queries, tables, e-mail templates, snippets or help pages – search and tick. Picks of several kinds and searches are added together.
  3. Suggest related lists what the parts already in the project use and is not in it yet: the sub-forms, lookups and run buttons of a form, its table and the tables of its list SQL, procedures and reports named in its code, the launch form and data source of a report, the tables of an SQL query. Untick what does not belong and add the rest.

Each part links to its editor (form in design mode, procedure, report …) in a new tab. A part deleted elsewhere stays in the list, marked No longer exists here, until you remove it.

Notes and to-dos

Notes are written in Markdown (**bold**, lists with -, `code`, links). A pinned note is shown on the Overview.

A to-do has a title, optionally details, a user it is for, a due date and the part it is about. The user gets a notification (the bell) when the to-do is given to them, and again on the day it is due. Tick it on the Overview or the To-do tab when it is done. Your own open to-dos of all projects are listed above the list of projects.

The Overview also shows the recent changes of the project's forms from the form history and their open drafts.

Working on a project

Work on this on the project page narrows the lists of forms, procedures, reports, SQL queries and e-mail templates to the project's parts – their filter Project is set for you. Choose another project or none in that filter to see more; Stop working on it ends it. The choice lasts until you sign out and only affects you.

Export and import

Export writes one JSON file with the project, its notes and to-dos and its parts: forms with their tabs, objects, list columns, events and code, procedures, reports, SQL queries with their clauses, e-mail templates, snippets, permission items, formats, files, data exports, webhooks, help pages and the structure of the tables. It also holds the access rights of the forms, procedures and reports (by the code of the access level) and the translations of the forms' texts. Package with table rows (globeadmin only) also contains the rows of the tables, up to 20,000 per table. Secrets (the secret of a webhook) are never exported.

Import project (globeadmin) reads such a file and shows each part with its state here – new, the same, different, exists, conflict – and what will happen. Nothing changes before you confirm:

  • New parts are added with their ids. A part that exists and differs is replaced only when you choose Replace.
  • Before anything is replaced, the current versions are kept as a restore point in the backup folder – the message after the import links to it. Importing the restore point puts the replaced parts back (added parts stay). A replaced form is also in the form history.
  • A form whose code another form already uses is skipped. An open draft of a replaced form stays and may conflict when it is published.
  • Tables are never dropped and their columns never changed. A table that exists here only gets the columns the package has and it lacks. New tables (and views) are created on MySQL / MariaDB and SQLite (not on SQL Server), with their rows when the package has them.
  • Parts that exist here but not in the package are listed as Only here – for a project package the parts of the same project, for the application package every own part. They stay unless you choose Delete per row, or Delete all listed. A part that something kept still uses (a form opened as sub-form, lookup or button target, a form an access level starts with, a procedure or report behind a button) cannot be deleted; the row says by what. Tables are never deleted. Deleted parts go into the restore point too, so importing it brings them back.
  • Access rights here on the package's forms, procedures and reports for levels the package gives no right appear as one Only here line and can be removed the same way.
  • Access rights go to the access levels with the same code here; levels that do not exist are listed and left out. Translations are added or updated per language and English text.
  • A project with the same code gets the new parts; its notes and to-dos stay. Otherwise a new project is made with the package's notes and to-dos.

Back up the database before a larger import (Backups).

Development, test and production

To move work from a development installation to a test or production one, put what belongs together into a project and export it, or export the whole application with Export application in the title bar of the projects list (globeadmin). The application package holds every form, procedure, report and the other parts above that are not nuBuilder Forte's or nuBuilder Next's own, plus the structure of the tables, the access levels, the settings and the code files of custom pages. Import it on the other installation as above – the check shows exactly what is new and what differs.

Access levels travel by their code: a level the other installation lacks is added, an existing one takes the description, group, Home form, two-factor switch and start page of the package. Their rights come with the forms, procedures and reports. A project package carries the levels its rights name; add a level to a project to carry it on its own. A level that exists only on the target is listed but never deleted.

Settings travel only in the application package, one line per part: shared settings, Global code, branding and logos, themes, languages, security settings, password policy, audit trail settings and custom page settings. What belongs to one installation never travels: the secret key and nuconfig.php, e-mail (SMTP), single sign-on, IP access, the health check key, API clients, webhook secrets, the environment label, update settings, and among the shared settings passwords, demo mode, the globeadmin list, database tools, the backup folder and debugging.

Give each installation an environment label (Branding): it shows in the top bar, on the sign-in page and in the browser tab, so nobody mistakes production for test.

Keeping the application in git. On the command line, php nucron.php app export --dir=<folder> writes the application (or with --project=<code> one project) as a folder: one folder per form, procedure, report …, the item as item.json and every longer piece of code beside it as its own file (sph_php.php, form.sfo_browse_sql.sql …). The same database always writes the same files, so after git add / git commit a diff shows only what really changed. php nucron.php app import --dir=<folder> lists what an import would do – parts that are no longer in the folder as delete?; with --yes it imports (new parts added, changed parts replaced, restore point first). Deleting needs --delete as well; --keep=<kind>|<id> protects single parts. See Command line.

Who may do what

Viewing projects needs the admin right Projects (view) or the save right on the Forms form; changing them the right Projects (change), the save right on the Forms form or the globeadmin. Import and the export with table rows are for the globeadmin. Projects are stored in nuBuilder Next's own tables; nuBuilder Forte does not see them.
