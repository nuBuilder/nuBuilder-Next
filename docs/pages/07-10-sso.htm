Single sign-on

Users sign in with their company account – Microsoft Entra ID, Google Workspace, Keycloak, Okta, Authentik or any other OpenID Connect provider. The provider checks the password and the second factor; nuBuilder Next still decides what the user may do.

For: the globeadmin

Settings → Sign-in & security → Single sign-on (index.php?p=sso). While it is switched on and complete, the sign-in page shows a button such as Sign in with Microsoft above the password form. The globeadmin always signs in with the password of nuconfig.php – a provider that is down never locks you out.

Setting it up

  1. At the provider, register a web application. Enter the redirect URI the page shows (https://<your server>/<folder>/oauth.php – the same address as the OAuth sign-in of the e-mail settings). Note the client ID and create a client secret.
  2. On the page: pick the kind of provider, enter the issuer, the client ID and the secret, and save.
    • Microsoft Entra ID: https://login.microsoftonline.com/<tenant id>/v2.0 – the tenant ID, not common.
    • Google: https://accounts.google.com; with one allowed domain the sign-in page of Google offers only accounts of that domain.
    • Keycloak: https://<host>/realms/<realm>. Others: the address in front of /.well-known/openid-configuration.
  3. Test sign-in signs in at the provider and shows what a sign-in with that account would do – which user it finds or would create, the access level and the claims the provider sent. Nothing changes, and it also works while single sign-on is still switched off.
  4. Switch on Offer single sign-on on the sign-in page.

The secret is stored sealed with $nuConfigSecretKey (the page warns when that is not set). Leave the field empty to keep the stored secret.

Which user signs in

  • The provider's verified e-mail address (claim email, for Entra ID also preferred_username / upn) is compared, ignoring case, with the e-mail and the login name of the users. Exactly one user must match; an e-mail the provider marks as not verified is refused.
  • Allowed e-mail domains limits the accounts (empty = every account the provider vouches for).
  • Create users who sign in for the first time (off by default): a new user gets the access level of the group map, else the default access level; without either the sign-in is refused. The new user's login name is the e-mail address, the password a long random one nobody knows; the log shows User created by single sign-on.
  • Group map: the claim named in Group claim (default groups) lists the groups or roles of the account; the first row whose group matches gives the access level. With Keep the access level in step an existing user's main access level follows the map at every sign-in (no match leaves it as it is; additional access levels are not touched). Entra ID sends the groups as object IDs – enter those, or use app roles with the claim roles. Keycloak needs a mapper that adds the groups to the ID token.

Rules of a single sign-on

  • No second factor of nuBuilder Next and no password policy – the provider owns the password and its multi-factor rules. A user signed in this way is not asked to change the password.
  • Expiry date, access level, the login rate limit, IP access and the procedure nu_startup apply as for every sign-in. The log shows Login with via: sso; refusals are logged as Single sign-on refused with the reason.
  • Single sign-on only: users of the ticked access levels (main level or an active additional level) can no longer sign in with a password, an auto-login link or a one-time login link – they see “Please sign in with single sign-on”. It applies only while single sign-on is on and complete.
  • nuBuilder Forte's settings keep working: with $nuConfigLogonMode = 'sso' every user except those named in $nuConfigSsoOnlyExcept signs in with single sign-on only, and the sign-in page folds the password form behind Sign in with a password. nuBuilder Forte's separate SSO service (zzzzsys_sso_login) is not used – set up the provider here.

What is checked

The authorization code flow with PKCE (S256), a random state (once, 10 minutes, bound to the browser session) and a nonce. The ID token is checked here and not only trusted because it came from the token endpoint: the signature (RS256 / RS384 / RS512 with the provider's published keys, fetched again once when a key is unknown), the issuer of the discovery document, the audience (the client ID; azp with several audiences), the times exp / nbf / iat and the nonce. Only https addresses are accepted for the provider (http only for this computer, for tests). The discovery document and the keys are cached for a day.
