Libraries (library packs)

Advanced Third-party libraries that are not part of the package (TinyMCE, phpMyAdmin, Adminer …) and how library packs install them.

For: Administrators (globeadmin, admin roles)

Folders: all third-party code is in vendor/. vendor/bundled/ comes with nunext.zip – an update replaces it; vendor/packs/ holds the library packs – installed separately, an update never touches it. The folder name says who owns it.

Seven libraries are not part of the nuBuilder Next package. They come as library packs – one signed zip per library and version, independent of nuBuilder Next's own version and of nuBuilder Forte's copies (nuBuilder Next may need another TCPDF than nuBuilder Forte (4.x), phpMyAdmin comes with nuBuilder Forte's login config). The File Manager is part of nuBuilder Next (no pack needed):

  • Where they come from: the GitHub release with the tag libraries of the update repository (nuBuilder/nuBuilder-Next by default – the one set under Update from GitHub), which holds every pack and the signed index libraries.json; zips nunext-lib-<name>-<version>.zip copied by FTP into _update/ (or _install/ while installing); or an upload on the update page. Every pack is checked the same way: its signature (the key of nunext.zip), every file against its SHA-256 and size, nothing outside the listed files – a pack that fails is listed with the reason and never installed, whatever folder it lies in.
  • Update → tab Libraries: per library the version in use and where it comes from (pack, nuBuilder Forte's copy, copied by hand), the newest pack available (GitHub or the folder), its state against the first version without the vulnerabilities known at the time (a yellow dot on the tab and a badge when one is below it; a blue dot when updates are available). Install / Update per row, or tick several and Install / update selected. The ⋮ menu: Install again, Self-test, Roll back to …, Remove. Look on GitHub asks now (otherwise together with the automatic update check). Upload a pack installs a zip from your computer – for servers without access to GitHub. The libraries nuBuilder Next itself ships in vendor/bundled/ are listed in the card Libraries in the package below.
  • Versions side by side: each version gets its own folder; the active one is noted in vendor/packs/nunext-libs.php (not readable on the web). Installing writes into a temporary folder first and switches only when every file checked out – a failed install leaves the running version as it was. The active version, the previous one and two older ones are kept: Roll back switches back at once. vendor/packs/ itself is closed for the browser (deny-all .htaccess, written when the first pack is installed); TCPDF, PHPMailer, Adminer and PhpSpreadsheet get a deny-all .htaccess too; TinyMCE, phpMyAdmin and Uppy one that opens their folder (phpMyAdmin only after nuBuilder Forte's login check of its config) – so a pack of these three must not bring its own top-level .htaccess (building refuses it). An update of nuBuilder Next never touches vendor/packs/.
  • Self-test: TCPDF writes a small PDF, PHPMailer is loaded and checks addresses (send a real test mail under E-mail settings), TinyMCE is checked for its parts, phpMyAdmin for nuBuilder Forte's login check in its config (without it anybody could open them), Adminer for its blocked folder, Uppy for its script and style sheet, PhpSpreadsheet writes a small .xlsx file and reads it back (and names missing PHP extensions).
  • Old places: as long as no pack of a library is installed in vendor/packs/, nuBuilder Next still uses the copies of earlier versions – packs installed by older versions in third_party/<name>-<version>/ (they stay there and are shown as pack; installing a pack of that library puts the new one into vendor/packs/), the hand copies third_party/tcpdf, third_party/nudb, third_party/adminer, assets/vendor/tinymce, lib/PHPMailer, nuBuilder Forte's third_party/ and $nuConfigTCPDFPath / $nuConfigPHPMailerPath. An installed pack comes first (only an own $nuConfigTCPDFPath / $nuConfigPHPMailerPath still wins); Remove goes back to the old place. $nuConfigPMAURL points phpMyAdmin elsewhere ($nuConfigTFMURL is not used – the File Manager is built in). The old places are read until the upgrade baseline moves; the folders assets/vendor/ of earlier versions are left alone by the update – delete them by hand once everything works.

Versions a release needs: install/libraries-required.json lists, per library, the lowest version this version of nuBuilder Next works with and whether it must be installed ("needed": true) or only counts when it is there – none is required: nuBuilder Next runs without all seven (without TCPDF no PDF reports, without PHPMailer no e-mail – password reset, two-factor codes by e-mail, notifications by e-mail), so Check package warns only about an installed library that is too old. dev/release.py copies it into the package's manifest (requires_libs). Check package then lists every library the server does not meet – version installed, and the pack that would meet it (GitHub or _update/) – with Install the packs first, which installs them and comes back to the checked package. The update can still be installed; the features of those libraries may fail until they are updated. The tab Libraries marks a library below the need of the installed version (nuBuilder Next needs ≥ …), the unattended update reports them as libraries. So for a release that needs a newer library: publish its pack in the release libraries first, then raise the minimum in the file and release.

Building packs (developer mode, globeadmin): Update → Libraries → Build library packs (?p=libpack, password asked again, HTTPS or this computer).

  • Source folder per library – empty = ../libsrc/<name>/ next to the project when it exists (tcpdf, phpmailer, tinymce, phpmyadmin or nudb, adminer, uppy, phpspreadsheet – the PhpSpreadsheet folder is put together with python3 -I dev/pss_assemble.py <out folder>; all outside the project and the web root, so the sources never end up in a zip or on GitHub), otherwise the library in use now; the line under the name says which (folder names in any spelling, e.g. PHPMailer; if the host's PHP setting open_basedir hides the folder above nuBuilder Next – e.g. on free hosting that allows only htdocs – the page says so: then use _libsrc/<name>/ inside nuBuilder Next, next to index.php: nuBuilder Next writes a deny-all .htaccess into it as soon as it reads it, an update never touches it and it is never part of a package or backup; on nginx add _libsrc to the deny rule); TCPDF 7 = the whole Composer folder. Version: empty = read from the library or its NUNEXT-VERSION.txt.
  • Key: upload the signing key file – the one of nunext.zip; it is read in memory for this request, checked against the public key and never stored, logged or sent.
  • Result: the page builds and signs one zip per library and libraries.json (Keep the other libraries of the current GitHub index adds the packs not built now), checks every written zip again, and offers them one by one or as one zip. Attach them to the GitHub release libraries – step by step in Publishing the packs on GitHub.
  • Checks while building: no links, no nuconfig.php, .git, node_modules or logs; phpMyAdmin's config.inc.php must contain nuBuilder Forte's login check, and phpMyAdmin's config must not contain a blowfish_secret (it would be public).
  • Command line: php dev/libpack.php <out folder> <key file> --all (every library with a folder in ../libsrc/), or single ones tcpdf phpmyadmin=<other folder> uppy@<version>, plus --keep=<old libraries.json>.

Publishing the library packs on GitHub (step by step)

The packs live in one separate release with the tag libraries – never in a nuBuilder Next release (those carry only nunext.zip). It is created once and afterwards only edited when a library changes.

The first time – create the release:

  1. On the development installation: Update → Libraries → Build library packs, choose the key file, Build and sign, then Download all (zip). Unpack that zip (nunext-libs-<date>.zip) on your computer – it holds libraries.json and one nunext-lib-<name>-<version>.zip per library. The bundle itself is not uploaded.
  2. On GitHub, in the repository (nuBuilder/nuBuilder-Next, or the one set under Update from GitHub): Releases → Draft a new release.
  3. Choose a tag → type libraries (exactly this, lower case) → Create new tag: libraries on publish. The target branch does not matter.
  4. Release title: anything, e.g. Library packs. The description may stay empty.
  5. Drag libraries.json and every nunext-lib-….zip into the box Attach binaries – all at once; each must be its own file.
  6. Tick Set as a pre-release, so the release is never shown as the repository's latest one (on GitHub's page the newest nuBuilder Next version stays "Latest"). If the form shows Set as the latest release, leave it unticked.
  7. Publish release.
  8. On a server: Update → Libraries → Look on GitHub – the card lists the packs ("GitHub nuBuilder/nuBuilder-Next, release "libraries": … packs").

When a library changes – no new release, the same one is edited:

  1. Put the new version into its source folder (../libsrc/<name>/ or _libsrc/<name>/; for an own build raise the version: line of its NUNEXT-VERSION.txt, e.g. …nu2 → …nu3).
  2. Build library packs: tick only that library, leave Keep the other libraries of the current GitHub index ticked (the new libraries.json then still lists the other packs), choose the key file, Build and sign, download the files.
  3. GitHub: Releases → the release libraries → Edit (pencil). Delete the old libraries.json (and the old zip of that library, if it is no longer to be offered – servers only use what libraries.json lists), drag in the new libraries.json and the new zip, Update release.
  4. Servers see it at their next automatic look or with Look on GitHub; nothing is installed by itself. If a nuBuilder Next version needs the new library (install/libraries-required.json), publish the pack first, then that version.

Servers check every file themselves: libraries.json must be signed with the key of nunext.zip, each zip must match its size and SHA-256 in the index and its own signature – a changed or foreign file on GitHub is never installed.

TCPDF 7: TCPDF 7 is only a compatibility layer over tc-lib-pdf and needs it with about a dozen tc-lib-* libraries, Composer's vendor/autoload.php, the converted fonts of tc-lib-pdf-font and PHP 8.2 or newer. Build its pack from a complete Composer folder (vendor/tecnickcom/tcpdf/tcpdf.php and vendor/autoload.php) – nuBuilder Next finds TCPDF there and loads the autoloader; nuBuilder Forte keeps its own TCPDF 6. A folder with TCPDF 7 but without its libraries gives a clear message.

Own build or patched copy (e.g. a library from GitHub's master with your own fixes): put a file NUNEXT-VERSION.txt into the library's folder before building the pack. nuBuilder Next reads version: from it (e.g. 5.2.2+git.4149143.nu1 = release 5.2.2, master commit 4149143, own changes round 1 – compared as 5.2.2; the folder becomes nudb-5.2.2_git.4149143.nu1) and lines like CVE-…: open … / fixed … / patched locally …. The tab Libraries shows the version. Other lines are free (upstream, commit, downloaded, additions:, fixes: with "- " lines). The file is never served on the web (root .htaccess; nginx rule below).

version: 5.2.2+git.4149143.nu1
upstream: https://github.com/phpmyadmin/phpmyadmin
commit: 41491439a6b243c55502581e53fad20bc4c6e777
downloaded: 2026-10-19
fixes:
- config.inc.php: nuBuilder Forte's login check hardened

phpMyAdmin is packed with nuBuilder Forte's config file (config.inc.php) – the same for every server: they read ../../nuconfig.php, which from vendor/packs/<folder>/ is vendor/nuconfig.php – a two-line file of nuBuilder Next that loads its own nuconfig.php (from an old pack in third_party/<folder>/ it is the real one). So nuBuilder Forte's config files stay unchanged.

Font Awesome (icons fa fa-… of nuBuilder Forte forms): nuBuilder Forte's copy (<nuBuilder Forte>/third_party/fontawesome/, served through ?p=fa) when it is found – the same icons as nuBuilder Forte; otherwise, the copy in vendor/bundled/fontawesome-7.0.0/ (the version nuBuilder Forte 4.9 ships). $nuConfigFontAwesomePath chooses another folder. If nuBuilder Forte is not the folder above nuBuilder Next, set $nuConfigNuBuilderPath.

PHPMailer in the package: nunext.zip brings the signed PHPMailer pack in _install/, so the installer installs e-mail without GitHub. An update does not bring it (_install/ is never written by an update) – existing installations take it from the GitHub release libraries or an upload.
