Help pages for your users

Write help for the people who use your application – in the browser, without code – and open it from a form, a tab or a field.

For: Administrators (globeadmin, admin roles with the right Help pages)

This guide explains nuBuilder Next itself. The help pages are for the application you build: what a screen is for, how to do the usual tasks, what a field means. Your users read them in a side panel next to the form they are working on, or on the help page of their own (user menu → Help, index.php?p=userhelp), with contents, search and links between the pages.

Write a page

  1. Help pages (start page tile, index.php?p=helppages) → Add.
  2. A title and a code – the short name forms and other pages use to point at the page (letters, digits, _ . -).
  3. Write the text in the visual editor: headings, lists, tables, pictures (pasted or chosen from a file – PNG, JPEG, GIF or WebP up to 10 MB, stored as files on the server and shown only to users who are signed in), links. Without the TinyMCE library pack, or if you prefer, switch to Markdown.
  4. Optional: a parent page and an order (the contents of the help is a tree), keywords for the search, access levels (below).
  5. Leave Published off while you write: a draft is only shown to those who edit the help pages.

The text is cleaned when it is saved: scripts, event handlers, frames and forms are removed, links keep only safe targets.

Insert adds the markers described below, a link to another help page or a hash variable. Draft with AI builds a prompt with the tabs and fields of a form, in the language you choose in the dialog (your interface language unless you pick another; the last choice is kept). When the chat answers in Markdown instead of HTML, Use answer turns headings, lists, tables and bold text into the visual editor's formatting (on a Markdown page the text is kept as it is). Related screens are found too – sub-forms, the lists a field picks its value from, forms opened by buttons – and offered as ticks (sub-forms ticked), so the help also explains adding rows or picking a value. Focus (optional) tells the AI what to stress – a task, a group of users, a tricky field (e.g. “closing a ticket, for new agents”); left empty, the page covers the whole form. Paste the prompt into the AI chat you use, paste the answer back, check it, publish it. View opens the page as your users see it.

Open it from a form, a tab or a field

In design mode, section Help:

  • Help page of the form – a Help button appears in the form's button row; it and F1 open the page in the side panel.
  • Tab … – a tab with its own page opens that one while the tab is shown.
  • Select a field: Help page of the field – a small (?) after its label shows the first paragraph of the page as a tooltip and opens the page on a click.

The panel has a link to open the page in a new tab, links to other pages open inside the panel (← goes back). Drag its left edge to make it wider or narrower (double-click: the default width); the width is kept in the browser. Users only see the button and the marks when they may read the page. The editor lists under Used on where a page is linked. Add to a form… there links the saved page without design mode: pick the form, then the whole form (its Help button), a tab or a field; a place that shows another page turns the button into Replace. The × next to an entry removes the link (the page stays). The published form changes at once – and an open draft of it too, so publishing the draft keeps the link. Needs the change right on help pages and the save right on forms.

Different help for different access levels

A whole page: choose its access levels – only users with one of them (main or additional level) see it in the contents, the search and the panel. Empty = everyone who is signed in.

Parts of a page: put markers with the codes of access levels in paragraphs of their own:

[[level: sales, support]]
Text only these levels read.
[[else]]
Text everybody else reads.
[[/level]]

[[not: guest]]
Hidden from guests.
[[/not]]

[[else]] is optional, markers can be nested, globeadmin works as a code. Those who edit the help pages see every part, framed and labelled; on the help page, View as shows the help exactly as a user of one access level (or of none of them) reads it.

Links, names, translations, moving the help

  • Links between pages: #help=<code> as the address (Insert → Link to another help page, or the link dialogue's list). A link to a page the reader may not open is shown as plain text.
  • Hash variables such as #USER_NAME#, #USER_FIRST_NAME#, #ACCESS_LEVEL_CODE# or #USER_DEPARTMENT# are filled in for the reader.
  • Translations: Translations on a saved page adds the text in another installed language (title, text, keywords; the rest belongs to the page). Users read their language, else the page itself. Translate with AI builds the prompt from the page.
  • Export / import: all pages as one JSON file (format nunext-help-1) – to move the help to another installation. Access levels travel by their code; levels missing there are left out and named.
  • Users find the pages in the start page search and Ctrl+K too. A tile for user start pages: an own tile of kind page with the target userhelp.

Stored in the table zzzzsys_nunext_help (one row per page and language), the pictures in the folder custom/userhelp/ (named after their content, so the same picture is kept once; pictures no page uses are removed by the housekeeping after a day; an export carries them inside the JSON file, an import makes files of them again); the links of forms, tabs and fields in sfo_json / sob_all_json under nunext.help and nunext.help_tabs – nuBuilder Forte ignores them.
