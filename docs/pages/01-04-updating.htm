Updating nuBuilder Next

Advanced Installing a new version from the browser, from GitHub or from the command line, with backups and rollback.

For: Administrators (globeadmin, admin roles)

Start page → Update (in tabs: Update – install a new version; Backups – list, Back up now, restore, keep rule; History – the change history; Libraries – the library packs and the libraries in the package; System – server requirements, database steps and database structure. A dot on System means something there needs a look – red: a requirement is not met. The tab is part of the address, e.g. index.php?p=update#backups). This help and the tutorial always belong to the installed version; when the daily GitHub check has found a newer one, they say so at the top (for users who may update) with a link to Update – the newer help comes with the update:

Updates switched off: with nuBuilder Forte's setting $nuConfigEnableDatabaseUpdate = false (in nuconfig.php, or in the Settings with $nuConfigSettingsFromDB) the Update page shows a notice and allows no upload / install of a package, no rollback and no Apply of the database structure – also refused on the server. Backups, downloads and deleting backups still work; the database steps of the installed version still run. Not set or true = updates allowed.

  1. Without uploading: copy nunext.zip by FTP into the folder _update of nuBuilder Next (<nuBuilder Next>/_update/ – the page creates it; the web cannot read it, updates never touch it). The page lists every zip there with version, size and date; packages with a valid signature can be chosen – unsigned, broken or foreign zips are listed but not offered. Check package continues as with an upload; after a successful install the zip is deleted from the folder (Cancel keeps it). Useful for big packages or a small upload limit of the host.
  2. Layout: the card Install a new version shows Update from GitHub first; Other ways to update (upload a zip, the folder _update) is folded – click it to open it. This browser remembers whether it was open; it opens by itself when a signed package waits in _update.
  3. From GitHub: the section Update from GitHub looks for the newest release of the repository (default nuBuilder/nuBuilder-Next, public repositories only) that has the file nunext.zip attached, and shows its version, date, size, a pre-release badge and a link to the release notes. Look for a new version asks GitHub now; Check for updates automatically (Never, Once a day – the default –, Once a week or Once a month) asks GitHub again when that time has passed – when cron.php runs, or when someone who may update opens the start page or the update page (other users never wait for GitHub); the update page also looks again when the release it knows is not newer than the installed version and the last look is more than an hour old, so a release published since then shows up – and a newer version shows a green New: x.y.z badge on the Update tile of the start page. Download x.y.z and check downloads the zip into the folder _update and continues with Check package as above – a download whose signature is not valid is deleted at once, so a changed file on GitHub can never be installed. The message names the reason: not signed, signature not valid, not a nuBuilder Next package, or PHP's zip extension missing (the package cannot be read at all). Without PHP's sodium extension the signature cannot be checked: the download is kept and Check package shows that warning, as for an uploaded zip. The Security check lists both extensions. Settings: the repository (owner/name), whether pre-releases count (default on, nuBuilder Next is alpha) and how often to check automatically. The server needs outgoing HTTPS access to github.com; GitHub allows 60 requests per hour per server address without a login. Downloads are only taken from GitHub's own addresses, at most 64 MB.
  4. Choose the new nunext.zip and click Check package (the button shows a spinner and is locked until the check is done). Nothing changes yet: you see the version, how many files change, which old files are deleted and what's new, and whether the package is signed by nuBuilder Next (a package whose signature does not match is refused, an unsigned one shows a warning). Install nunext.zip; nunext-dev.zip is for development (it adds the notes and tools that are never installed).
  5. Database changes of this update: Check package lists, grouped by table, what installing the package changes in the database – nothing is changed by the check:
    • the package's database steps this database has not run yet, with the tables they touch and how (e.g. zzzzsys_nunext_list_view · data · the start page layout inserted as shared layout "Standard");
    • new tables and columns of nuBuilder Next's own tables (zzzzsys_nunext_* – missing columns of existing own tables are added too);
    • missing columns and safe type changes of nuBuilder Forte's tables (the same as Database structure below, where they are selected). Columns whose type in your database is larger than nuBuilder Forte 4.9's (e.g. longtext instead of mediumtext) are no change of the update: they stay as they are and are only listed folded (… columns have a larger type … – left as they are); making them smaller is possible under Database structure but not recommended;
    • a refresh of the sample data.
    Each structure change has an SQL link with the statements for this database (MySQL / MariaDB or SQL Server). Nothing to do: No changes to the database. Packages of older versions do not describe their steps – then only the structure is compared. The dry run of the unattended update (API "dry_run": true, php cron.php update … --dry-run) returns the same list as database (steps, tables with kind, what, step, risky, sql). The package carries the description as install/db_changes.json (written by dev/release.py from NuMigrate::CHANGES and the own table definitions).
  6. Database structure: the check compares the zzzzsys_ tables with what the new version expects (nuBuilder Forte 4.9's tables and nuBuilder Next's own, install/schema_expected.json). Missing columns and columns with a smaller type (e.g. varchar(100) instead of varchar(255)) are listed and selected; they are changed when you click Install, before the files are copied. Columns whose database type is larger or different are listed separately and not selected – changing them could cut off or convert values. Column types are compared on MySQL / MariaDB only (MSSQL, SQLite: missing columns). Primary keys and extra columns are never changed, missing tables are not created. Back up the database first: the file backup does not cover structure changes. The same check is at the bottom of the update page for the installed version (Change selected columns).
  7. Click Install and confirm: a window with a spinner shows the version being installed and that the page must stay open until the result appears (it cannot be closed; Install and Cancel are locked – the install also finishes on the server when the connection drops; open the update page again to see the result). nuBuilder Next checks every file, makes a backup (program files and nuBuilder Next's own tables, plus an SQL dump chosen in Database in the backup: nuBuilder tables (the default – every zzzzsys_ table of nuBuilder Forte and nuBuilder Next, which is all an update can change; your own application tables are never touched by an update), whole database or none. Your application data needs its own backup, usually the database backup of your host), switches on maintenance mode (users see a short notice; you keep working), copies the new files, removes old ones and resets PHP's code cache. If copying fails, the backup is put back automatically.
  8. In developer mode ($nuConfigDevMode = true) the card Install a new version is shown above the result of an update, so the next package can be uploaded right away.
  9. Unattended update (command line or REST API) – the same steps without a browser, for scripts, cron jobs and updating several installations from one place. Only packages with a valid signature are installed; $nuConfigEnableDatabaseUpdate = false blocks it; one update at a time (lock file); every run is logged and kept as a job (_backup/update-job-*.json, the last 20). Options for both:
    • url (https; http only for localhost; at most 64 MB) – or "github": true (the newest release of the repository set on the update page; not newer than the installed version → error unless reinstall) – or on the command line zip (a file on the server); sha256: expected checksum of the package (optional).
    • backup: auto (default) or nubuilder: the zzzzsys_ tables without logs · files: program files only · sql / sql_nologs: the whole database with / without logs.
    • schema: database columns to change before the files – safe (default, as the page preselects: missing columns and larger types) · missing · all (also types that could cut values) · none.
    • sample: auto (default: refresh the sample data when the package brings a newer sample version) · yes · no. New sample passwords are never printed or returned: Sample data → New passwords.
    • reinstall: also when the package is not newer. dry_run: check only – signature, requirements, file changes (new / changed / removed), database differences and what would be applied, sample data, backup mode – nothing changes.
    Like the page, an update has two phases: the check and install, then the database steps with the new code. The command line starts the second phase itself in a new PHP process; for the API it runs on the status request; a job that is still pending is also finished by cron.php and by opening the update page.
    Command line (as the web server's user, so the new files belong to it): sudo -u www-data php cron.php update --url=https://example.com/nunext.zip --dry-run (or --github instead of --url), then without --dry-run. Options as --backup=sql --schema=missing --sample=no --reinstall --sha256=… --json; php cron.php update --status [job] lists the jobs; exit code 0 = done / checked, 1 = failed, 2 = wrong call.
    REST API: an API client with the scope system:update (admin level – give it only to a client you trust, ideally with an IP allowlist). POST /v1/system/update with {"url": "https://…/nunext.zip", "dry_run": true} answers 200 with the check; without dry_run it installs and answers 202 with the job and Location: /v1/system/update/{job}. Call GET /v1/system/update/{job} once afterwards: it runs the database steps and returns status: done (or failed with the errors). GET /v1/system/update shows the installed version and the last jobs. A failed check answers 409 with the errors. The API playground has the three requests.
  10. Sample data: when the sample data is installed, Update the sample data too appears next to Install – ticked when the package brings a newer sample version (the label shows both versions). After the update (with the new code) the sample data is refreshed as with Admin tools → Sample data → Refresh: all sample records are created again, changes to them are lost and the sample users get new passwords; the result page links to them.
  11. The Server card lists what the update needs. Folder writable is red when PHP may only read the program folders – usually because they were uploaded by SFTP and belong to the SFTP user (permissions 755), while PHP runs as the web server's user (e.g. www-data). The (i) next to it shows the fix: chown by SSH, or in the SFTP client set the folders to 777 for the update (recursive, folders only) and back to 755 afterwards – or update by hand by uploading the files of nunext.zip over the old ones (the database steps run on the next page view). PHP upload limit is red below 16 MB (upload_max_filesize / post_max_size).
  12. The tab Libraries: the library packs (install, update, roll back, remove, self-test) and the card Libraries (collapsed – click to open; a yellow badge counts problems) with the libraries in the package – version, folder, use and licence, replaced by an update. Check package also lists the libraries the new package changes (e.g. Tom Select 2.6.2 → 2.7.0).
  13. The next page shows "Updated from … to …" and runs the database steps of the new version. Maintenance mode ends – also by itself as soon as the new version is completely installed (e.g. when the update logged you out), at the latest after 15 minutes; End maintenance mode on this page ends it at once.

Change history: the card Change history on the update page lists every version of the installed package, newest first – 10 per page with the list footer, the installed one with a green badge, the newest five open; the search field (Enter) finds versions by number, title and text, with every hit open. The user menu entry nuBuilder Next 0.8.x · What's new opens it.

nuconfig.php, vendor/packs/ (the library packs) and the copies of earlier versions in third_party/, assets/vendor/ and lib/ are never touched; vendor/bundled/ is replaced by the package's libraries.

Backups are listed below the upload, newest first, 10 per page (first / previous / page / next / last below the list): download, Roll back (puts the program files of that version back – the current files are backed up first; database changes stay) or delete them. Back up now makes one by hand – once per click: the button is disabled while the backup is made, a second click or a resent form is refused ("already made"), and two backups never run at the same time. Backups are stored in _backup/, or in $nuConfigBackupPath – preferably a folder outside the web root, above all when backups contain the database.

Deleting several backups: tick backups in the first column (the box in the header ticks all on the page) and click Delete selected (n) – the confirmation says how many and how much space is freed. Clean up… opens a rule: Keep the newest … backups or Delete backups older than … days; a preview lists what would go before Delete now (n) deletes it. Save rule only stores it, and with Apply automatically after each update the rule runs after every successful update (the tab button then shows automatic). Never deleted by either: the newest backup (the way back from the last update) and the newest safety backup made before a roll back – they show a lock instead of a box; the delete button of their own row still works. Every deletion, also of a single backup, is in the log (Backups deleted, with the file names).

Database in the backup (MySQL / MariaDB and SQL Server – written by the App cloner's export): next to Back up now, Database chooses none (the default), nuBuilder tables (every zzzzsys_ table) or the whole database – tables, views, data, functions, procedures, triggers and events, written by the same code as the App cloner's Download SQL (sessions and one-time tokens are left out). without logs (default) creates the log tables empty. The sizes shown are estimates. The dump is stored gzip-compressed in the backup (db/database.sql.gz):

  • A green SQL badge shows its size (tooltip: tables and rows). The download button then offers Whole backup (.zip) or SQL only (.sql.gz) – that file can be imported with phpMyAdmin (Import) or zcat file.sql.gz | mysql newdb – SQL Server: unpack it and run it with SQL Server Management Studio or sqlcmd. Restoring the database is done by hand; Roll back only puts the program files back.
  • Every dump ends with a marker line that is checked: if it is missing or the dump failed, the badge says SQL incomplete (red) – don't rely on it. If the server stops the backup (time limit), no backup is saved and the next visit of the update page says so; choose nuBuilder Next tables or without logs, or ask your hoster for a longer time limit.
  • MySQL / MariaDB: the dump is taken in one consistent snapshot (InnoDB) with TIMESTAMP values in UTC – records saved during the backup can't leave half a change in it, and it imports with the same moments on a server in another time zone. INSERT statements are at most about 1 MB, so the import also works where max_allowed_packet is small.
  • Keep SQL dumps in the newest … backups (default 5, 0 = all): older backups lose their dump automatically (badge SQL removed), their program files stay. The header shows the number and total size of the backups.

If the update page is not available (e.g. PHP may not write to the folder): unpack the zip over the old folder (nuconfig.php and _backup/ stay), and log in as globeadmin – the database steps run automatically. What changed in each version: CHANGELOG.md in the package, or Change history on the update page.

The server needs PHP 8.1+, the zip extension, write permission for PHP on the nuBuilder Next folder (Plesk: the folder belongs to the site user) and some free disk space – the update page shows each of them.
