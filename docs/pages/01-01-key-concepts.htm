Key concepts

The ideas everything else builds on: metadata-driven forms, objects, hooks, hash variables, access levels and nuBuilder Next's own tables.

For: Everyone

Forms are data

A form is a row in zzzzsys_form with its tabs (zzzzsys_tab), objects (zzzzsys_object), list columns (zzzzsys_browse), JavaScript events (zzzzsys_event) and PHP hooks (zzzzsys_php). The design mode edits these rows; nuBuilder Next draws the form from them on every request. Nothing is generated as files, so a form changed in design mode is live at once – or, with a draft, after publishing.

  • Form types: browse and edit (a list and a record), browse or edit only, launch (a form without a table, e.g. a menu), subform (shown inside another form) and page (your own PHP, see Pages).
  • Objects are the fields and elements on a form: input, select, lookup, subform, calc, display, HTML, image, run (button), word, contentbox, chart … – see Object types. An object's ID is the column it saves to.
  • The browse SQL of a form is the SELECT of its list; the browse columns say which of its columns are shown.
  • List and record: a tile or button opens a form's list (nuBuilder Forte's search or browse screen), a row of the list opens the record (the edit screen); Add opens the same screen empty. The whole application follows this pattern – see The pattern every form follows.

Code: hooks, procedures and events

  • PHP hooks of a form run on the server: Before Browse, Before Edit, Before Save, After Save, Before Delete, After Delete – and After Browse of a lookup. Global hooks (procedures with reserved codes) run for every form.
  • Procedures are named pieces of PHP that buttons, run objects, nuRunPHP() and nuRunPHPHidden() start, and that reports use.
  • JavaScript runs in the browser: the form's custom code, object events (onchange, onclick …) and hooks such as nuOnLoad() or nuBeforeSave().

The order in which they run is on Form lifecycle and event order.

Hash variables

#RECORD_ID#, #USER_ID#, #cus_name# … are replaced by their values in SQL, PHP and HTML before the code runs – the record, the user, the form's fields and properties set with nuSetProperty(). Unlike nuBuilder Forte (4.x), values are escaped for the place they are inserted into, so a field value cannot break out of a quoted SQL or PHP string. See Hash variables.

Rights

The globeadmin (login from nuconfig.php) may do everything. Every other user has a main access level – and optionally additional ones with an end date (see Additional access levels) – that lists the forms, procedures and reports they may use and, per form, the buttons (Save, Add, Delete, Clone, Print). Permission items are named switches your code checks; admin roles give a user a defined part of the globeadmin's tools; field data access decides per field who sees and changes it. See How rights work.

nuBuilder Forte's tables and nuBuilder Next's tables

All system tables start with zzzzsys_. nuBuilder Next reads and writes nuBuilder Forte's tables the way nuBuilder Forte does, and keeps everything only it needs in tables named zzzzsys_nunext_* – sessions, log, audit trail, form drafts and history, start page settings, dashboards, API clients … They are created by the installer (or when the globeadmin signs in); nuBuilder Forte never reads them and its updates keep them. See Database schema and Database table reference.

Configuration in two places

nuconfig.php holds the database connection and settings in PHP variables – the same file and variable names as nuBuilder Forte, plus nuBuilder Next's own (Configuration). nuBuilder Forte's settings table zzzzsys_config holds the settings of nuBuilder Forte's Setup → Settings – in nuBuilder Next Settings → nuBuilder Forte (Settings). nuBuilder Next's own installation settings (security, start page layouts, branding …) are JSON rows in zzzzsys_nunext_setting.
