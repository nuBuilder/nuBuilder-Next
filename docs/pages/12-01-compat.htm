Compatibility check

Which nuBuilder Forte (4.x) functions your application uses and whether they work.

For: Administrators (globeadmin, admin roles)

Start page → Compatibility check scans all code of your application – form JavaScript, object events, lookup code, HTML objects, the setup header and procedures – for calls of nu…() functions and shows for each one whether nuBuilder Next supports it:

  • supported – works in nuBuilder Next; stub – exists but does nothing yet; missing – a nuBuilder Forte function nuBuilder Next does not have (the call fails); unknown – not a nuBuilder Forte function (typo, other library); your own – defined in your code, in the files of $nuConfigIncludePHP / $nuConfigIncludeJS (looked for in nuBuilder Next's folder, then nuBuilder Forte's, as the form page does), in the scripts of Setup → Include or in Global JS.
  • Each row shows the number of calls and where they are; form names link to design mode and procedures to the procedure (both in a new tab, so the list stays open). Show supported functions too lists everything, Include nuBuilder Forte's own forms also scans the nu… forms.
  • Run it after importing an application into a database used by nuBuilder Next, and before opening it to users.
  • nuBuilder Forte 4.9 features: the features of the nuBuilder Forte 4.9 compatibility review your application uses, with the places (form, object, procedure, line of nuconfig.php) and since which version nuBuilder Next supports them – red = not supported yet, test these places by hand. IDs as in the review: C1–C6 (browse columns with table names or aliases, AS aliases, browse SQL without the primary key, SELECT * over joins, nu_filter_match, access conditions), M1–M10 (scripts in HTML objects, nuAddBrowseTitleSelect, multi-value filters, selects from a procedure, files into the file system, $nuConfigIncludeJS / …CSS, nuAfterSave, nuFORM methods, report PDFs from PHP, SSO), N1 (nuSERVERRESPONSE), I3 (MyISAM tables). Also the points of the nuBuilder Forte 4.9 gap analysis – not only function names: G1 access levels with data mode / form type, G2 global hook procedures, G3 calc objects on sub-forms, G4 events onnuload / onenter, G5 nuFORMdata, G6 scripts, frames, styles or images from other sites that the Content Security Policy of form pages blocks (images from https://, this server and the sites of scripts / stylesheets named in $nuConfigIncludeJS / $nuConfigIncludeCSS or Setup → Include are allowed and not listed; frames, fonts and fetch() to other sites have no setting – copy the file onto the server), G7 hash variables nuBuilder Next does not set (#USER_A11Y#, lower-case internals such as #browse_sql#), G10 users with additional access levels (nuBuilder Forte 4.x gives them only the rights of the main level), G8 hidden procedures that read #RECORD_ID# / #FORM_ID# (shown as supported, the places stay listed: in a hidden procedure nuBuilder Forte fills #RECORD_ID# with the procedure code and #FORM_ID# with doesntmatter, nuBuilder Next with the open record and form). The lower-case #record_id#, #form_id# and #hash_record_id# that nuBuilder Forte code reads instead hold the open record and form here as well – a field, property or hash cookie of the same name comes first, as in nuBuilder Forte.
  • Hash variables outside quotes: #field# is escaped for a quoted string only. In WHERE id = #field# or $x = #field#; a user can put SQL or PHP into a field value. The list shows every procedure, hook, browse SQL, select / display SQL and SQL builder query with such a variable (also SQL inside PHP strings, nuRunQuery("… = #x#")). Fix: '#field#' in quotes, or parameters (nuRunQuery($sql, [$value])). Variables the server sets (#USER_ID#, #FORM_ID#, #TABLE_ID# …) are not listed; #RECORD_ID#, #ID# and #CODE# are – they come from the browser.
