Contributing: development with Claude

How nuBuilder Next itself is developed, released and tested.

For: Globeadmin in developer mode

Only shown in developer mode. nuBuilder Next is developed in sessions with Claude (Anthropic's AI) working on a copy of the project in its own Linux workspace: it changes the code, tests it in a browser against a real nuBuilder Forte (4.x) database and hands back two signed zips. The rules it follows are in CLAUDE.md (in nunext-dev.zip and the repository, never in the install package) – read it once; this chapter is the short version for the developer.

What a session needs

  • Claude with a workspace: a Claude session that can run commands and handle files (Claude Code – web, desktop or terminal – or claude.ai with the code / file tools). It needs internet access for the package registries (apt, npm, pip) and GitHub (cloning nuBuilder Forte for the test installation, and pushing).
  • nunext-dev.zip of the last release – the whole project including CLAUDE.md, TODO.md, dev/ (release script, tests, tools) and .github/.
  • The signing key file nunext-signing.key (see below) – without it releases are unsigned and every installation warns.
  • For "gate": write access to the repository nuBuilder/nuBuilder-Next in the session (GitHub connection with push rights).

Nothing survives between sessions: the workspace, the test database and the test installation are rebuilt from the zip each time (CLAUDE.md → "Test environment": MariaDB, PHP's built-in server, a clone of nuBuilder Forte with nuBuilder Next inside it at /nunext/, Playwright with Chromium, PHPStan, ESLint, axe-core).

Starting a new session

  1. Attach nunext-dev.zip (from the last answer) and nunext-signing.key.
  2. First message, e.g.: "New session: unpack nunext-dev.zip, put nunext-signing.key next to the project folder, read CLAUDE.md and TODO.md, rebuild the test environment." – then the request.
  3. Claude unpacks to nunext/, puts the key next to it (../nunext-signing.key – outside the project, never in a zip), installs MariaDB / the test site / the tools and reads the newest changelog sections.

A long session that reaches its context limit continues with a summary – nothing to do. A new session is only needed when the old one is gone; always send it the nunext-dev.zip of the last answer.

The signing key

  • An Ed25519 key pair. The public key is in the code (NuUpdate::SIGN_PUBLIC in core/nuupdate.php); every installation checks nunext.zip and the library packs against it. The secret key is the file nunext-signing.key (last line = the base64 secret key) – whoever has it can make packages every installation accepts. Keep it private: never in the project, a zip, the repository, a ticket or a chat that is shared.
  • Where the tools look for it: $NUNEXT_SIGNING_KEY, ../nunext-signing.key (next to the project folder), ~/.nunext-signing.key. The page Build library packs takes it as an upload for that one request and never stores it.
  • A new key pair (only if the old one is lost or leaked): 
    php -r '$k = sodium_crypto_sign_keypair(); echo "nuBuilder Next signing key\n", base64_encode(sodium_crypto_sign_secretkey($k)), "\n"; fwrite(STDERR, "public: " . base64_encode(sodium_crypto_sign_publickey($k)) . "\n");' > nunext-signing.key
    Put the printed public key into NuUpdate::SIGN_PUBLIC and release. Installations still on the old key refuse the new packages – update them once by hand (unpack the zip over the folder), and rebuild the library packs with the new key.
  • Not the same as $nuConfigSecretKey in nuconfig.php – that one is per installation (API tokens, one-time links) and never leaves the server.

Requests

  • A short request ("add a filter to the users list") → Claude builds it and ends with a fast release (next version 0.8.x+1), tests of the changed areas and a look in the browser, and sends both zips. It asks first only when a wrong guess would be expensive.
  • "Suggest …" → numbered options with a recommendation, nothing built. Answer with the option, "do recommendations" or "ok all".
  • "Gate" → full release gate and push to GitHub (below).
  • Every release: version bump, CHANGELOG.md section, texts in all eleven languages, the help (this file), TODO.md (points to verify), tests for new features. No personal details of the developer in any file.

The push makes the code public on GitHub – it does not create a GitHub release. Servers updating from GitHub only see a version once its release exists (next chapter).

Making a release by hand

  1. In the project folder (key next to it): write the changelog text into a file – - bullets, continuation lines indented by two spaces – and run python3 dev/release.py 0.8.x "Title" changes.txt (add --gate with the test variables set). The version must be higher than NU_VERSION.
  2. It updates README.md (version line), CHANGELOG.md, NU_VERSION in core/nuapp.php, lang/en-US.php / de-CH.php, install/db_changes.json, writes and signs nunext-manifest.json and builds ../nunext.zip and ../nunext-dev.zip.
  3. Check it like an installation would: php dev/inspect.php <test installation> ../nunext.zip → ok=true, the new version, signature=valid, errors=[].
  4. Publish: on GitHub create a release with the tag v0.8.x (on the pushed commit), release notes made from the changelog (Claude writes them on request after the template dev/release-notes.md: link to the changelog, highlights, security, steps after updating), and attach nunext.zip (that file name – the update page looks for it; pre-release while nuBuilder Next is alpha). nunext-dev.zip is not needed there (the repository is the same).
  5. Library packs are a separate, fixed release with the tag libraries – touched only when a library changes (Publishing the packs on GitHub). If the new version needs a newer library (install/libraries-required.json), update that release first.

If a release must be rebuilt before it went out: set NU_VERSION back, remove its CHANGELOG.md section and the manifest's changes entry, then run it again.

What the packages contain

  • nunext.zip – the install / update package, folder nunext/ inside: everything that runs on a server. Left out because they are readable on a web server and not needed there: CLAUDE.md, TODO.md, .gitignore, dev/, .github/. Added (not in the manifest): _install/nunext-lib-phpmailer-<version>.zip, built and signed by release.py from dev/libsrc/phpmailer/ – to update PHPMailer, replace that folder (only the release's PHPMailer; existing servers get it from the libraries release). release.py compares its version with the GitHub release libraries and warns when they differ – then publish the new pack and libraries.json there (php dev/libpack.php <folder> ../nunext-signing.key phpmailer=dev/libsrc/phpmailer --keep=<current libraries.json>), so new installations and updates get the same version.
  • nunext-dev.zip – the whole project, to continue the development (send it to the next session). In developer mode, To do → Upload nunext-dev.zip / Upload new takes only TODO.md out of it (or a TODO.md uploaded on its own) and replaces the server's copy without asking; the zip is deleted at once.
  • nunext-manifest.json (in both): version, built, files (SHA-256 and size of every deployed file – the update checks each one and knows which old files to remove), changes (the change history shown on the update page), libraries (bundled libraries and versions), requires_libs (library versions this version needs), page_api (page form API versions – pages that would break are listed), gated / last_gate, and signature (Ed25519 over nunext-release|<version>|sha256 of the file list).
  • Also inside: install/db_changes.json (the database steps and own tables – Check package previews the database changes), install/schema_expected.json (structure check), install/libraries-required.json.
  • Folders: vendor/bundled/ (bundled libraries, registry libraries.json), vendor/nuconfig.php (loader for the packed configs of phpMyAdmin / Tiny File Manager).
  • Never inside: nuconfig.php, vendor/packs/, third_party/, _backup/, _update/, the signing key (see .gitignore).

Tests

  • php dev/tests/run.php – unit tests without a database (every release).
  • dev/tests/smoke.js – opens every page; dev/tests/e2e.js – the end-to-end tests (forms, rights, update page, library packs …; ONLY=name1,name2 runs single ones; it saves the database first and puts it back); dev/tests/compat.js – nuBuilder Forte 4.9 and nuBuilder Next on the same database, a save without a change must leave nuBuilder Forte's rows alone.
  • dev/tests/install.js – the installer with an uploaded nubuilder4.sql (and LIBPACKS=<folder> for the library step); load.js – large data and timings; a11y.js – accessibility (WCAG 2.1 AA) in light, dark and phone width.
  • Self-test (?p=selftest) – the same kind of checks inside a running installation.
