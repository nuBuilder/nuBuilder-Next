Access levels

Which forms and buttons a user may use.

For: Users with rights on: nuaccess

Menu Access levels. An access level lists the forms a user may open and, per form, the buttons: Save, Add/New, Delete, Clone, Print. The row itself means "may view". Procedures need their own entry.

When you set up a level, remember the forms users reach indirectly: the criteria form (launch form) of each report – without it the report runs at once without criteria – and the lookup form of every lookup they use. A report also needs its own tick under Reports. Check the result with Act as user; a full example is in Your first application.

The other way round – all access levels of one form: on the open form (list or record) choose ⋮ → Access levels…, or in design mode Form settings → Tools → Access levels. The dialogue lists every level with Open (the level may use the form), its buttons, data mode and form type; search, a group filter and a tick box in the title of Open and of each button column (for the levels shown) help with many levels; a click on a column title sorts by it (ticked first for Open and the buttons, again for the other way round). A level that gets the form starts with Open only – tick its buttons. Save writes only the levels that changed (logged per level); the arrow opens the level itself. It needs the right to view access levels, and to change them their Save right; with Only the globeadmin grants admin rights nobody changes their own levels or grants new admin-equivalent rights here either.

Forms for everyone – the switch Everyone at the top of that dialogue gives the form to every access level at once, with the buttons ticked next to Buttons for all (Open is always on). It writes the normal form rights of each level, so nuBuilder Forte opens the form for everyone too. While it is on, the table of levels follows it (read-only); the badge counts the levels that already have the form – orange when some still miss it, and Save then adds them. Also for new access levels (on by default) gives the form to every level created or cloned later in nuBuilder Next (also through the REST API), with a message naming the forms added; levels created in nuBuilder Forte do not get it – the Compatibility check lists such gaps (FE), and opening the dialogue and Save closes them. Switching Everyone off keeps the rows, so single levels can be taken away again. In the forms list the column Access levels shows Everyone for these forms, and the filter Access levels finds them (or the forms no level may open). Admin-equivalent forms (users, access levels, forms, procedures, SQL builder, setup) can never be given to everyone.

The form has two tabs: General (code, description, group, start form – the button next to it opens the form in a new tab –, two-factor login, the users with this level and their full names) and Form rights (the forms and their buttons; the badge shows how many; a click on a column title sorts by form, by a right – ticked first – or by data mode / form type, and the browser remembers it). The open tab stays after Save and in the address (&tab=rights); an error opens the tab that shows it.

In the list, the counts Form rights, Procedures and Reports open the level on that part, Users opens the users list filtered by it; the filter Can open form lists the levels that have a given form. On the level, the Users card's Show in the users list opens the users list with every user of the level, also those who have it as an additional level.

  • Use two-factor authentication: users of this level must confirm their login with a second factor – an authenticator app or a code by e-mail (hover or focus the icon for this hint). It needs $nuConfig2FAUser = true; the form shows whether it is on, and while it is off the globeadmin can switch it on there (Switch on, or a link to Settings when the settings table is used).
  • Reports: the reports users of this level may run (nuBuilder Forte's zzzzsys_access_report); the form shows how many are ticked. They are set on the report itself (see Reports).
  • Adding forms: pick one form from the list (type to search by code or description; forms already in the list are greyed out), or click Several…: search (code, description, table), filter by form group, type and own / nuBuilder Forte (4.x) system forms, tick the forms (or Select all shown) and choose the rights the new rows get – e.g. everything but Delete. Forms already in the list are hidden. Save afterwards.
  • Removing a form: crosses the row out – it is removed when you save the access level. Until then the same button () brings it back. The design mode's lists (tabs, list columns, events, columns of a new table, HTML attributes) work the same way.
  • Data mode and Form type per form (as in nuBuilder Forte 4.9, enforced): No changes to existing records opens existing records read only, without Save – the server refuses a save even from code (“Changes to existing records are not allowed”); new records, Clone and Delete follow their own rights. Browse only shows the list, but no record (also no new one: no Add, rows open nothing); Edit only opens records, but not the list (nor its export). The globeadmin and admin roles with change on the form are not limited.
  • Users card: the users with this level, by default only the active ones – Archived shows the users whose Valid until is in the past, All both (with counts).
  • An access level cannot be deleted while users still have it. Deleting it also removes its form, procedure and report rights; cloning copies them.

Additional access levels

A user has one main access level (nuBuilder Forte's sus_zzzzsys_access_id) and can get more in the user form (Users → Additional access levels), optionally until a date. nuBuilder Next stores them in its own table zzzzsys_nunext_user_access.

  • They only add: on a form a right counts when any level grants it (Save, Add, Delete, Clone, Print); browse and edit screen when any level allows them; No changes to existing records only when every level with the form says so. Procedures, reports and dashboards of every level are open to the user, and the forms list and the automatic start page show them.
  • From the main level only: the start page layout, list views, field data access rules by access level and the hash variables #ACCESS_LEVEL_ID# / #USER_GROUP_ID#.
  • Two-factor login is required when any active level asks for it.
  • In your own code: see Access levels in your code below.
  • Effective rights (button next to Add in the user form, shown once there is an additional level): a dialogue with the combined rights as entered in the form – also before saving. Forms with View, Add, Save, Delete, Clone and Print (a form only an additional level grants is marked Additional, a tick only an additional level grants names it), procedures and reports with their levels; search, Only from additional levels, and Copy (tab-separated, e.g. into a spreadsheet). Expired levels are shown crossed out and not counted.
  • Admin rights: with Only the globeadmin grants admin rights (Security check) a level with rights on admin forms can only be added by the globeadmin, nobody changes the additional levels of their own account or the rights of a level they hold, and users with such a level can only be changed by the globeadmin.
  • The Users card of the level lists these users with the badge Additional (an expired one under Archived); a level that is still in use as an additional level cannot be deleted. Changes are written to the log (User changed, field access_extra:<code>).
  • nuBuilder Forte 4.x does not know the table: there the user has only the rights of the main level. The Compatibility check lists these users (G10).

Access levels in your code

nuBuilder Forte's functions and hash variables know only one access level per user – in nuBuilder Next they keep returning the main level. For all levels (main + active additional ones) there are their own:

WhereMain level onlyAll levels
PHP (procedures, Before Save …)nuAccessLevelCode(), nuGetUserAccess()['USER_GROUP_ID']nuNextAccessLevels(), nuNextAccessLevels($userId)
JavaScript (form pages)nuAccessLevelId(), nuAccessLevelCode()nuNextAccessLevels()
SQL with hash variables#ACCESS_LEVEL_ID#, #USER_GROUP_ID#, #ACCESS_LEVEL_CODE##ACCESS_LEVEL_IDS#

nuNextAccessLevels() returns a list, the main level first, then the additional levels whose until date has not passed. Each entry has id, code, description, group, main (true for the main level) and valid_until (YYYY-MM-DD or null). For the globeadmin the list is empty – check nuGlobalAccess(). In JavaScript the list is the one of the moment the page was loaded; decide on the server too (Before Save), a browser check alone can be bypassed.

// JavaScript: show a field for everyone with the level "sales" (main or additional)
if (nuNextAccessLevels().some(l => l.code === 'sales')) nuShow('cus_discount');

// PHP: refuse a save without the level "approver"
if (!in_array('approver', array_column(nuNextAccessLevels(), 'code'), true)) {
    nuDisplayError('Only approvers may change this.');
}

#ACCESS_LEVEL_IDS# holds the ids of the same levels, each in single quotes and separated by commas ('5f2a…','6c1b…'), so write it without quotes of your own, inside IN (…). It works in every SQL that hash variables reach: browse SQL, lookups, select options, report and SQL builder queries, access conditions of objects. For the globeadmin it is '', which matches nothing.

-- browse SQL: only the documents released for one of the user's levels
SELECT * FROM document
WHERE doc_access_id IN (#ACCESS_LEVEL_IDS#) OR '#GLOBAL_ACCESS#' = '1'

-- access condition of an object: editable for the level "hr", else read only
SELECT IF(COUNT(*) > 0, 0, 1) FROM zzzzsys_access
WHERE zzzzsys_access_id IN (#ACCESS_LEVEL_IDS#) AND sal_code = 'hr'

In PHP code use nuNextAccessLevels() rather than the hash variable – inside a PHP string the quotes of the list are escaped.

Other users, or without the helpers (e.g. a report over all users): the main level is sus_zzzzsys_access_id of zzzzsys_user, the additional levels are the rows of zzzzsys_nunext_user_access (user_id, access_id, valid_until) whose valid_until is empty or today or later:

SELECT u.sus_login_name, a.sal_code, 'main' AS kind, NULL AS valid_until
FROM zzzzsys_user u JOIN zzzzsys_access a ON a.zzzzsys_access_id = u.sus_zzzzsys_access_id
UNION ALL
SELECT u.sus_login_name, a.sal_code, 'additional', x.valid_until
FROM zzzzsys_nunext_user_access x
JOIN zzzzsys_user u   ON u.zzzzsys_user_id   = x.user_id
JOIN zzzzsys_access a ON a.zzzzsys_access_id = x.access_id
WHERE x.valid_until IS NULL OR x.valid_until = '' OR x.valid_until >= CURDATE()
ORDER BY 1, 3 DESC

On MySQL the own tables can have another collation than nuBuilder Forte's tables; a join then ends with error 1267 – add COLLATE with the collation of zzzzsys_user to the compared columns (x.user_id COLLATE utf8mb4_general_ci). On SQL Server use CAST(GETDATE() AS date) instead of CURDATE().
