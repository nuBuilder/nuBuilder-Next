Sample data

Two sample applications for trying things out: a sales sample with every object type, and a ticket system with roles and a real workflow.

For: Administrators (globeadmin, admin roles)

Admin tools → Sample data (index.php?p=sample) installs the samples one by one. The list on the left shows every sample with its state at a glance (green dot = installed, yellow = a newer version is available, grey ring = not installed); the selected sample opens on the right with Install or Open sample start page / Refresh and the tabs Overview, Contents, Logins (users, access levels and – right after installing or New passwords – the passwords, masked until Show passwords, each with a copy button) and Maintenance (New passwords, Remove). ?p=sample&s=ticket opens a sample directly. The sales sample is a small application for trying out and testing nuBuilder Next (and nuBuilder Forte (4.x) – the forms are stored in nuBuilder Forte's format and open there too).

  • Forms (codes sample_…, ids without underscore such as sampleorder, because nuBuilder Forte splits hook ids like sampleorder_BS at "_"): sample_home (launch form, start page of the sample access levels), sample_customer (nuBuilder Forte positions, two tabs, validation, Before Delete check), sample_product (grid layout), sample_order + sample_order_item (auto layout, audit columns, lookup, grid subform, calc, Before Edit / Before Save / After Save PHP) and sample_all + sample_all_line – every object type and input type with different formats, access settings (read only, hidden, globeadmin only), events, an iframe and a subform in form layout. Its tabs Run and Subform show the run object types and the subform; Charts three charts, Miscellaneous tooltip icons, the info bar and button spinners. The charts get their data (from the form's JavaScript, from the database via Before Edit, and in the object). Upload has a file object with the target File System: files are uploaded with Uppy into the folder nu_uploads/ next to the web root by nuBuilder Forte's procedure nu_upload_file_template (needs the library pack Uppy).
  • Users and access levels: sample_anna (view only), sample_ben (add and change, German), sample_carla (everything), sample_dario (orders only, must change the password), sample_eva (two-factor login, expires in a year). Passwords are random and shown once; New passwords creates new ones.
  • Excel export: the start page tiles Orders to Excel (procedure sample_xlsx, nuBuilder Next's built-in writer NuXlsx: styled header, number and date formats, a total with SUM, frozen header, filter) and Excel with chart (sample_xlsx_pss, the library pack PhpSpreadsheet: a second sheet with COUNTIF / SUMIF per country, a bar chart and conditional formatting; without the pack it says how to get it). Open the procedures to copy the code.
  • Also: 9 formats, 5 procedures (a window, a hidden one, the dashboard data and the two Excel exports), four dashboards, an e-mail template, 3 code snippets, a picture in Files, and two reports (customers by country from a table, orders by customer from the SQL builder query sample_orders) – started from tiles on the start page and from All objects; every sample access level may run them.
  • Start pages of users: sample_sales, sample_manager and sample_editor have their own tile start pages – see Start pages of users (examples).
  • Lists as a showcase: orders – Status as coloured badges and the filters Customer / Status (design mode, no code), the customer name opens the customer (list JavaScript with nuBrowseLoop and nuForm, the customer's id in a hidden column); products – Active as a green / grey badge, filter Category; customers – filter Country, credit limits above 30,000 in red (nuBrowseStyleBadge with a test rule); all objects – Select and Checkbox as labelled badges. The start form's box What to look at lists them with links.
  • Tables sample_customer, sample_product, sample_order, sample_order_item, sample_all, sample_all_line with data (InnoDB).

Remove deletes every sample record (ids starting with sample_ and the sample form ids), rights of other access levels on sample forms and the sample tables. It is blocked while a non-sample user has a sample access level. A newer nuBuilder Next may bring a newer sample set: the page then shows update available – Refresh removes and installs it again (changes to sample records are lost).

The ticket system

A support desk with four roles, built entirely with design mode – open any of its forms with Design to see how it is made. Everything starts with tkt_: forms tkt_… (ids such as tktticket), tables, access levels, users, procedures, templates and dashboards.

  • Roles: tkt_clara and tkt_oscar are customers (tkt_customer: report problems, follow and answer their own tickets, rate the solution, read public articles), tkt_alex and tkt_mia agents of the 1st level, tkt_sam a specialist (2nd level, gets escalations), tkt_lea the team lead (everything, assigns tickets, categories and SLA, closes old tickets). Each role has its own start page.
  • Tickets (tkt_ticket, grid layout, tabs Ticket · Conversation · Attachments · Handling): automatic number, status and priority lists, the category as a lookup, a description editor, the conversation as a sub-form in form layout (internal notes for the team only), attachments as a grid sub-form with a file field (tab Attachments, also while a new ticket is written), the list with filters for category, priority, status, assigned agent and requester and coloured badges for priority, status and overdue due dates (nuBrowseStyleBadge with rules, form JavaScript of the list), and on Handling the agent, the level, the SLA due date and the buttons Take ticket and Escalate to 2nd level (a procedure that notifies the specialists).
  • Rules in code (Code in design mode): Before Edit refuses another customer's ticket, Before Save sets defaults and the due date from the category's SLA hours (a quarter for urgent tickets) and checks the permission item tkt_assign, After Save records the author of new messages, re-opens a ticket the customer answered, sends the e-mail templates tkt_mail_created / tkt_mail_assigned / tkt_mail_resolved (only with e-mail settings) and a notification to the assigned agent.
  • Who sees what: the list's browse SQL filters by #ACCESS_LEVEL_CODE# (customers their own tickets, agents the 1st level, specialists the 2nd), the conversation's browse SQL leaves out internal notes for customers, field access rules make status and requester read-only and hide the channel for customers, the form's JavaScript hides the tab Handling from them.
  • More: categories with team and SLA hours, a knowledge base with public and internal articles (views counted), two dashboards (their tables Due next and My latest tickets open a ticket in a new tab; Support desk for the team, My tickets for customers – on the start pages and on the launch form tkt_home, one per role through an access condition), the PDF report Tickets by status, 3 permission items, and 60 tickets with about 220 messages over six weeks. The dates are moved to today when the sample is installed.

What to look at in the lists (also as a box on tkt_home for the team): the ticket list has the filters Category, Priority, Status, Assigned to and Requester (design mode, column Filter) and badges for priority, status and an overdue Due date (the list's JavaScript, nuBrowseStyleBadge with rules – the overdue rule tests the row: not resolved or closed and past the due date); the knowledge base shows Visibility as Public / Internal badges and categories Active as a badge (design mode's Show as badge, no code), with the filters Category and Team; the dashboards' tables Due next and My latest tickets open a ticket in a new tab (nu_record_id). Badges and filters are nuBuilder Next features – nuBuilder Forte shows the lists without them.

The ticket system is stored as install/samples/ticket.json. It was built on a test installation and captured with php dev/sample_capture.php <installation> ticket tkt_ – the tool replaces design mode's ids by readable ones – so it can be changed in design mode and captured again.
