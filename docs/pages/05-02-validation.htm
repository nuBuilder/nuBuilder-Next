Validation and business rules

Advanced Required and unique fields, masks, validation rules set in design mode, and rules written in Before Save.

For: Users with rights on: nuform

Built-in checks

Set per object in design mode (nuBuilder Forte's Validation of an object). They are checked on the server for every save, also when the browser's checks are bypassed:

CheckMarker after the labelMessage
Required (no blanks)*"… cannot be blank."

Text mask complete (format with the option "complete")–names the field (and the row of a sub-form)

Fields whose posted value is not saved (field data access; read only and hidden while the Security setting is on – see the rule) are not checked from the post. The markers can be switched off with $nuConfigValidationMarkers.

Validation rules without code

In design mode, the icon bar on the left has Validation rules (with the number of rules; on phones in the bar on top): the list of the form's rules with Add rule and Test all. A rule says what must be true for the record to be saved, for example cus_credit <= 30000. The rules are checked on the server for every save, after the built-in checks and before Before Save, so existing PHP keeps working. The same rules also run in the browser: a field you choose to mark turns red (error) or yellow (warning) while you type, and an error stops the save at once.

  • Builder or expression: build the conditions row by row (field, operator, value / other field / today; all or any), or type an expression – status = 'shipped' AND (ship_date IS NOT EMPTY OR qty <= 0). Operators: = != < > <= >=, CONTAINS, NOT CONTAINS, STARTS WITH, ENDS WITH, IS EMPTY, IS NOT EMPTY, IN (…), NOT IN (…), BETWEEN a AND b, MATCHES 'pattern', BEFORE / AFTER (dates, also TODAY). Text goes in quotes; a name without quotes is another field. Text is compared without regard to case; numbers as numbers.
  • Hash variables: #NAME# as a value – hash cookies and form properties (nuSetProperty()), the user and access level variables (#USER_ID#, #ACCESS_LEVEL_CODE# …) and the record's, with the same values as in Before Save. In the builder the value field takes any text and offers the hash variables while you type (# …); the messages fill them in too. A hash variable can also stand on the left, as the thing that is checked: #MY_COOKIE# = 123, or under Only when … #ACCESS_LEVEL_CODE# = 'sales' – in the builder type #NAME# into the field box. In the browser a property set by the page's JavaScript wins, so the live check matches the save. Test rule uses the hash of the tested record.
  • Only when …: a second condition – the rule applies only while it holds (e.g. only when the status is "shipped").
  • Error or warning: an error refuses the save; a warning asks "Save anyway?" and saves after OK.
  • Sub-forms: a rule can check every row of a sub-form (the message names the row), and COUNT(sub-form) counts the rows of the record, e.g. COUNT(sample_items) >= 1.
  • Only for: access levels and / or a permission item – the rule then applies only to users who have one of the levels and the item. The globeadmin has no access level: rules limited to levels do not apply to him.
  • Message: #field# inserts a field's value; the text is translated through the translations of the application like other texts of the form.
  • Test rule checks a rule against a saved record (the open one, or the newest) before you save it; Test all checks every rule.

The rules are stored with the form (sfo_json of the table zzzzsys_form, shared with nuBuilder Forte, which ignores them) – they go through drafts, the form history and the Form cloner with the form. nuBuilder Forte does not check them: a form opened there saves without these rules.

Your own rules

  • In the browser: nuBeforeSave() returning false – quick feedback, but not a protection.
  • On the server: in Before Save read the posted values ('#field#' or nuGetNuDataValue()) and stop with nuDisplayError('message', 'field') – the field is highlighted. For rules that apply to every form, use the global hook nu_before_save.
  • Who may change what belongs into rights, not code: access levels, field data access, permission items (nuUserHasPermission()).

Required and unique fields of nuBuilder Next's pages

The record pages of nuBuilder Next itself check these fields on the server; the label shows a red * for required and a key for unique (the tooltip of the key explains it). Unique values are compared as stored; the user code ignores spaces at the ends and upper / lower case. Values that must be unique only together with others (e-mail templates, translations) carry no key.
