How a save works

Advanced The steps of a save on the server, from the posted fields to After Save.

For: Users with rights on: nuform

The browser posts the record's values, the list of fields the user edited, the form properties and the sub-form rows to the form API (save). NuRecord::save() then works through these steps:

Which fields are written

  • Only objects that save to a column (input, select, lookup, calc, textarea …) and whose id is a column of the table; buttons and file-system uploads never.
  • Existing record: only fields the user edited – so changes others made to other fields are kept.
  • New record: untouched empty fields are not written, so the column default or NULL applies (as in nuBuilder). nuAutoNumber inputs get the next number.
  • Fields the user may not change (read only, hidden, or limited by field data access) are dropped from the post – never taken from the browser. A clone takes such values from the source record in the database.
  • Values are converted to the column's type (dates, numbers); text with a mask is stored with or without the mask characters, as the format says.

Columns set by the server

  • Audit columns created_at, created_by, updated_at, updated_by – on forms created with the audit option.
  • nuBuilder's record log <table>_nulog – JSON with who added and last edited the record.
  • "Updated on" of notes and code snippets.
  • New primary keys: a nuBuilder id (nu_id()), or the database's auto increment.

What hooks can do during a save

  • Before Save: stop with nuDisplayError(); read the posted values from #nuFORMdata# / nuGetNuDataValue() and change what is saved with nuSetNuDataValue(); add JavaScript with nuAddJavascript().
  • After Save: the record is written; #RECORD_ID# is its id; nuReturnNewRecord() makes the form open another record.

Delete works the same way: visibility check, Before Delete, one transaction for the record and its sub-form rows with audit trail, After Delete.
