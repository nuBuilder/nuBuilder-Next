Getting started

nuBuilder Next is a modern front end for nuBuilder applications. It works on the same database as nuBuilder, so your forms, users and data are the same in both.

Signing in

Sign in with your nuBuilder user name and password. Depending on your access level you may be asked for a second factor (see Security).

If your session has ended (no activity for a while), the next click shows the sign-in page; after signing in you are taken to the page you had clicked – also when the sign-in page was left open for a long time.

  • Your account can expire or be locked by an administrator – then the login is refused.
  • If your administrator requires a new password, you are asked to set one right after signing in.
  • After a period without activity you are signed out automatically and must sign in again.
  • If your company uses the shared login, you are signed in automatically when you are already signed in to nuBuilder.
  • If the sign-in page shows Try the demo, one click signs you in to a demo: you can look at everything, but nothing you change is saved (a badge Demo – read only in the menu bar shows it).

Navigation, language and theme

The menu bar shows only the areas you have rights for. On phones the menu is behind the ☰ button. The logo (nuBuilder Next) always opens the start page; Start is listed only next to other areas.

  • Language (Deutsch (DE), Deutsch (CH), English (UK), English (Australia), English (US), Français, Italiano, Español, Português, Русский, 简体中文, Nederlands, Polski, العربية): your choice is saved with your user. Arabic is shown right to left. The three English versions differ in spelling (colour / color, customise / customize), the two German versions too (Deutsch (CH): ss instead of ß and «quotes»); the page language (<html lang>: de-DE, de-CH, en-GB, en-AU, en-US) follows the choice, e.g. for numbers in dashboards. nuBuilder's formats (Formats) stay as they are. nuBuilder itself only knows "English" and "German": the user's language stays English / German and the version is kept in the user's JSON (sus_json, NUNEXT_LANG_VARIANT). Without a choice: the installation's default (setup wizard), else the browser's (en-US, en-CA and plain "en" → US; en-AU, en-NZ → Australia; other English → UK; de-CH → Deutsch (CH), other German → Deutsch (DE)).
  • Back (, first button): goes one step up the breadcrumb – from a record to its list, from a form's list to where it was opened (Forms list, start page or another form). All other pages have it too: lists (users, forms, procedures …) go back to the start page or to the page above them in the breadcrumb (e.g. Settings → Admin tools, Procedures → Forms), single records go back to their list.
  • Theme (sun / moon icon): light, dark or automatic (follows your device).
  • User menu (your name, top right): Security, change password, this documentation, sign out.
  • Globeadmin: the start page shows all areas as tiles in groups and can be arranged with Customize (see Start page of the globeadmin); + on a tile opens a new record, ▾ a menu with the pages behind it. The user menu also has Admin tools, Database and File Manager.

Working with forms

Lists (browse)

  • Search: type into the search field and press Enter. Several words must all match. Dates are found as they are displayed. On a computer the cursor is already in the search field of nuBuilder Next's own lists (Users, Access levels, Forms …).
  • Same look everywhere (0.8.337): browse lists of your own forms look like nuBuilder Next's lists – the search field (350 px, search button on the right) sits inside the list card, the table has the same header and row height. Form code keeps working: #nuSearchField, #nuSearchButton, #nuBrowseTable, nuHideSearchField(), nuDisableSearchField().
  • Users list: columns Position (after Department / Team) and Code (after Login name), both sortable; filter Position (all, one position or "(no position)").
  • The users list has no row buttons: open the user to clone, archive or delete them. The access levels list has only a Clone button in the rows (hidden below 768 px); delete an access level on its page.
  • Forms list: filter Group (all, one group or "(no group)"); the column Status shows nuBuilder's form status (Active, Draft, Archived – set in the form builder). By default archived forms are hidden (filter Status: All except archived); choose All or one status to see them.
  • Filters of nuBuilder Next's own lists (group, status, type, dates …) are hidden behind the filter button (funnel) right of the search field; they stay open while a filter is set, and the × button resets search and filters. In the users list they are shown at once on screens at least 800 px wide.
  • Sort: click a column title; click again to reverse the order.
  • Filter: some columns have a filter list above them.
  • Open a record: click the row. Add creates a record (if you have the right). The buttons of a list or record (Add, Print, Save, Clone, Delete …) sit right after its title, so they stay close on wide screens.
  • Pages: below the list, Back / Next change the page; click Page x / y, type a page number and press Enter to jump there (Esc cancels).
  • Export / print (if you have the print right): a print view of the current list in a new tab, with Export CSV there (opens in Excel) – search, sort and filters apply. In the print view of the system lists the × after a column title hides that column (for printing and Copy); Undo shows the last one again, Reset view all of them – the browser remembers the hidden columns per list (0.8.397).

Editing a record

  • Save, Clone and Delete look the same (light buttons with icon and text, as in nuBuilder). As soon as you change something, Save turns red – red text on a light red background: there are unsaved changes. After saving it looks like the others again. On phones the three show only their icon.
  • After saving, deleting or cloning, a short message appears at the bottom right.
  • On phones, Save, Clone and Delete show only their icon (Save as a floppy disk); the text appears as tooltip.
  • Required fields are marked with *, fields whose value must be unique with a blue ◆ (see Markers after labels below). If something is missing or invalid, a message tells you which field, and the field is highlighted.
  • Fields with a mask (e.g. IBAN, phone) only accept the expected characters; the separators are added for you.
  • If you leave a record with unsaved changes, the browser asks first.
  • Ctrl+Shift+S (Mac ⌃⇧S) saves – in forms and on nuBuilder Next's own edit pages (user, access level, procedure, prompt, e-mail template …), also while you are typing in a field; the tooltip of the Save button shows it.
  • Fields with a suggestion list (an arrow on the right, e.g. Position, Department, Team) offer values to choose: type to filter, or click the arrow to see all values – also when the field already has one (the old value comes back if you pick nothing).
  • Searchable selects open their list above everything else; in multiple selects the chosen values are shown as tags, the field grows when they need more lines.
  • Some fields have a small help icon ? on their right: point at it (or tap it) to read a hint.

Two people editing the same record

  • Also open (since 0.8.401): a yellow note above the form shows who else has the same record open – “Anna also has this record open (since 10:40)”, or “… is editing this record – unsaved changes”. It is checked every 30 seconds and never blocks anybody.
  • Saving after someone else: only the fields you changed are saved, so changes of others to other fields are kept. If someone saved the same field after you opened the record, Save stops and shows Changed meanwhile: who changed it and when, and for each such field the value when you opened the record, yours and the one saved now. Pick Mine or Theirs per field and Save with these choices – or Reload to see the record as it is now (your changes are lost). The same value on both sides is no conflict.
  • Sub-forms: the same for each row; a row someone else deleted is named (your changes to it are not saved), a row you delete that someone else changed asks Delete anyway or Keep the row.
  • Delete: if the record was changed after you opened it, you are asked before it is deleted.
  • Changes made in nuBuilder itself, by procedures or directly in the database are found too – the record is compared with the database. Who and when come from the audit trail (when on), otherwise from nuBuilder's record log of the table, otherwise “someone else”.
  • Switching off: $nuConfigEditConflictCheck = false; (the check) and $nuConfigEditPresence = false; (the note) in nuconfig.php; per form in its Before Edit PHP: nuNextConflictCheck(false); / nuNextPresence(false);. The note is always off in demo mode. Saves made in nuBuilder itself are not checked (nuBuilder has no such check), but nuBuilder Next notices them.

Editing code

Fields that hold code – PHP, SQL, JavaScript, HTML or CSS – are shown in a typewriter font. Double-click such a field to open the code editor: syntax colours, line numbers and a full-screen button. Ctrl+Enter (or Ctrl+S, or OK) takes the code over into the field; Esc or Cancel closes the editor and asks first if you changed something. Save the record afterwards as usual.

The toolbar of every code editor (double-click editor, form builder, procedures) offers Undo / Redo, Search (Ctrl+F, then Enter / Shift+Enter for next / previous), Replace (Ctrl+H), Toggle comment on the selected lines (Ctrl+/), Show spaces and tabs, Full screen (F11, Esc ends it) and Format (Shift+Alt+F). Format tidies PHP, SQL (MySQL or T-SQL), JavaScript, HTML and CSS with the same rules as nuBuilder; hash variables such as #RECORD_ID# are kept unchanged. Code with a syntax error is left as it is and a message names the problem. Undo reverts a format in one step.

Keyboard shortcuts and the options menu

The ⋮ button at the end of the toolbar opens the options menu: it lists everything you can do on this form, each with its keyboard shortcut. All shortcuts are Ctrl+Shift+key:

  • S save (in a list: search; also on nuBuilder Next's own edit pages), C clone, Y delete, A in a list: add a record, P print the list, R refresh, ? help, L log out.
  • ← → previous / next tab (in a list: page), Home / End first / last page, 1–9 in a list: switch a column in or out of the search.
  • Only what you are allowed to do is offered – a shortcut for something you have no right for does nothing.
  • Mac: use Control+Shift (shown as ⌃⇧). Cmd+Shift also works, except for combinations macOS or the browser keeps for itself (⌘⇧Q logs you out of macOS!).

Clone and delete

  • Clone copies the record into a new, unsaved record. A yellow badge Clone – not saved yet and a dashed yellow frame show that you are working on the copy. Nothing is stored until you click Save.
  • Delete asks for confirmation and then returns to the list.

Sub-forms, lookups, files

  • Sub-forms (rows inside a record): typing in the empty last row adds a new row; switch Delete on to remove a row when saving.
  • Lookups: type a code or click the search button to pick a record from a list. With a description width of 0 (form builder) only the code is shown.
  • Markers after labels: a red * means the field must not be empty, a blue means its value must be unique (both can appear). Hover a marker for its meaning; the legend below the form lists the markers in use. They come from the object's Validation setting (No blanks / No duplicates / No duplicates and blanks), also in subform column titles, and are not shown when the form can only be viewed. $nuConfigValidationMarkers = false in nuconfig.php switches them off.
  • Files: choose a file to upload; download or remove it with the buttons next to the field.
  • Breadcrumbs (top left) show where you came from; click an entry to go back.

Security: password and two-step login

Open Security in the user menu.

Changing your password

Enter your current password and the new one twice. The minimum length is set by your administrator. Forgot it? Use Forgot password on the login page – you receive a link by e-mail that is valid for 60 minutes and can be used once.

Two-step login (2FA)

  • Authenticator app (Microsoft / Google Authenticator, …): scan the QR code and confirm with a code. From then on you enter the 6-digit code of the app after your password.
  • Code by e-mail: if no app is set up, a 6-digit code is sent to your e-mail address.
  • Remember this device: no code is asked on this browser for a number of days.
  • Lost your phone? Ask your administrator to reset your two-step login.

Notes

Menu Notes: notes with formatted text (bold, lists, tables, links), grouped in categories. The list has a category filter below the column title (All, ∅ = without category, or one category); it can be switched off in the form builder (browse column option Filter). Updated on is set automatically on every save. Categories are managed with the Categories button above the notes list (form nunotescategroy); a missing category can also be added right in a note: open the category lookup and click Add – after saving it is chosen in the note.

Users

Menu Users. The list can be searched and filtered by access level (searchable: type part of the code or description) and status – the filter button (funnel) right of the search field shows the two filters. The status Active (not expired) is the default, so archived and expired users only show with All or Expired. Each row has Clone and Delete / Archive; the Delete button in the user form opens the same dialog (after archiving, the form stays open):

  • Archive sets Valid until to yesterday: the user can no longer sign in (an open session ends on the next click), all data stays. To use the account again, change or clear Valid until. Needs the Save right; not offered for users that are already expired.
  • Delete removes the user and his permission items – it cannot be undone. Needs the Delete right. Your own account has no button.

Under the password, the user form shows when it was last changed and how – by the user, in the user form or via the e-mail link (stored like nuBuilder in sus_json: PASSWORD_CHANGED_TIME, PASSWORD_CHANGED_SOURCE = user / admin / reset; changes made before this version are not known). Cloning a user does not copy the login token, 2FA and password data.

In the user form, the magic-wand button next to the password opens a password generator: length (slider or number), upper and lower case, numbers, symbols, avoiding look-alike characters, a strength bar – Use password puts it into both password fields and copies it to the clipboard. The password is created in the browser; the settings are remembered per browser.

Welcome e-mail

Send welcome e-mail (shown when e-mail is set up) sends the user, after saving, the login name and a personal link to set the password – valid $nuConfigWelcomeLinkHours hours (default 72), usable once; afterwards "Forgot password?" works as usual. No password is sent by e-mail. For a new user the password field can stay empty: the account gets an unknown random password until the link is used. Like nuBuilder, the mail comes from the first of:

  1. your own procedure nu_send_welcome_email (Procedures) – it gets the placeholders below and sends the mail itself, e.g. with nuSendEmail();
  2. the e-mail template with code nu_send_welcome_email (E-mail templates; the user's language first, then the one without language) – Clone nuBuilder's template nu_send_welcome_email_template to get it;
  3. the built-in text in the user's language.

Placeholders: every #sus_…# field (e.g. #sus_name#, #sus_login_name#, #sus_email#), #SET_PASSWORD_URL#, #SET_PASSWORD_HOURS#, #LOGIN_URL#, #NUNEXT_URL#, #NUBUILDER_URL#, #PASSWORD_MIN_LENGTH# and, for old nuBuilder templates, #check_password# (the password typed in the form). Sent and failed welcome e-mails are written to the Log.

  • Person: Full name comes first – for a new user it fills First name / Last name below it (type * into one of them to split it again on an existing user). Code sits after Position, Department and Team, with Additional 1 and 2.
  • Login name must be unique; the password needs the minimum length.
  • Access level decides which forms and procedures the user may use. Without an access level the login is refused. The field is searchable (type part of the code or description); the button next to it opens the chosen access level in a new tab.
  • Position, Department, Team suggest the values of the other active users (alphabetically, each once).
  • Valid until: the login works through that day; empty = unlimited.
  • Change password at next login forces a new password.
  • Language: one of the eleven interface languages (stored with nuBuilder's names: German, English, French, Italian, Spanish, Portuguese, Russian, Chinese, Dutch, Polish, Arabic); empty = browser language. English and German also come as versions – English (UK / Australia / US), Deutsch (DE / CH); nuBuilder keeps English / German, the version is stored in sus_json (NUNEXT_LANG_VARIANT). Plain English / Deutsch = the installation's default version.
  • Reset 2FA removes the user's authenticator app and remembered devices (e.g. lost phone).
  • Demo user: a badge in the title marks a user named in $nuConfigDemoUser – it signs in read only and sees everything the globeadmin sees (see Demo mode).
  • Permission items (bottom of the user form): tick the items the user has. The search field and the group selection filter the list; All and None apply only to the items shown – e.g. pick a group, then All ticks just that group. Saved with the user; cloning a user copies them.

List views

nuBuilder Next's own lists – Users, Access levels, Permission items, Forms, Procedures, Reports, Files (tiles or table), Items, Translations, Prompt generator, Log and the E-mail log (0.8.334) – can be shown in different views – the button in the title bar shows the current view and switches between them.

  • A view sets the columns and their order, the width (auto, narrow, wide) and alignment of each column, the sort, the rows per page, which filters are offered with their default values, whether the filters start open – and, separately, what a phone shows: below 768 px every row is a card with a title, a badge on the right and up to four lines (label: value).
  • Standard views: Default (the list as before), Compact and All columns – fixed; New view… starts from the current view. The users list also offers last login, authenticator app, admin role, online now, password changed, status, valid until, language and more; filters for department, team, language, last login, valid until, authenticator app, online and admin role.
  • My views: everybody who may open the list can save personal views and choose one as my default (Set as my default; Use the list’s default again removes it).
  • Shared views (the globeadmin and admin roles with the right List views): visible for everyone or only for the ticked access levels (e.g. an HR view for the access level hr on top of the common views). Set as default for everyone makes a view the list's default – at first it is Default. Share a copy with everyone turns a personal view (also another user's, listed under Personal views of other users) into a shared one. Export shared views / Import views… move them as JSON to another installation (access levels by code; views with the same name are replaced).
  • More columns and filters than before, e.g. forms: table filter; procedures: category, template, run by everyone; items: category, language, form, sort order; log and e-mail log: a period (last 7 / 30 / 90 days) besides the dates; e-mail log: tag and sender. Files also has the display Tiles (the thumbnails as before, its default) or Table. Debug results keep their own message list.
  • Which view opens: the one in the address (&view=…; translations: &lv=…, because view is the tab Missing there), else the own default, else the list's default, else Default. Links of the list (sort, pages, Print) keep the view; Print and Export CSV use its columns in its order.
  • Stored in zzzzsys_nunext_list_view; the list default in zzzzsys_nunext_setting (listview_defaults), personal defaults in the user's sus_json (NUNEXT_LIST_VIEWS). Columns and filters are defined in core/nulistdefs.php – never free SQL. Saving, deleting, defaults and imports of shared views are logged.

Permission items

Start page tile Permission items, or Manage at the permission items of the user form (rights of nuBuilder's form nupermissionitem). A permission item is a named switch that your own code checks – for things an access level cannot express, e.g. "may approve invoices" for some users of the same access level.

  • Ident: the name used in code, unique (letters, digits and _ . : -). Group sorts the items in lists and in the user form.
  • Users: add or remove users directly on the item, or tick the item in the user form – both edit the same assignment (zzzzsys_user_permission, as nuBuilder).
  • Used in code lists form code, events and procedures that name the ident in quotes.
  • Deleting an item removes it from all users. The globeadmin has every item.

Checking an item: PHP nuUserHasPermission('ident') or nuGetUserPermissions(), JavaScript nuUserHasPermission('ident') or nuUserPermissions(), SQL / code #USER_PERMISSIONS#. Check on the server too (Before Save) – a browser check alone can be bypassed.

Access levels

Menu Access levels. An access level lists the forms a user may open and, per form, the buttons: Save, Add/New, Delete, Clone, Print. The row itself means "may view". Procedures need their own entry.

  • Use two-factor authentication: users of this level must confirm their login with a second factor – an authenticator app or a code by e-mail (hover or focus the icon for this hint). It needs $nuConfig2FAUser = true; the form shows whether it is on, and while it is off the globeadmin can switch it on there (Switch on, or a link to Settings when the settings table is used).
  • Reports: the reports users of this level may run (nuBuilder's zzzzsys_access_report); the form shows how many are ticked. They are set on the report itself (see Reports).
  • Adding forms: pick one form from the list, or click Several…: search (code, description, table), filter by form group, type and own / nuBuilder system forms, tick the forms (or Select all shown) and choose the rights the new rows get – e.g. everything but Delete. Forms already in the list are hidden. Save afterwards.
  • Removing a form: crosses the row out – it is removed when you save the access level. Until then the same button () brings it back. The form builder's lists (tabs, list columns, events, columns of a new table, HTML attributes) work the same way.
  • An access level cannot be deleted while users still have it. Deleting it also removes its form, procedure and report rights; cloning copies them.

Self-test (developer mode)

Admin tools → Self-test (since 0.8.361, index.php?p=selftest) is shown only to the globeadmin while $nuConfigDevMode = true. Run checks the installation, by group:

  • System: PHP version and extensions (a warning while PHP lacks the PHP2Shell fix – see Security check), writable folders (temp, backups), nuBuilder Next's tables and columns, the database steps of all updates, the structure of nuBuilder's tables, complete language files, red points of the Security check, e-mail set up.
  • Data: sample application installed, a form's browse list, the queries of all system lists, a report as PDF.
  • Forms: save a new record, required / unique fields refused, change a record, sub-form rows (add, change, delete), hash variables, audit trail and restore, delete with sub-form rows.
  • Rights: access levels give exactly the stored rights; the admin role rights are complete.
  • Features: a notification is published, received and read; the housekeeping ran in the last two days.

Results: OK, warning, failed or skipped, with details and duration. The form checks write into the sample application (customers, orders with items) and delete their records and audit rows again; a notification to the globeadmin is created and deleted. Without the sample application they are skipped. Use it on development and test installations – not with live data. Each run is in the log.

Releases are also checked by browser tests outside the application (dev/tests/e2e.js, only in the development package): login, forms, sub-forms, nuBuilder's form events (Before Save, Before Delete, After Save, Before Edit, a lookup's After Browse), lookups, JavaScript events, procedures, permission items, rights, admin roles, demo mode, one-time login links, user import, audit trail, notifications, list views, start page, branding, dashboards, the login limit, CSV import, update check, the self-test, CSRF – and since 0.8.364 by cross-tests against nuBuilder itself (dev/tests/compat.js): the same database opened in nuBuilder 4.9 and in nuBuilder Next, every application form compared (browse list, field values, a save without a change), the same typed input must give the same row, sub-form rows and reports across both, and a save without a change in nuBuilder Next's editors (users, access levels, procedures, SQL builder, report designer, permission items, e-mail templates, form builder) must leave nuBuilder's rows as they were. It can be pointed at a copy of a real nuBuilder database.

Notifications

The bell in the top bar (since 0.8.357, for everybody who is signed in) shows a red badge with the number of unread notifications. It checks every 60 seconds (not while the browser tab is in the background, at once when it comes back; the check does not keep an idle session alive). A new notification rings the bell and shows a short message at the top right.

  • Panel (click the bell): the latest ten, unread ones highlighted, level icon (info, success, warning, important), time; marks one as read or unread, hides it, Open follows its link; Mark all as read; Show all opens My notifications (filters all, unread, hidden – hidden ones can be shown again).
  • Must confirm: such a notification appears as a dialog on the next page until Got it is clicked; the time is recorded.
  • Demo visitors see the bell; read / hidden / confirmed last for their session only.

Sending notifications

Notifications → Manage (start page tile, or the bell panel): who may send – the globeadmin, users with the admin role right Notifications = change, users with the permission item NUNEXT_NOTIFY (anyone) or NUNEXT_NOTIFY_OWN (only their own department and / or team – the other recipient fields are not offered). Both items are created by the update (group nuBuilder Next); give them to users under Permission items or in the user form. Notifications = view and NUNEXT_NOTIFY also show all notifications and their read receipts; NUNEXT_NOTIFY_OWN users see and change their own ones.

  • Content: title, text, level, optional link (index.php?p=… or https://…). The text is plain text (line breaks kept, web addresses become links) – or, with the switch Formatted text (since 0.8.400), formatted in an editor: bold, italic, underline, strikethrough, lists, links, quotes. When saving, everything else is removed (only these tags, no colours, fonts, images, styles or scripts; links only to https://, mailto: or pages of nuBuilder Next, opened in a new tab); at most 4000 characters including the tags. The bell, the confirm dialog and the e-mail show the formatting. Switching back to plain text removes it (after a question). The editor is TinyMCE – a library pack; without it the formatted text is edited as HTML.
  • Recipients, combined (each user gets it once): Everybody, single users (also the globeadmin), departments, teams, positions (the fields of the user records; a new value can be typed) and access levels. The form shows how many users it reaches now and their names.
  • Who gets it: Whoever matches at the time – checked whenever the bell is read, someone joining the team later sees it too; or Fixed list when published – the users matching at publishing are stored (exact read receipts). Must confirm always uses the fixed list.
  • Publish at (later = scheduled), Expires at (then gone from the bell), Pinned (on top), Must confirm, Also by e-mail (once, when it appears, to the recipients with an e-mail address – needs the e-mail settings; scheduled ones are mailed by the housekeeping).
  • Save as draft (invisible) or Publish. In the list: status (draft, scheduled, published, expired, withdrawn), recipients, read count; ⋯ → edit, read receipts (who read / confirmed / hid it and when), copy, publish / withdraw, delete. The edit page has Delete and the same ⋯ menu (read receipts, copy, withdraw) next to Save; on phones the list keeps the ⋯ column visible at the right. Every step is in the log.
  • Settings: Delete notifications after 30 days … 2 years or never (default 180 days, counted from the expiry or the publishing) – the housekeeping deletes them with their read receipts.
  • From code: nuNextNotify(['title' => 'New order', 'body' => '…', 'level' => 'info', 'link' => 'index.php?p=form&f=…&r=…', 'teams' => ['Sales'], 'users' => ['jdoe'], 'must_confirm' => false, 'email' => false]) ('format' => 'html': the body is formatted text, cleaned like in the form) in a procedure or form event (e.g. After Save) publishes at once and returns the id ('' when not valid; no rights check – it is server code). Keys: all, users (ids or login names), departments, teams, positions, access_levels, mode, publish_at, expires_at, pinned.
  • REST API (scope notifications:write): POST /v1/notifications with the same fields and "audience": {…}, GET /v1/notifications/{id} (state, recipients, read, confirmed), DELETE /v1/notifications/{id}.

E-mail

Settings and test mail

Menu E-mail → Settings: SMTP server, port, user, password, sender. These are the same settings nuBuilder uses. The password is never shown again – leave the field empty to keep it.

  • Port 465 uses SSL/TLS, 587 STARTTLS; on other ports Use SSL selects SSL/TLS (the same hint is behind the next to Use SSL).
  • Authentication method (0.8.342): Automatic lets PHPMailer take the first method the server offers, in the order CRAM-MD5, LOGIN, PLAIN, XOAUTH2. Some servers offer a method and then refuse it (often CRAM-MD5) – choose LOGIN or PLAIN for them (PHPMailer's AuthType). Stored in nuBuilder Next's own settings (nuBuilder's zzzzsys_setup has no field for it) and used for everything nuBuilder Next sends, also with the SMTP settings of nuconfig.php; nuBuilder itself always uses automatic.
  • Test mail sends a message and shows the conversation with the server (passwords hidden) – useful when mails don't arrive. With authentication it also shows the methods the server offers and the one used; when sending fails with Automatic it suggests another method, and it warns when the chosen method is not offered. The To address is remembered in your browser for the next test.
  • nuBuilder writes 1 into every field when its settings are reset; nuBuilder Next treats 1 as "not set".
  • Copy settings puts the settings shown (server, port, user, sender, authentication method, switches) as JSON on the clipboard – without the password. Paste settings fills the fields from such a JSON, e.g. from another installation (nuBuilder's set_smtp_… names work too); a password in it is ignored and the stored one stays. Pasted values are only saved with Save. Where the browser may not read the clipboard (http without TLS, permission refused) a dialog opens to paste the text.

Audit trail

Menu Log → Audit trail (globeadmin, admin role right Audit trail, or rights on nunextaudit): every change nuBuilder Next makes to the tables of forms, in zzzzsys_nunext_audit, one row per changed column:

  • Who and when: user id, login, IP address, date/time. What: action (added, changed, deleted, copied = saved clone, restored), source (form, sub-form, CSV import, restore, from the log = copied by the update), table, record id, form, for sub-form rows the parent table and record, column, old and new value (NULL stays NULL, shown as ∅). One save (main record and its sub-form rows) shares a change_id; a CSV import is one change.
  • Captured: saving and deleting in forms (sub-form rows included – a deleted record takes its sub-form rows along), saving a clone, the CSV import (insert / update / upsert, not the dry run). Only columns whose value really changed (numbers and dates compared as values). Not recorded: nuBuilder's own zzzzsys_ tables (the log has users, access levels, forms …), the columns <table>_nulog, created_at/created_by/updated_at/updated_by (the audit row has who and when), and changes made outside nuBuilder Next – nuBuilder itself, phpMyAdmin, PHP code or procedures that write with their own SQL. No database triggers are used.
  • Secrets and size: columns that look like secrets (password, token, secret, …) or hold password hashes are stored as •••; values longer than 4000 characters are cut and marked with a SHA-1 of the full value. Neither can be restored.
  • Settings (button Settings, globeadmin or Audit trail = change, confirmed with the password when the last confirmation is older than the re-login time): Record changes on/off (without a saved setting it follows $nuConfigLogRecordChanges), Keep (for ever or 30 days … 10 years – the housekeeping deletes older rows), Not recorded: tables (customer) or columns (invoice.notes), comma separated.
  • List: list views, filters (action, table, form, user, record, column, date), search in table, record, column and values, print and CSV. A row opens the history of its record.
  • Delete… (since 0.8.351; globeadmin or Audit trail = change, not in demo mode): a dialog that combines Only the rows of the current search and filters (exactly the listed rows, over all pages – a filter on a column can take part of a save) with an Age: any, older than 1 / 2 / 3 / 6 / 12 months, or before a date (cut by time, so a save goes as a whole). Neither = the whole audit trail, which needs DELETE typed. The dialog shows how many rows and saves will go; Download as CSV first saves exactly these rows with all columns. Deleting asks for the password when the last confirmation is older than the re-login time, works in batches of 5000 rows and is written to the log (Audit trail entries deleted: number, filter, date). For regular clean-up use Keep in the settings.
  • History of a record: the record's ⋮ menu → History of this record (shown while the audit trail is on), or index.php?p=audithistory&f=<form id>&r=<record id>. Rights: view on the form (and the record must be visible to the user while it exists). Newest first, one block per save, sub-form rows included.
  • Restore (, needs Save on the form, not in demo mode): a changed value goes back to its old value only while the column still holds the value shown as new (otherwise restore the later change first); a deleted row (main record or sub-form row) is inserted again with its recorded values only while no row with that key exists. Restoring is recorded itself (restored) and in the log. Entries copied from the log cannot be restored.

Drafts and publishing

Since 0.8.386 a form can be changed in a draft: users keep working with the live form until the draft is published in one step. The pill at the top of the builder shows Live or Draft.

  • Start draft (builder, top): copies the complete form definition – form settings, tabs, objects, events, PHP hooks (also of lookups), list columns and SQL builder selects. One open draft per form; the forms list shows it as Draft · author (filter With draft).
  • Working in the draft: everything works as in the live builder; Save writes into the draft only. Undo in the draft bar goes back step by step (last 20 saves). New table columns are created at once (the table is shared with the live form) and listed when publishing.
  • Preview: opens the form as the draft – only for you, with a yellow banner (Back to live ends it). Forms the draft opens that have a draft of yours too are shown as drafts as well. By default the preview is read-only; when saving is allowed (draft setting, default from the security setting below) Save and Delete change the live data after a confirmation.
  • Compare (panel Compare with live): what changed – form settings, tabs, objects (added, removed, changed, moved), events, PHP and JavaScript line by line, list columns, SQL builder.
  • Publish…: a note, the summary of the changes and the checks (errors such as a missing table column stop it; warnings need a tick). The live form is saved in the history first (before publish), then replaced in one transaction and stored as published vN – note. Versions are never removed by the history's limit.
  • Conflict: when the live form was changed after the draft was started, Publish shows it; publishing anyway needs the form code typed in and overwrites those live changes.
  • Discard deletes the draft; the live form is not touched. Two windows on the same draft: the second save is refused and the builder reloads.
  • Rights: anybody who may change the form may start and edit a draft; publishing needs the globeadmin or the admin right Publish forms (drafts) (see Admin roles).
  • Only through drafts (security setting): the builder then edits a draft for every published form, and new forms start as drafts (status Draft: only form designers can open them until they are published). The globeadmin may still change a form live after a confirmation. While a draft is open, changing the form live asks first, and deleting the form is refused.

Drafts are stored in zzzzsys_nunext_form_draft (database step 0015); nuBuilder itself only ever sees the published form.

  2. The builder of a page form shows the folder custom/pages/<code>/ and whether index.php is there. Create from template copies custom/pages/_template/ there (when the folder is writable; otherwise copy it by FTP).
  3. Give access levels the right on the page form, as for any form (view = may open it; the other rights can be read by the page with $nu->rights() and used as the app's roles).
  4. Write the app in index.php (more files, assets/ for css / js / images). Copy AI prompt puts the guide, this page and the list of your tables into the clipboard – paste it into any AI together with a description of the app.

Settings of a page

  • Open in: New tab (default – menus, tiles and run buttons open it in a new browser tab), Inside nuBuilder Next (the page in an iframe below the top bar and breadcrumbs; Iframe height auto = the page reports its height, or a fixed height like 800px) or Whole window.
  • Settings (JSON): the app's configuration (lists, colours, limits), read with $nu->setting('key') (dot paths). Invalid JSON is not saved. No secrets here – the settings are copied by the cloners. Below the field the builder lists the keys the page reads (every $nu->setting('key', default) in its files) with the default in the code, the file and whether the key is set, and it names keys that are set but never read (0.8.391). When the page folder has a settings.example.json, Insert example fills the field with it (the template has one).
  • Secrets (API keys, passwords): secrets.php in the page folder (guard line first, return ['key' => '…'];), read with $nu->secret('key'). Never in a package, a cloner copy or the builder (it only says whether the file exists).
  • Content-Security-Policy (optional): added to frame-ancestors 'self', which every page gets.
  • Notes: for the developers.

How a page runs

  • index.php?p=form&f=<code> – the normal form address: an iframe page (mode Inside nuBuilder Next) or a redirect to the page's own address. Every way to open a form works: menus, tiles, run buttons, iframe run objects, nuForm(), bookmarks.
  • index.php?p=page&f=<code> – the page's own output (HTML, JSON for its fetch calls, downloads). r (record id), ps (nuSetProperty values) and the opening form and record (pf / pr, accepted only with the view right on that form) are passed on.
  • index.php?p=pageasset&f=<code>&file=assets/… – files of assets/ only (css, js, images, fonts, json, txt, pdf), with the same login and right.
  • Every POST needs the CSRF token ($nu->csrfField(), NuPage.fetch()). A fetch of the page gets JSON answers: 401 login, 400 csrf, 403 forbidden, 404 not_found, 500 server – error details only for the globeadmin.
  • While the globeadmin views as another user, $nu->user() is that user, $nu->realUser() the globeadmin, $nu->readOnly() is true and POSTs are refused. In demo mode readOnly() is true too.

The complete list of $nu methods and of the JavaScript helpers (NuPage.fetch, toast, resize, refreshParent, openForm …) is in custom/PAGE_GUIDE.md (also part of Copy AI prompt). The API has a version ($nu->apiVersion(), now 1): pages that use only $nu keep working when nuBuilder Next changes inside.

API versions

Since 0.8.388 the page API ($nu and NuPage) has a version number – this nuBuilder Next supports version 1. A page declares the version it is written for with $nu->api(1); as the second line of index.php (the template and Copy AI prompt include it; a page without it counts as version 1).

  • Rule: within one version, methods are only added – never removed or changed. A breaking change raises the version; the older version keeps running (through an adapter) for at least 6 months / 20 releases.
  • Unsupported version: the page does not run; the globeadmin sees which version it needs and what this nuBuilder Next supports, other users a short error.
  • Deprecated methods keep working; each call writes a notice to Debug results (once a day per page and method), deprecated NuPage names a warning in the browser console.
  • Before an update: Check package on the update page lists every page the new version would break (unsupported version, unknown or removed $nu->… / NuPage.… calls) or that uses deprecated ones. The update can still be installed.
  • Form builder of a page form: the declared version and the problems with this version; the forms list shows a warning next to the type of such pages.
  • Only calls written as $nu->name( and NuPage.name are found – keep the variable name $nu.

Files, updates, copies

  • Pages live in custom/pages/<code>/, uploaded by FTP. $nuConfigCustomPagesDir in nuconfig.php (an absolute path) moves the pages folder, e.g. outside the web root – the safest setup.
  • Updates never touch custom/pages/ and custom/lib/ – only custom/.htaccess, custom/PAGE_GUIDE.md and custom/pages/_template/ come with nuBuilder Next. A rollback does not change them either. Include custom pages (update page, backups) puts a copy of the folders into a backup.
  • Direct requests of files in custom/ are blocked three ways: the guard line defined('NU_PAGE') || exit; at the top of every PHP file (the builder warns when index.php lacks it), custom/.htaccess (Apache) and the nginx rule in Web server rules. Security check tests that the folder cannot be reached.
  • Renaming the code of a page form: rename its folder by FTP too (the builder says so). Deleting a page form keeps its files.
  • The cloner copies a page form with its settings, not its files (it shows the folders to copy). The App cloner copies the folders with the files of the installation, but never secrets.php.

Installation and update

Requirements

  • Apache with AllowOverride All for the folder (nuBuilder Next protects its program files with .htaccess) – or nginx with the rules from Security check.
  • PHP 8.1 or newer with pdo_mysql (MySQL / MariaDB) or pdo_sqlsrv (MSSQL), mbstring, openssl.
  • A nuBuilder 4 database (or the install scripts for an empty database).
  • Recommended: nuBuilder Next in a sub-folder of nuBuilder (e.g. /nubuilder4/nunext/). Then nuBuilder's libraries are found automatically.

First installation (installer)

  1. Unpack nunext.zip on the web server (e.g. /nubuilder4/nunext/) – nunext-dev.zip is for development only. The package brings its libraries in vendor/bundled/ (Bootstrap, Bootstrap Icons, jQuery, jquery-confirm, Tom Select, CodeMirror, the code formatters, the QR code generator, ApexCharts, Font Awesome as a fallback) and the PHPMailer pack in _install/. TCPDF, TinyMCE, phpMyAdmin, Adminer and Tiny File Manager come as library packs – the installer offers them (PHPMailer from the package, without internet).
  2. Open nuBuilder Next in the browser. As long as nuconfig.php does not exist, every page shows the installer.
  3. Start: server check. From another computer you enter the setup token – nuBuilder Next writes it to _install/setup-token.txt; open that file by FTP / SFTP / file manager / SSH (it is readable for every account on the server, so also for an FTP user who is not the web server's user). Or create an empty file install.allow in the nuBuilder Next folder and click Start without a token – always possible, and the only way when the token file cannot be written. Only PHP's built-in development server (php -S) opened from the same computer skips the token – every other server asks for it (a reverse proxy on the same host would make every visitor look local). 10 wrong tokens lock the installer for 15 minutes.
  4. Database: MySQL / MariaDB or MSSQL; settings are taken from nuBuilder's nuconfig.php next to nuBuilder Next when found. Test connection checks them; the database can be created. While nuBuilder Next is being tested (since 0.8.380) a database that already holds nuBuilder's tables is refused – choose a new, empty database.
  5. Content: an empty database gets either nuBuilder's complete system (nubuilder4.sql from the nuBuilder folder, MySQL only), nuBuilder Next's own install scripts or – since 0.8.384 – the nubuilder4.sql of any nuBuilder 4.x version (MySQL only): upload it (.sql, .sql.gz or .zip, up to PHP's upload limit) or copy it into the folder _install/ by FTP / SFTP and pick it. The file is checked before it runs – it may only create, fill and change nuBuilder's own tables (zzzzsys_…); other tables, other databases, users and rights, files, triggers and routines are refused – and checked again right before the import. A file of an older version (4.5 – 4.8) is then brought to the structure of nuBuilder 4.9 like nuBuilder's own update does: missing tables created, nuBuilder's column changes applied (adapted to 4.9's own nubuilder4.sql), the *_json columns added, 4.5's views replaced; a 4.9 file stays as it is. nuBuilder's own system forms remain those of the file – if nuBuilder 4.9 runs on the same database too, run its update once. The uploaded file is removed after the installation. All tables are created as InnoDB.
  6. Administrator: globeadmin name and password – stored in plain text in nuconfig.php, as in nuBuilder – e-mail and optional two-factor login.
  7. Options: address, time zone, session timeout, nuBuilder folder, shared login. Install writes nuconfig.php from nuconfig-sample.php (with a new secret key; readable for every account on the server, so an FTP / SFTP user can download it – to change it use Admin tools → nuconfig.php or upload an edited copy), creates nuBuilder Next's tables and removes the token.
  8. Libraries (since 0.8.405, before Install): the six library packs with where each would come from – the GitHub release libraries (looked up once; Look on GitHub asks again) or zips copied into _install/ or _update/ (Look again). TCPDF, PHPMailer and TinyMCE are ticked, phpMyAdmin, Adminer and Tiny File Manager are optional. A pack with a wrong signature is listed in red with the reason and cannot be ticked. The ticked ones are installed after nuconfig.php is written; one that fails does not stop the installation (the result page says which, and the update page can install it later). Packs left in _install/ move to _update/.
  9. If the folder is not writable, the installer shows the content of nuconfig.php: download it, copy it to the shown place and click Check again.
  10. Sign in as globeadmin: the setup wizard follows with nuBuilder Next's own settings (language, look, security, sample data).
  11. Libraries not installed now: Update → Libraries (next chapter).

By hand instead: rename nuconfig-sample.php to nuconfig.php, enter the settings (an existing nuBuilder nuconfig.php works unchanged) and, for an empty database, run install/schema_mysql.sql, schema_mysql_forms.sql and notes_snippets_mysql.sql (MSSQL: schema_mssql.sql).

nuBuilder Next's own tables (zzzzsys_nunext_*: log, form history, 2FA, tokens, sessions) are created automatically on first use, as InnoDB.

Setup wizard

Right after the globeadmin's sign-in, nuBuilder Next opens the setup wizard – after a new installation and also when nuconfig.php already exists, e.g. nuBuilder Next added to a running nuBuilder. It asks only for nuBuilder Next's settings; the database is not touched otherwise. Nothing changes before Apply on the last step.

  • Basics: default language (nuBuilder's Setup → Language; used for the globeadmin and for users without their own language; English as UK, Australia or US), time zone, address (URL), session timeouts for users and for the globeadmin, nuBuilder folder, shared login.
  • Look & tools: application title ($nuConfigTitle), environment label such as TEST or DEV (see Branding), primary database tool (when phpMyAdmin and Adminer are both there), REST API on / off.
  • Security: a new globeadmin password (you sign in again afterwards), two-factor login for the globeadmin with its e-mail address, whether the page runs on HTTPS, and the cron line to copy.
  • Sample data: install (or refresh) the sample application; the new passwords of the sample users are shown once afterwards.

The settings are written to nuconfig.php in one save (with a backup in _backup/, like Admin tools → nuconfig.php); with $nuConfigSettingsFromDB = true settings that have a row in nuBuilder's settings table are saved there. When PHP cannot write nuconfig.php, the wizard shows the lines to add by hand.

When it opens: once per sign-in, until it is finished or closed with Skip, do not show again. Both write $nuConfigShowInstaller = false; to nuconfig.php (and note it in the database, which is enough when the file is read-only). $nuConfigShowInstaller = true; shows it again after every sign-in; Admin tools → Setup wizard opens it any time. Not for demo users or while acting as another user.

Publishing the library packs on GitHub (step by step)

The packs live in one separate release with the tag libraries – never in a nuBuilder Next release (those carry only nunext.zip). It is created once and afterwards only edited when a library changes.

The first time – create the release:

  1. On the development installation: Update → Libraries → Build library packs, choose the key file, Build and sign, then Download all (zip). Unpack that zip (nunext-libs-<date>.zip) on your computer – it holds libraries.json and one nunext-lib-<name>-<version>.zip per library. The bundle itself is not uploaded.
  2. On GitHub, in the repository (nuBuilder/nuBuilder-Next, or the one set under Update from GitHub): Releases → Draft a new release.
  3. Choose a tag → type libraries (exactly this, lower case) → Create new tag: libraries on publish. The target branch does not matter.
  4. Release title: anything, e.g. Library packs. The description may stay empty.
  5. Drag libraries.json and every nunext-lib-….zip into the box Attach binaries – all at once; each must be its own file.
  6. Tick Set as a pre-release, so the release is never shown as the repository's latest one (on GitHub's page the newest nuBuilder Next version stays "Latest"). If the form shows Set as the latest release, leave it unticked.
  7. Publish release.
  8. On a server: Update → Libraries → Look on GitHub – the card lists the packs ("GitHub nuBuilder/nuBuilder-Next, release "libraries": … packs").

When a library changes – no new release, the same one is edited:

  1. Put the new version into its source folder (../libsrc/<name>/ or _libsrc/<name>/; for an own build raise the version: line of its NUNEXT-VERSION.txt, e.g. …nu2 → …nu3).
  2. Build library packs: tick only that library, leave Keep the other libraries of the current GitHub index ticked (the new libraries.json then still lists the other packs), choose the key file, Build and sign, download the files.
  3. GitHub: Releases → the release libraries → Edit (pencil). Delete the old libraries.json (and the old zip of that library, if it is no longer to be offered – servers only use what libraries.json lists), drag in the new libraries.json and the new zip, Update release.
  4. Servers see it at their daily look or with Look on GitHub; nothing is installed by itself. If a nuBuilder Next version needs the new library (install/libraries-required.json), publish the pack first, then that version.

Servers check every file themselves: libraries.json must be signed with the key of nunext.zip, each zip must match its size and SHA-256 in the index and its own signature – a changed or foreign file on GitHub is never installed.

TCPDF 7 (0.8.232): TCPDF 7 is only a compatibility layer over tc-lib-pdf and needs it with about a dozen tc-lib-* libraries, Composer's vendor/autoload.php, the converted fonts of tc-lib-pdf-font and PHP 8.2 or newer. Build its pack from a complete Composer folder (vendor/tecnickcom/tcpdf/tcpdf.php and vendor/autoload.php) – nuBuilder Next finds TCPDF there and loads the autoloader; nuBuilder keeps its own TCPDF 6. A folder with TCPDF 7 but without its libraries gives a clear message.

Own build or patched copy (e.g. Tiny File Manager from GitHub's master with your own fixes): put a file NUNEXT-VERSION.txt into the library's folder before building the pack. nuBuilder Next reads version: from it (e.g. 2.6+git.4149143.nu1 = release 2.6, master commit 4149143, own changes round 1 – compared as 2.6; the folder becomes tinyfilemanager-2.6_git.4149143.nu1) and lines like CVE-2025-15138: open … / fixed … / patched locally …: the Security check warns about Tiny File Manager until that CVE line starts with fixed or patched. Missing columns and columns with a smaller type (e.g. varchar(100) instead of varchar(255)) are listed and selected; they are changed when you click Install, before the files are copied. Columns whose database type is larger or different are listed separately and not selected – changing them could cut off or convert values. Column types are compared on MySQL / MariaDB only (MSSQL, SQLite: missing columns). Primary keys and extra columns are never changed, missing tables are not created. Back up the database first: the file backup does not cover structure changes. The same check is at the bottom of the update page for the installed version (Change selected columns).
  7. Click Install and confirm: a window with a spinner shows the version being installed and that the page must stay open until the result appears (it cannot be closed; Install and Cancel are locked – the install also finishes on the server when the connection drops; open the update page again to see the result). nuBuilder Next checks every file, makes a backup (program files and nuBuilder Next's own tables – with Back up the whole database too also an SQL dump of the database, ticked when it is smaller than 50 MB; an update can change the database structure), switches on maintenance mode (users see a short notice; you keep working), copies the new files, removes old ones and resets PHP's code cache. If copying fails, the backup is put back automatically.
  8. Unattended update (command line or REST API, 0.8.301) – the same steps without a browser, for scripts, cron jobs and updating several installations from one place. Only packages with a valid signature are installed; $nuConfigEnableDatabaseUpdate = false blocks it; one update at a time (lock file); every run is logged and kept as a job (_backup/update-job-*.json, the last 20). Options for both:
    • url (https; http only for localhost; at most 64 MB) – or "github": true (0.8.374: the newest release of the repository set on the update page; not newer than the installed version → error unless reinstall) – or on the command line zip (a file on the server); sha256: expected checksum of the package (optional).
    • backup: auto (default: whole database without logs when it is smaller than 50 MB, otherwise program files only) · files · sql · sql_nologs.
    • schema: database columns to change before the files – safe (default, as the page preselects: missing columns and larger types) · missing · all (also types that could cut values) · none.
    • sample: auto (default: refresh the sample data when the package brings a newer sample version) · yes · no. New sample passwords are never printed or returned: Sample data → New passwords.
    • reinstall: also when the package is not newer. dry_run: check only – signature, requirements, file changes (new / changed / removed), database differences and what would be applied, sample data, backup mode – nothing changes.
    Like the page, an update has two phases: the check and install, then the database steps with the new code. The command line starts the second phase itself in a new PHP process; for the API it runs on the status request; a job that is still pending is also finished by cron.php and by opening the update page.
    Command line (as the web server's user, so the new files belong to it): sudo -u www-data php cron.php update --url=https://example.com/nunext.zip --dry-run (or --github instead of --url), then without --dry-run. Options as --backup=sql --schema=missing --sample=no --reinstall --sha256=… --json; php cron.php update --status [job] lists the jobs; exit code 0 = done / checked, 1 = failed, 2 = wrong call.
    REST API: an API client with the scope system:update (admin level – give it only to a client you trust, ideally with an IP allowlist). POST /v1/system/update with {"url": "https://…/nunext.zip", "dry_run": true} answers 200 with the check; without dry_run it installs and answers 202 with the job and Location: /v1/system/update/{job}. Call GET /v1/system/update/{job} once afterwards: it runs the database steps and returns status: done (or failed with the errors). GET /v1/system/update shows the installed version and the last jobs. A failed check answers 409 with the errors. The API playground has the three requests.
  9. Sample data: when the sample data is installed, Update the sample data too appears next to Install – ticked when the package brings a newer sample version (the label shows both versions). After the update (with the new code) the sample data is refreshed as with Admin tools → Sample data → Refresh: all sample records are created again, changes to them are lost and the sample users get new passwords; the result page links to them.
  10. The Server card lists what the update needs. Folder writable is red when PHP may only read the program folders – usually because they were uploaded by SFTP and belong to the SFTP user (permissions 755), while PHP runs as the web server's user (e.g. www-data). The (i) next to it shows the fix: chown by SSH, or in the SFTP client set the folders to 777 for the update (recursive, folders only) and back to 755 afterwards – or update by hand by uploading the files of nunext.zip over the old ones (the database steps run on the next page view). PHP upload limit is red below 16 MB (upload_max_filesize / post_max_size).
  11. The tab Libraries: the library packs (install, update, roll back, remove, self-test) and the card Libraries (collapsed – click to open; a yellow badge counts problems) with the libraries in the package – version, folder, use and licence, replaced by an update. Check package also lists the libraries the new package changes (e.g. Tom Select 2.6.2 → 2.7.0).
  12. The next page shows "Updated from … to …" and runs the database steps of the new version. Maintenance mode ends – also by itself as soon as the new version is completely installed (e.g. when the update logged you out), at the latest after 15 minutes; End maintenance mode on this page ends it at once.

Change history: the card Change history on the update page lists every version of the installed package, newest first – 10 per page with the list footer, the installed one with a green badge, the newest five open; the search field (Enter) finds versions by number, title and text, with every hit open. The user menu entry nuBuilder Next 0.8.x · What's new opens it.

nuconfig.php, vendor/packs/ (the library packs) and the copies of earlier versions in third_party/, assets/vendor/ and lib/ are never touched; vendor/bundled/ is replaced by the package's libraries.

Backups are listed below the upload, newest first, 10 per page (first / previous / page / next / last below the list): download, Roll back (puts the program files of that version back – the current files are backed up first; database changes stay) or delete them. Back up now makes one by hand – once per click: the button is disabled while the backup is made, a second click or a resent form is refused ("already made"), and two backups never run at the same time. Backups are stored in _backup/, or in $nuConfigBackupPath – preferably a folder outside the web root, above all when backups contain the database.

Database in the backup (MySQL / MariaDB and SQL Server – written by the App cloner's export): next to Back up now, Database chooses none (the default), nuBuilder Next tables or the whole database – tables, views, data, functions, procedures, triggers and events, written by the same code as the App cloner's Download SQL (sessions and one-time tokens are left out). without logs (default) creates the log tables empty. The sizes shown are estimates. The dump is stored gzip-compressed in the backup (db/database.sql.gz):

  • A green SQL badge shows its size (tooltip: tables and rows). The download button then offers Whole backup (.zip) or SQL only (.sql.gz) – that file can be imported with phpMyAdmin (Import) or zcat file.sql.gz | mysql newdb – SQL Server: unpack it and run it with SQL Server Management Studio or sqlcmd. Restoring the database is done by hand; Roll back only puts the program files back.
  • Every dump ends with a marker line that is checked: if it is missing or the dump failed, the badge says SQL incomplete (red) – don't rely on it. If the server stops the backup (time limit), no backup is saved and the next visit of the update page says so; choose nuBuilder Next tables or without logs, or ask your hoster for a longer time limit.
  • MySQL / MariaDB: the dump is taken in one consistent snapshot (InnoDB) with TIMESTAMP values in UTC – records saved during the backup can't leave half a change in it, and it imports with the same moments on a server in another time zone. INSERT statements are at most about 1 MB, so the import also works where max_allowed_packet is small.
  • Keep SQL dumps in the newest … backups (default 5, 0 = all): older backups lose their dump automatically (badge SQL removed), their program files stay. The header shows the number and total size of the backups.

If the update page is not available (e.g. PHP may not write to the folder): unpack the zip over the old folder (nuconfig.php and _backup/ stay), and log in as globeadmin – the database steps run automatically. What changed in each version: CHANGELOG.md in the package, or Change history on the update page.

The server needs PHP 8.1+, the zip extension, write permission for PHP on the nuBuilder Next folder (Plesk: the folder belongs to the site user) and some free disk space – the update page shows each of them.

One-time login link (nuBuilder's Single-User Password Token, 0.8.339): index.php?u=<login name or user id>&p=<token> (with &f= / &r= as above) signs the user in once when the token matches LOGIN_TOKEN in the user's sus_json – like nuBuilder without a second factor; afterwards the token is replaced by a new random one, so the same link never works twice (also not for two clicks at the same moment). Ways to get a token:

  • User form (globeadmin) → One-time login link: validity 1 hour, 1 day, 7 days, 30 days or no expiry; Create link shows the link once to copy, the envelope sends it to the user's e-mail address (in the user's language), the red button removes the token.
  • In a procedure: nuCreateLoginToken($userId, $minutes = 0, $formId = '', $recordId = '') returns the link ('' when not possible).
  • REST API: POST /v1/users/{id}/login-link (scope users:login_link, see REST API).
  • Another system writes the token itself, as in nuBuilder's wiki: sus_json → {"LOGIN_TOKEN": "…"}, at least 20 characters; optional "LOGIN_TOKEN_EXPIRES": <Unix time> (nuBuilder Next only – nuBuilder ignores it).

Differences to nuBuilder (all safer, the links stay compatible): exact comparison in constant time, never the globeadmin or an API service user, the user's expiry date and access level apply, wrong tokens count for the login rate limit, every use is logged (Login with via: token), creating, mailing and removing are logged too. Dangerous actions still ask for the password (the session counts as not confirmed). p with 64 hex characters is nuBuilder Next's signed auto-login hash while $nuConfigAutoLogin is on; anything else of 20 characters or more is treated as a token. Own login page: $nuWelcomeBodyInnerHTML works as in nuBuilder – nuBuilder's HTML can be used as it is (inputs nuusername / nupassword, the submit button). Error messages, "Forgot password?", the language and theme menus stay. nuconfig-sample.php has a commented example.

Acting as another user (globeadmin)

To see nuBuilder Next exactly as a user does – menu, forms, rights, permission items, hash variables – the globeadmin clicks Act as user in the user form – the icon in front of the user name – or in a row of Log → Sessions, and chooses:

  • View only: everything the user sees, but nothing can be changed – no save, delete, clone or new, no procedures, no form posts.
  • Full access: work as the user (after a confirmation). Records are saved as this user; nuBuilder Next's log adds acting_globeadmin to every entry written meanwhile.

A coloured bar (blue = view only, red = full access) stays on top of every page; Back to globeadmin (in the bar or the user menu) returns to the page where you started – no new login. Works for every user, also expired ones and users with two-step login (no code needed). Not available while acting: the user's password and the security page (two-step login, devices). If the user is deleted or gets a new password meanwhile, you are the globeadmin again. A session timeout logs you out completely. Start and end are logged (impersonate_start / impersonate_end).

Demo mode

Lets visitors look at the whole application – forms, lists, the form builder, the admin pages – without being able to change anything. Like nuBuilder's demo mode, but with a real user:

  1. Create a user (e.g. login demo) with a password and any access level – it is only needed to log in.
  2. In nuconfig.php: $nuConfigDemoUser = "demo"; – the login name or the user id. Several demo users are separated by commas.
  3. Optional: $nuConfigDemoSavingAllowedIds = "form_id,form_code"; – forms where demo users may still save (nuBuilder's setting, also in Admin tools → Settings).

nuBuilder's demo globeadmin (0.8.341): with $nuConfigIsDemo = true, $nuConfigDemoDBGlobeadminUsername and $nuConfigDemoDBGlobeadminPassword – the same settings as in nuBuilder – that name and password sign in as a read-only demo globeadmin, also in nuBuilder Next (and the login page offers it under Try the demo). The real globeadmin's name and password always win. Changing the three settings ends running demo globeadmin sessions. Developer mode is never on for a demo session.

The login page then shows Try the demo (one button per demo user): one click logs in without a password. A demo user can also log in with name and password, or through an auto-login link. In the top bar a badge Demo – read only shows the mode.

What a demo user can do:

  • See everything the globeadmin sees – all forms and records, the form builder, procedures, settings, log. All buttons are there.
  • Change nothing: whatever would change data answers Not available in the demo – saving (except in the allowed forms), deleting (never, also not sub-form rows), the builder, user and access level pages, settings, update, CSV import, cloner, phpMyAdmin and File Manager, acting as another user.
  • Saving in the allowed forms: at most 10 times per hour per visitor (IP address) and 100 times per hour for all demo visitors together – then at most 10 saves per hour.
  • Procedures run only when Demo access is switched on (procedure form) – and they cannot write either. No e-mails are sent.
  • The database refuses every change of a demo session (also from PHP in forms – Before Browse / Before Edit code that writes ends with the demo message). Exceptions: nuBuilder Next's session and log tables and temporary tables (#TABLE_ID#).
  • Never shown: passwords and keys in Settings and Inspect record, auto-login links, backups, the database name, IP addresses of sessions and log entries; in sus_json the login token, two-factor and OTP secrets (•••).
  • Typed SQL (SQL builder preview, dashboard widgets) may not mention zzzzsys_user, zzzzsys_session, zzzzsys_setup, zzzzsys_config, nuBuilder Next's own tables or the server's catalogs (information_schema, mysql, performance_schema, sys) anywhere in the statement – also after a comma, in STRAIGHT_JOIN, in parentheses or with a schema name (0.8.341).
  • Own account: no password change, no "Forgot password" e-mail, no two-step login. The language can be switched for the session.

Demo data reset (0.8.341): System status → Demo mode → Demo data lists the tables of the allowed forms and their sub-forms. Take snapshot stores their rows (in the protected backup folder, at most 50,000 rows / 20 MB); Reset now empties the tables and fills them from the snapshot; Reset automatically (never, 6 or 12 hours, 1, 2 or 7 days – default 1 day) lets the housekeeping (cron.php, or now and then a page view) do it. Without a snapshot nothing is reset.

System status → Demo mode shows the demo users and warns when one cannot log in (unknown, expired, no access level), which forms allow saving and which procedures have Demo access. The globeadmin can try it with Act as user on the demo user. A nuBuilder demo session is never taken over by the shared login.

In form code and procedures, nuDemo() (as in nuBuilder) returns true in a demo session and adds Not available in the demo to the messages; nuDemo(false) only checks.

Keep in mind: demo users see all data and code of the application – use a database with demo data.

Logged-in users

Log → Logged-in users lists every active nuBuilder Next session: user, IP address, browser, login time and last activity (green = active in the last 5 minutes). Activity is recorded at most every 30 seconds.

  • End session signs the user out with his next click (your own session cannot be ended here).
  • Log out all others ends every nuBuilder Next session except your own; Log out everyone (incl. me) ends your own session too, and you sign in again. Both ask first and are logged (All sessions ended). nuBuilder's own sessions are not touched.
  • The (i) next to the title shows the current timeouts. Sessions without activity for longer than $nuConfigSessionTimeout (globeadmin: $nuConfigSessionTimeoutGlobeadmin) disappear.
  • The second list shows nuBuilder's sessions (zzzzsys_session) for information; they are ended in nuBuilder.

Admin roles

Start page → Admin roles (0.8.323) gives other users a defined part of the globeadmin's rights in nuBuilder Next. A role is a set of rights, one per tool, each view or change (some tools have one level only, e.g. Database or Setup wizard). A user gets at most one role: the field Admin role on the user form. nuBuilder itself does not know these roles – there the user stays a normal user with his access level.

  • Default roles (created once, then editable and copyable): Full administrator (everything), Administrator without system (everything except Update, nuconfig.php, Settings, Database, File Manager, App cloner, API clients, Admin roles), Developer (forms, procedures, reports, dashboards, prompt generator, CSV import, debug results and compatibility check to view), User manager (users, access levels, logged-in users) and Support (read only) (change log, audit trail, debug results, logged-in users, System status – view only; audit trail since 0.8.350 – roles created before keep their rights). Since 0.8.357 a role can also have Notifications (view = all notifications and read receipts, change = send).
  • What a user with a role sees: the start page tiles, ▾ menu entries, Ctrl+K results and admin help chapters of his rights – and his normal forms below. Every page checks the right on the server; a page he may only view shows View only and its buttons that change something are switched off. Customize needs the right Start page layout (the layout chosen for them – a shared layout of their role or an own one, see Saved layouts below).
  • Rights on nuBuilder's system forms (users and permission items, access levels, forms with items, files, formats and translations, procedures, reports and SQL builder, e-mail, logs) are added to the user's access level: change = all buttons, view = open and print.
  • Full access (red badge): Update, nuconfig.php, Database, File Manager, App cloner, forms, procedures, act as another user, Admin roles and API clients lead to full access in the end – PHP code on the server, the whole database, the web folder or the passwords. Give them only to people you would trust with the globeadmin password.
  • Who manages roles: the globeadmin and users with the right Admin roles. Nobody gives rights he does not have himself, changes his own role or edits the role he holds; a role with users cannot be deleted. Users with a role act as other users only when the role has Act as another user, and never as another admin.
  • Publish forms (drafts) (0.8.386): publishes form drafts; starting and editing a draft only needs the rights on the form.
  • The log names the real user; Security check lists everybody with an admin role and warns when a role holds full-access rights. Two-factor login is not required for admin roles (the access level's 2FA setting applies).

Start page hooks

Since 0.8.378 a procedure with the reserved code nunext_home runs every time the tile start page is built (globeadmin and users with an admin role – normal users get their access level's page and are not affected). Its PHP changes only this page view: badges, descriptions, hidden tiles, extra groups and tiles, banners. Nothing is saved into a layout. Create it under Procedures → Add, code nunext_home (suggested in the code field); status Draft or Archived switches it off.

// procedure nunext_home – runs every time the tile start page is built
nuHomeCache(60);                                   // keep the result 60 s per user

$open = (int)nuRunQuery("SELECT COUNT(*) FROM orders WHERE status = 'open'")->fetchColumn();
nuHomeSetBadge('c_orders', "$open open", $open > 20 ? 'danger' : 'secondary');

if ('#ADMIN_ROLE#' === 'Developer') nuHomeHideTile('cloner');

nuHomeAddGroup('x_today', 'Today');
nuHomeAddTile('x_backup', ['group' => 'x_today', 'label' => 'Last backup', 'icon' => 'bi-archive', 'page' => 'update']);

nuHomeBanner('Maintenance on Saturday 22:00', 'warning');
nuHomeSetData('openOrders', $open);
  • Tile keys: built-in tiles by their key (users, access, forms, update … – the data-nu-tile attribute of a tile), own tiles c_…, pinned pages, and the hook's own tiles x_….
  • Hash variables: the user's ones (#USER_ID#, #USER_LOGIN#, #GLOBAL_ACCESS#, #ACCESS_LEVEL_CODE#, #USER_DEPARTMENT#, #USER_TEAM#, #LANGUAGE# …) and #ADMIN_ROLE# (name of the user's admin role, empty for the globeadmin), #HOME_LAYOUT# (name of the start page layout), #HOME_SIZE# (large, compact, list, listwide, list2), #HOME_DISPLAY# (groups, tabs).
  • Dynamic tiles are checked like own tiles of the tile editor – a link the editor would refuse is refused here too – and drawn by the same code: search, the compact tooltips and every tile size work. They are not shown in Customise (so they can never be saved into a layout) and cannot be favourites. A form tile is shown only to users with rights on the form. All texts are escaped – a hook cannot add HTML.
  • Errors: a failing hook (an error, an exception, a refused tile or key) leaves the page as it would be without the hook. The globeadmin sees the message above the tiles with a link to the procedure; users with an admin role see nothing. Every error and every echo output goes to Debug results.
  • Off switch: $nuConfigHomeHooks = false; in nuconfig.php (or the row Start Page Hooks in Settings). Safe mode: index.php?p=home&tiles=1&safe=1 skips the hook for one page view (globeadmin only; a note on the page says so).
  • Speed: the hook runs on every visit – nuHomeCache(seconds) (at most 3600) keeps its result in the session of each user (also for the same layout and the same code).
  • Demo mode: the hook runs read only for demo visitors (writes stop it with an error). An active hook is listed as information in the Security check and in System status. Whoever may change procedures may change the hook – there is no extra right.
  • nuAddJavascript() does nothing on this page (the start page allows only scripts from files). Hand values to JavaScript with nuHomeSetData().

Configuration file (nuconfig.php)

Admin tools → Configuration file (nuconfig.php) (globeadmin; not in demo mode) edits nuconfig.php in a code editor with the usual tool buttons (undo / redo, search, replace, comment, spaces and tabs, Format, full screen – no hash variables). The path is shown under the title.

  • Save writes the file only if it passes every check: valid PHP, starts with <?php, runs without an error and without output, sets $nuConfigDBName, and the database connects with the new settings. Save checks right away, without leaving the page: on an error the message appears above the editor and the line PHP reports is marked (for a missing ; that is often the line after it); the file is not written. Check runs the same tests without saving.
  • Before writing, the current file is copied to the backup folder (_backup/ or $nuConfigBackupPath, blocked for the web) as nuconfig-<date-time>.php; the newest 10 are kept. Backups loads one into the editor – Save restores it.
  • If someone else changed the file since the page was opened (FTP, another globeadmin), saving is refused and your text is kept.
  • Changes apply with the next request. A nuBuilder that reads the same file is affected too. New globeadmin user name / password: the current session continues, the next login uses the new ones. Saving is logged (nuconfig.php changed, without the content).
  • The web server needs write access to the file and its folder; otherwise the editor is read only. If a saved value still stops the site from working (e.g. a setting nuBuilder Next reads only later), correct the file by FTP or copy a backup over it.

CSV import

Admin tools → CSV import (also Forms → Tools; globeadmin only) imports a CSV file into a table of the database in three steps. nuBuilder's and nuBuilder Next's own tables (zzzzsys_…) cannot be chosen.

  1. File: choose or drop the file (up to $nuConfigImportMaxMB, default 20 MB). The encoding (UTF-8, UTF-16, Windows-1252 from Excel) and the separator are detected; separator, text qualifier and "first row holds the column names" can be changed – the preview shows the first 10 rows.
  2. Mapping: choose the table; Map automatically matches CSV columns by name (also with the table's column prefix like cus_, German and English synonyms). Each column gets a CSV column, a fixed value or – for nuBuilder ids – Generate nuID(). Date columns get a format (detected from the file; Unix timestamps and Excel numbers too); numbers follow the chosen decimal separator (detected), yes/no values (ja, x, true, 1 …) become 1/0. The preview column shows converted values and problems right away.
    Options: add new records, update existing ones or both (found by a key column), empty values as NULL or empty text, trim spaces, fill created/updated columns, and what happens on errors: all or nothing (default) or skip faulty rows.
  3. Check runs the whole import as a trial in a transaction that is rolled back – it shows new, updated and faulty rows with line, column, value and problem, including database errors such as duplicate keys. The problem list can be downloaded as CSV. Import now then writes the data.

Save configuration downloads the mapping and options as JSON; Load configuration applies it to the next file (columns are matched by name). The uploaded file is kept only for this session in a private temp folder and deleted after the import. Every import is written to the Log.

Cloner (copy a form)

Forms → Tools → Cloner, or the copy button of a form in the list (globeadmin), copies a form – as nuBuilder's cloner:

  • What: the form with its browse columns and PHP (Before Browse, Before Save …), the chosen tabs with their objects, events and object PHP (e.g. lookup After Browse); optionally its subforms and iframe forms (each copied once, the copied objects point to the copies – the original stays untouched) and the access level rights.
  • Where: as a new form (code and description can be changed; default code_clone_1, the first free number) or into an existing form – the tabs come after its own, object ids that exist there get _2, _3 … (listed afterwards).
  • Only create SQL: instead of cloning, the INSERT statements are shown to copy or download (optionally with the same primary keys, REPLACE INTO and notes) – e.g. to move a form to another database.
  • Everything runs in one transaction: an error changes nothing. The copy uses the same table as the source. The result links to the new form and the form designer; the form history and the Log record it.
  • Saved settings: the Cloner opens with a list of saved settings – Add (or the copy button of a form) opens a new one, Save keeps source form, destination, tabs, subforms, iframe forms and the options; Clone copies them, Delete removes them. They are stored in nuBuilder's table zzzzsys_cloner – the same settings nuBuilder's Cloner opens, and the other way round. Clone / Create SQL work with the values on the page, saved or not. The code of a new form is not saved – a free one is suggested each time.

App cloner (copy the whole application)

Admin tools → App cloner (globeadmin, MySQL / MariaDB or SQL Server – source and target are the same kind) copies the whole application – e.g. for a test or development copy:

  • Database: into another database on the same or another server (it can be created). Choose what is copied: nuBuilder system tables and views, own tables and views, system records (nu…), application records (forms, users …), data of own tables, functions, procedures, triggers, events – all tables or chosen ones. When the target is not empty: stop, add to it, or empty it first. Sessions and one-time tokens (password reset links) are left out by default.
  • Files (optional): the nuBuilder folder – with nuBuilder Next inside – into another folder; folders to leave out (e.g. .git, backups) can be listed. The database settings in the copied nuconfig.php files are changed to the target database.
  • 1:1 copy (MySQL / MariaDB): tables exactly as SHOW CREATE TABLE gives them (engine, row format, partitions, collations per column, comments, generated columns, AUTO_INCREMENT values), all indexes (unique, prefix, descending, ignored / invisible, fulltext, spatial), CHECK constraints and foreign keys (ON DELETE / ON UPDATE), MariaDB sequences with their current value, every row byte for byte (binary data, BIT, geometry, JSON, emoji, zero dates), views in dependency order after the functions they may call, functions and procedures with their own sql_mode, triggers in their execution order (FOLLOWS / PRECEDES) and events with their time zone. Like mysqldump the copy runs with sql_mode = 'NO_AUTO_VALUE_ON_ZERO' only, so also data a strict server would refuse (zero dates, old ENUM definitions) arrives unchanged. Not copied (they do not belong to the database): users and privileges; DEFINER becomes the target's user. An object that cannot be created is a warning in the log – the rest is still copied.
  • Live database (MySQL / MariaDB): all tables are read in one consistent snapshot (START TRANSACTION WITH CONSISTENT SNAPSHOT, as mysqldump --single-transaction) – a record saved while the clone runs is either completely in the copy or not at all (InnoDB tables; MyISAM tables have no snapshot). Each table is read once with one streaming query, so large tables are not slower towards the end. TIMESTAMP values are read and written in UTC (time_zone '+00:00'), so a copy to a server in another time zone keeps the same moments. INSERT statements are at most about 1 MB (and at most half of the target's max_allowed_packet), so tables with large BLOBs no longer break the copy or the import; a single row larger than max_allowed_packet is reported as a warning and the clone goes on. The rows of a table are written in one transaction; the SQL file wraps each table in SET autocommit = 0 … COMMIT and DISABLE KEYS / ENABLE KEYS, which makes the import noticeably faster.
  • Dry run shows every step and how many rows and files would be copied, without changing anything. Run asks once more and shows the log while it runs; at the end the record counts of source and target are compared.
  • Download SQL exports the database as an SQL file instead – for an import with phpMyAdmin elsewhere. On shared hosting, where PHP cannot create databases, create the database in the control panel and use Add to it, or import the SQL file.
  • Safety: the target can't be this database, the target folder can't be inside the nuBuilder folder (or the other way round), and nothing outside the target is deleted. DEFINER is removed from views and routines so they work with another database user; routines the user may not read are reported. The password of the target is not stored.
  • Saved configurations: the App cloner opens with a list of saved configurations – Add opens a new one with code and description; Save, Clone and Delete as on other pages. They are stored in nuBuilder's table zzzzsys_app_cloner – the same configurations nuBuilder's App cloner opens, and the other way round. Not saved: the target password (a password saved with nuBuilder's App cloner is used when the field stays empty), Create it when it does not exist and Leave out sessions (both on when a configuration is opened). Download SQL, Dry run and Run work with the values on the page, saved or not.
  • SQL Server: tables, views, functions, procedures and DML triggers of your schema (usually dbo). The structure is read from SQL Server's catalog: columns with IDENTITY, defaults, computed columns, primary key, unique and check constraints, indexes (XML, spatial and columnstore indexes are reported and left out). Foreign keys are added after the data, so the order of the tables does not matter; functions come before the views that may use them. Data is copied in batches (max. 1000 rows per INSERT) with IDENTITY_INSERT. Collation instead of character set; INSERT only (no INSERT IGNORE / REPLACE); SQL Server has no events (SQL Server Agent jobs are not copied). The SQL file separates batches with GO – run it in SQL Server Management Studio or with sqlcmd -S server -d newdb -i file.sql; it can be run again on the same database (foreign keys and tables are dropped first). Encrypted modules cannot be read and are reported.

Dashboards (KPI tiles, charts, tables)

Admin tools → Dashboards (globeadmin) builds dashboards from SQL. A dashboard is a set of widgets and can be shown on the start page of users and anywhere on any launch or edit form.

  • Widgets: KPI tile – first column = value, optional second = previous value (change ▲▼ in %), third = a note; colour by thresholds (low / high, higher is better). Chart (ApexCharts) – columns, bars, line, area, pie, donut, radial: first column = categories (x axis), every further column = one series named after the column; pie / donut: label and value. Table – the rows as returned (up to 100). Per widget: width (quarter … full; tablets show two, phones one per row), number format, decimals, text before / after (e.g. CHF), chart height, stacked, a link (form list, report or address), cache and automatic refresh.
  • Data sources: SQL – exactly one SELECT; a saved SQL builder query; or a PHP procedure that hands over its rows with nuDashboardData($rows) (a list of arrays, e.g. [['month' => 'Jan', 'sales' => 120], …]; the user does not need access to the procedure). Everything runs read-only (rolled-back READ ONLY transaction, 10 s time limit) – a widget cannot change data.
  • Hash variables: the user's (#USER_ID#, #USER_CODE#, #ACCESS_LEVEL_CODE#, #LANGUAGE# …), the date filter #DATE_FROM# / #DATE_TO# (YYYY-MM-DD) and on forms #RECORD_ID# and the fields of the record (#cus_id#). Values are escaped – write them in quotes: WHERE ord_customer_id = '#RECORD_ID#'. The values of the saved record are read from the database, not from the browser; fields that are not saved (criteria of a launch form, display fields) come from the page. Widget titles may contain hash variables too (Orders of #cus_name#).
  • Start page: Show on the start page + access levels (none ticked = every user). Users see the dashboards of their access level above their forms, in the dashboards' order. The globeadmin's start page keeps its tiles.
  • On forms: add an HTML object in the form builder with <div data-nu-dashboard="CODE"></div> – position, size and tab as for any object (make it large enough; it scrolls otherwise). nuBuilder shows an empty box there, so the form keeps working in nuBuilder. In form JavaScript: nuNextDashboard('CODE', 'element_id'); nuNextDashboardRefresh() (or nuNextDashboardRefresh('CODE')) reads the data again, e.g. after the criteria of a launch form changed. Everyone who may open the form (and the record) sees the dashboard, unless access levels are ticked. On a new record, widgets that use #RECORD_ID# or a field show Available after saving; after saving they are filled. The dashboard page shows the snippet to copy and the forms that use it.
  • Date filter: shown above a dashboard when one of its widgets uses #DATE_FROM# / #DATE_TO# – today, yesterday, last 7 / 30 / 90 days, this / last month, this quarter, this / last year, all or custom dates. Each user's last choice is remembered in the browser; the default comes from the dashboard.
  • Test on the widget page runs the widget before saving (with a date range and an optional #RECORD_ID#) and shows the preview and the rows. The dashboard page shows a live preview of all widgets.
  • Cache: results are kept per user for the widget's cache time (default 60 s), so a busy start page does not run every query on every visit; the refresh button reads them again. Errors are shown in full to the globeadmin only, users see Not available.
  • Examples in the sample data (Admin tools → Sample data): sample_sales (start page of sample_manager / sample_sales: KPIs, charts, latest orders, date filter), sample_products (start page of every sample level: SQL, the SQL builder query sample_orders and the PHP procedure sample_dashboard_data), sample_customer (customer form, tab Statistics, #RECORD_ID#) and sample_country (sample start form: the field home_country filters, its onchange calls nuNextDashboardRefresh('sample_country')).
  • Stored in nuBuilder Next's tables zzzzsys_nunext_dashboard and zzzzsys_nunext_widget (part of backups and App cloner copies). Charts use the bundled ApexCharts (loaded only where a dashboard has a chart) and follow dark mode and the branding accent colour. Pages with dashboards allow style attributes and a per-page style nonce for ApexCharts; scripts stay restricted.

Storage engine (InnoDB)

All tables should use InnoDB (transactions, row locking, crash safety). nuBuilder Next creates every new table – its own, the ones of new forms and nuCreateTableFromSelect() – as InnoDB, whatever $nuConfigDBEngine says. Older nuBuilder databases often still contain MyISAM tables.

  • System status → Storage engine lists every table that is not InnoDB with its engine and approximate row count.
  • Convert all to InnoDB runs ALTER TABLE … ENGINE=InnoDB table by table. Tables that fail are listed; the others are converted. Make a backup first; large tables take time.
  • Keep $nuConfigDBEngine = "InnoDB" in nuconfig.php: nuBuilder's update converts its system tables to that engine.

REST API

JSON API for users, access levels with their form rights, permission items and reports (PDF): api.php/v1/… (no URL rewriting needed). Switch it on with $nuConfigApi = true in nuconfig.php and set a long random $nuConfigSecretKey. HTTPS only (localhost excepted; $nuConfigApiAllowHttp = true for tests). Access tokens live $nuConfigApiTokenMinutes minutes (default 15).

Clients – Admin tools → API clients

  • A client has a public client_id and a client_secret that is shown once (copy it right away). Only HMAC hashes of secrets and tokens are stored.
  • Service user: each client acts as its own user (created on the page or chosen). The rights of that user's access level apply exactly as in the browser (view / save / add / delete on nuuser, nuaccess, nupermissionitem). A service user can no longer log in, and neither it nor its access level can be changed through the API.
  • Scopes: what the client may do at all – users:read, users:write, users:password, users:login_link, reports:run, notifications:write, access:read, access:write, permissions:read, permissions:write. A request needs the scope and the right of the access level.
  • Optional: allowed IP addresses / networks, requests per minute (default 120, then 429), expiry date. New secret (the old one stays valid 24 h or ends at once), Revoke all tokens, Delete. Every token and request is logged (Log: API token issued / refused, API read / change).

Access token (OAuth 2.0 client credentials)

curl -u 'nk_…:ns_…' -d grant_type=client_credentials https://example.com/nunext/api.php/v1/token
→ {"access_token":"nt_…","token_type":"Bearer","expires_in":900,"scope":"users:read …"}

curl -H 'Authorization: Bearer nt_…' 'https://example.com/nunext/api.php/v1/users?q=anna&state=active&limit=20'

Credentials as HTTP Basic or as client_id / client_secret in the body; scope may ask for fewer scopes. Ten wrong secrets lock the client for 15 minutes. If the Authorization header does not reach PHP (some FastCGI set-ups), add SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1 to the folder's .htaccess.

Excel export (NuXlsx, 0.8.398)

The class NuXlsx writes .xlsx files without other libraries – in procedures, PHP hooks and page forms ($nu->excel()). Values keep their type: numbers stay numbers, DateTime becomes an Excel date, true / false a boolean, strings are always text (a string starting with = never becomes a formula – formulas only with NuXlsx::formula()).

$x = NuXlsx::create('Orders');                       // or $nu->excel() in a page
$s = $x->sheet('Open orders');                       // more sheets: $x->sheet('…') again
$s->header(['Customer', 'Amount', 'Date'])           // bold, frozen below, autofilter

  ->row(['Total', NuXlsx::formula('SUM(B2:B99)')], ['bold' => true])
  ->style('B2:B100', ['format' => '#,##0.00'])
  ->row([NuXlsx::cell('late', ['color' => '#c00000', 'bg' => '#fff3cd'])])
  ->width('A', 30);                                   // other columns: width from the content
$x->download('orders.xlsx');                         // or $x->save($file) / $x->toString() (e-mail attachment)

Development with Claude

Only shown in developer mode. nuBuilder Next is developed in sessions with Claude (Anthropic's AI) working on a copy of the project in its own Linux workspace: it changes the code, tests it in a browser against a real nuBuilder database and hands back two signed zips. The rules it follows are in CLAUDE.md (in nunext-dev.zip and the repository, never in the install package) – read it once; this chapter is the short version for the developer.

What a session needs

  • Claude with a workspace: a Claude session that can run commands and handle files (Claude Code – web, desktop or terminal – or claude.ai with the code / file tools). It needs internet access for the package registries (apt, npm, pip) and GitHub (cloning nuBuilder for the test installation, and pushing).
  • nunext-dev.zip of the last release – the whole project including CLAUDE.md, TODO.md, dev/ (release script, tests, tools) and .github/.
  • The signing key file nunext-signing.key (see below) – without it releases are unsigned and every installation warns.
  • For "gate": write access to the repository nuBuilder/nuBuilder-Next in the session (GitHub connection with push rights).

Nothing survives between sessions: the workspace, the test database and the test installation are rebuilt from the zip each time (CLAUDE.md → "Test environment": MariaDB, PHP's built-in server, a clone of nuBuilder with nuBuilder Next inside it at /nunext/, Playwright with Chromium, PHPStan, ESLint, axe-core).

Starting a new session

  1. Attach nunext-dev.zip (from the last answer) and nunext-signing.key.
  2. First message, e.g.: "New session: unpack nunext-dev.zip, put nunext-signing.key next to the project folder, read CLAUDE.md and TODO.md, rebuild the test environment." – then the request.
  3. Claude unpacks to nunext/, puts the key next to it (../nunext-signing.key – outside the project, never in a zip), installs MariaDB / the test site / the tools and reads the newest changelog sections.

A long session that reaches its context limit continues with a summary – nothing to do. A new session is only needed when the old one is gone; always send it the nunext-dev.zip of the last answer.

The signing key

  • An Ed25519 key pair. The public key is in the code (NuUpdate::SIGN_PUBLIC in core/nuupdate.php); every installation checks nunext.zip and the library packs against it. The secret key is the file nunext-signing.key (last line = the base64 secret key) – whoever has it can make packages every installation accepts. Keep it private: never in the project, a zip, the repository, a ticket or a chat that is shared.
  • Where the tools look for it: $NUNEXT_SIGNING_KEY, ../nunext-signing.key (next to the project folder), ~/.nunext-signing.key. The page Build library packs takes it as an upload for that one request and never stores it.
  • A new key pair (only if the old one is lost or leaked): 
    php -r '$k = sodium_crypto_sign_keypair(); echo "nuBuilder Next signing key\n", base64_encode(sodium_crypto_sign_secretkey($k)), "\n"; fwrite(STDERR, "public: " . base64_encode(sodium_crypto_sign_publickey($k)) . "\n");' > nunext-signing.key
    Put the printed public key into NuUpdate::SIGN_PUBLIC and release. Installations still on the old key refuse the new packages – update them once by hand (unpack the zip over the folder), and rebuild the library packs with the new key.
  • Not the same as $nuConfigSecretKey in nuconfig.php – that one is per installation (API tokens, one-time links) and never leaves the server.

Requests

  • A short request ("add a filter to the users list") → Claude builds it and ends with a fast release (next version 0.8.x+1), tests of the changed areas and a look in the browser, and sends both zips. It asks first only when a wrong guess would be expensive.
  • "Suggest …" → numbered options with a recommendation, nothing built. Answer with the option, "do recommendations" or "ok all".
  • "Gate" → full release gate and push to GitHub (below).
  • Every release: version bump, CHANGELOG.md section, texts in all eleven languages, the help (this file), TODO.md (points to verify), tests for new features. No personal details of the developer in any file.

Making a release by hand

  1. In the project folder (key next to it): write the changelog text into a file – - bullets, continuation lines indented by two spaces – and run python3 dev/release.py 0.8.x "Title" changes.txt (add --gate with the test variables set). The version must be higher than NU_VERSION.
  2. It updates README.md (version line), CHANGELOG.md, NU_VERSION in core/nuapp.php, lang/en-US.php / de-CH.php, install/db_changes.json, writes and signs nunext-manifest.json and builds ../nunext.zip and ../nunext-dev.zip.
  3. Check it like an installation would: php dev/inspect.php <test installation> ../nunext.zip → ok=true, the new version, signature=valid, errors=[].
  4. Publish: on GitHub create a release with the tag v0.8.x (on the pushed commit), the changelog section as text, and attach nunext.zip (that file name – the update page looks for it; pre-release while nuBuilder Next is alpha). nunext-dev.zip is not needed there (the repository is the same).
  5. Library packs are a separate, fixed release with the tag libraries – touched only when a library changes (Publishing the packs on GitHub). If the new version needs a newer library (install/libraries-required.json), update that release first.

If a release must be rebuilt before it went out: set NU_VERSION back, remove its CHANGELOG.md section and the manifest's changes entry, then run it again.

Built in (no setting)

  • Login rate limit: 5 failed logins (or wrong second-factor codes) for a name from one address, 20 for a name from anywhere or 30 from one address within 15 minutes lock further attempts – counted in the log, so a client without cookies cannot reset it. Auto-login links, one-time login tokens and the password confirmation count too.
  • "Forgot password" sends links only to $nuConfigBaseURL or, while that is empty, to the address the globeadmin last used – never to the host name of the anonymous request (a forged host name would send the reset link to someone else's server). At most 10 requests an hour per address and 3 links an hour per user.
  • Sessions: the cookie belongs to the nuBuilder Next folder; a login is bound to this folder and database, and a globeadmin login ends when name or password change in nuconfig.php. Strict session ids, Secure cookies also behind a proxy that ends TLS ($nuConfigTrustProxy + X-Forwarded-Proto); with $nuConfigTrustProxy the client address is the last X-Forwarded-For entry (the one your proxy adds).
  • Headers: Content-Security-Policy, X-Frame-Options, Permissions-Policy, Cross-Origin-Opener-Policy, and Strict-Transport-Security on HTTPS.
  • Log: passwords, keys, tokens and password hashes are written as ••• in the record changes.
  • Demo mode: password hashes and secret columns show as ••• in forms, lists and the hash viewer; the SQL builder cannot read zzzzsys_user, sessions, setup, settings or nuBuilder Next's tables.
  • Hash variables in SQL are escaped for the database's mode (also MySQL's NO_BACKSLASH_ESCAPES); they are safe inside quotes only – the Compatibility check lists places without quotes.
  • Update packages are signed (Ed25519); the update page shows Signed by nuBuilder Next, warns for unsigned packages and refuses a package whose signature does not match.
  • Package files: every PHP file of core/, pages/ and lang/ ends at once when called directly; .htaccess files block core/, pages/, lang/, install/, docs/, dev/, _backup/, _install/, temp/ and the notes in the main folder (Apache 2.2 and 2.4). TODO.md, CLAUDE.md and dev/ are no longer part of the installed package.

Web server rules

Apache reads the .htaccess files only with AllowOverride All (Debian / Ubuntu's default for /var/www is None). nginx ignores them. Add rules like these (path of your installation), then run the Security check again:

# Apache: virtual host or apache2.conf
<Directory /var/www/html>
	AllowOverride All
</Directory>

# nginx: server block
location ~ ^/nunext/(core|pages|lang|install|docs|dev|_backup|_install|_update|_libsrc|temp|custom|lib)/ { deny all; }   # custom/: page forms (0.8.387)
location ~ ^/nunext/(README\.md|CHANGELOG\.md|LICENSE|TODO\.md|CLAUDE\.md|nunext-manifest\.json|nuconfig.*\.php|cron\.php)$ { deny all; }
location ~ /NUNEXT-VERSION\.txt$ { deny all; }
# library packs (0.8.409): vendor/packs/ is closed except the browser packs; vendor/nuconfig.php is covered by the nuconfig rule above
location ~ ^/nunext/vendor/(nuconfig\.php|packs/(nunext-libs\.php|index\.html|[^/]+/nunext-lib\.json))$ { deny all; }
location ~ ^/nunext/vendor/packs/(tcpdf|phpmailer|adminer)(-[^/]*)?/ { deny all; }
location ~ ^/nunext/third_party/((tcpdf|phpmailer|adminer)(-[^/]*)?/|[^/]+/nunext-lib\.json$) { deny all; }   # packs of 0.8.405–0.8.408
# browser cache (Apache: assets/.htaccess and vendor/bundled/.htaccess do it) – files with ?v= never change under their URL
location ^~ /nunext/assets/ { expires 7d; if ($arg_v) { expires 1y; add_header Cache-Control "public, immutable"; } }
location ^~ /nunext/vendor/bundled/ { expires 7d; if ($arg_v) { expires 1y; add_header Cache-Control "public, immutable"; } }

Browser cache (0.8.366): every script, stylesheet and picture of nuBuilder Next is loaded with a version in its address (?v=…), so assets/.htaccess lets browsers keep it for a year without asking again (immutable); after an update the address changes and the new file is loaded. Files without a version (fonts, pictures of a stylesheet) are kept for a week. Needs Apache's mod_headers / mod_expires (without them nothing changes); nginx: the rule above.

Even better for backups: $nuConfigBackupPath outside the web root.

Housekeeping (cron)

cron.php removes expired tokens and sessions, old API counters, log entries beyond Keep the log, PDFs of the REST API whose download link expired and temporary files older than a day. Run it as the web server's user, e.g. every 15 minutes:

*/15 * * * *  sudo -u www-data php /var/www/html/nunext/cron.php > /dev/null

Without cron a page view does it now and then (as before); once cron has run in the last 25 hours, page views leave it to cron. The web server never runs cron.php.

Checklist for a live server

  1. HTTPS only; $nuConfigBaseURL set; $nuConfigTrustProxy only behind your own proxy.
  2. A long globeadmin password, $nuConfig2FAAdmin = true and a globeadmin e-mail or authenticator.
  3. $nuConfigSecretKey set (API clients page → Generate key).
  4. $nuConfigDebug = false, PHP display_errors = Off, PHP 8.2 or newer.
  5. Files on the web all green; backups outside the web root.
  6. Admin-equivalent rights only for people who may change code and users.
  7. A log retention and cron for the housekeeping.
  8. Demo mode only with a demo database.

Compatibility check

Start page → Compatibility check scans all code of your application – form JavaScript, object events, lookup code, HTML objects, the setup header and procedures – for calls of nu…() functions and shows for each one whether nuBuilder Next supports it:

  • supported – works in nuBuilder Next; stub – exists but does nothing yet; missing – a nuBuilder function nuBuilder Next does not have (the call fails); unknown – not a nuBuilder function (typo, other library); your own – defined in your code or $nuConfigIncludePHP.
  • Each row shows the number of calls and where they are; form names link to the builder. Show supported functions too lists everything, Include nuBuilder's own forms also scans the nu… forms.
  • Run it after importing an application into a database used by nuBuilder Next, and before opening it to users.
  • nuBuilder 4.9 features (0.8.382): the features of the nuBuilder 4.9 compatibility review your application uses, with the places (form, object, procedure, line of nuconfig.php) and since which version nuBuilder Next supports them – red = not supported yet, test these places by hand. IDs as in the review: C1–C6 (browse columns with table names or aliases, AS aliases, browse SQL without the primary key, SELECT * over joins, nu_filter_match, access conditions), M1–M10 (scripts in HTML objects, nuAddBrowseTitleSelect, multi-value filters, selects from a procedure, files into the file system, $nuConfigIncludeJS / …CSS, nuAfterSave, nuFORM methods, report PDFs from PHP, SSO), N1 (nuSERVERRESPONSE), I3 (MyISAM tables).
  • Hash variables outside quotes (0.8.207): #field# is escaped for a quoted string only. In WHERE id = #field# or $x = #field#; a user can put SQL or PHP into a field value. The list shows every procedure, hook, browse SQL, select / display SQL and SQL builder query with such a variable (also SQL inside PHP strings, nuRunQuery("… = #x#")). Fix: '#field#' in quotes, or parameters (nuRunQuery($sql, [$value])). Variables the server sets (#USER_ID#, #FORM_ID#, #TABLE_ID# …) are not listed; #RECORD_ID#, #ID# and #CODE# are – they come from the browser.

Troubleshooting

  • Old layout or buttons after an update: not all files were replaced, or OPcache needs a reload.
  • Mails don't arrive: E-mail → Test mail shows the server conversation; check the e-mail log for errors.
  • "Illegal mix of collations": tables created by hand with another collation than nuBuilder's tables – align the collation.
  • Editor field shows HTML code: TinyMCE is not installed – Update → Libraries.
  • phpMyAdmin says "Please log into nuBuilder": open it again from the user menu (the login ended), or check that nudb/config.inc.php is nuBuilder's version.
  • Icons of old forms missing: an icon that Font Awesome 7 (the bundled fallback) no longer has – set $nuConfigNuBuilderPath or $nuConfigFontAwesomePath to nuBuilder's copy.
