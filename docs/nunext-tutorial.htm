First steps

What nuBuilder Next is, how the start page works and how to find your way around.

Welcome to nuBuilder Next

nuBuilder Next is a modern front end for nuBuilder 4 applications. It runs on the same database as nuBuilder – the same forms, users, access levels, procedures and reports – so both can be used side by side: an application built in one opens in the other.

  • nuBuilder's tables all start with zzzzsys_. nuBuilder Next reads and writes them in nuBuilder's formats and adds only its own tables (zzzzsys_nunext_…: log, sessions, two-factor data, settings, dashboards …).
  • The globeadmin is the main administrator. Its name and password are not stored in a user record but in the configuration file nuconfig.php. The globeadmin may do everything.
  • All other people are users. What they may do comes from their access level – exactly as in nuBuilder. In addition, nuBuilder Next can give a user an admin role: a defined part of the globeadmin's rights.

How this tutorial works

  • The tutorial is split into three parts: Basics (finding your way, users and rights), Building applications (forms, code, reports, e-mail) and Administration (settings, security, updates and advanced topics).
  • Each lesson explains one topic. Links with open the page in a new tab, so this lesson stays open; links with open the matching chapter of the documentation.
  • A green Try it box suggests a small exercise. When you are done, click Done – next lesson. Your progress is saved; the start page tile shows it.
  • The tutorial is in English, like the documentation. The pages themselves follow your language.

Look at the list of lessons on the left (below on a phone). Then click Done – next lesson.

The start page and navigation

After signing in, the globeadmin sees the start page: tiles in groups such as Users & rights, Development, Communication, System, Look, Data and Integration. Each tile opens one area.

  • + on the right of a tile opens a new record straight away (e.g. a new user). ▾ opens a menu with the pages behind the tile (e.g. Forms → New form, Cloner, Formats, Translations …).
  • Badges on tiles show information at a glance: an update of the Sample data, how many points of System status need a look.
  • The search field above the tiles filters them as you type (/ jumps into it). Below, More results also lists forms, procedures, reports and the pages of the ▾ menus. English words always work, too.
  • Ctrl+K (or the magnifier in the top bar) opens the same search on every page.
  • The top bar: the logo always leads back to the start page; the theme button switches light / dark / automatic; the language menu changes the interface language; the user menu (top right) holds Help, this tutorial, System status, the database tools and Sign out.
  • Back (first button on every page) goes one level up – from a record to its list, from a list to the start page.
  1. Open the start page and type mail into the search field – see which tiles stay.
  2. Press Ctrl+K, type users and press Enter.
  3. Switch the theme to dark and back.

Working with forms and lists

Everything your users do happens in forms: a list (nuBuilder calls it browse) and an edit form for one record. nuBuilder Next's own pages (users, access levels …) work the same way.

Lists

  • Type into the search field and press Enter – several words must all match. Click a column title to sort; click again to reverse.
  • Filters sit behind the funnel button next to the search field; × resets search and filters.
  • Click a row to open the record; Add creates a new one. Print opens the list in a new tab – with Copy (for Excel) and Export CSV.

Edit forms

  • As soon as something changes, Save turns red. Ctrl+Shift+S saves. Leaving with unsaved changes asks first.
  • Clone copies the record into a new, unsaved one (yellow frame); Delete asks first.
  • A red * after a label means "required", a blue ◆ means "must be unique".
  • The ⋮ button at the end of the toolbar lists everything you can do on this form, each with its keyboard shortcut. As globeadmin you also find the builder shortcuts, Inspect record and the hash variables there.
  • Sub-forms (rows inside a record): typing in the empty last row adds a row. Lookups: type a code or click the search button.
  1. Open the sample customer list, search for a customer and open it.
  2. Change a field – watch Save turn red – and save with Ctrl+Shift+S.
  3. Open the ⋮ menu and look at the entries.

Users and rights

Who may sign in, and what they may do: users, access levels, permission items and admin roles.

How rights work

Before creating users it helps to know the model – it is nuBuilder's:

  1. Every user has exactly one access level. Without one the login is refused.
  2. An access level lists the forms the user may open. Per form: view (the row exists), Save, Add / New, Delete, Clone and Print.
  3. Procedures (PHP code) and reports are allowed per access level too.
  4. Permission items are named switches your own code checks – for finer rules ("may approve invoices").
  5. The globeadmin may do everything.

nuBuilder Next's own pages are protected by nuBuilder's system forms: the users page by nuuser, access levels by nuaccess, the form builder by nuform, procedures by nuprocedure and so on. Give an access level the row nuuser and its users see the users page.

Admin-equivalent rights: changing rights on nuform, nuprocedure, nuselect, nusetup, nuuser or nuaccess amount to full control – PHP on the server, SQL on every table, the passwords of all users. With Only the globeadmin grants admin rights (Security check, on by default) only the globeadmin hands them out.

How rights work

Access levels

Access levels define what a group of users may do. Create one per role in your organisation (e.g. sales, accounting, read only).

  • Forms: add a single form from the list, or Several… to pick many at once (search, filter by group and type) and set the buttons they get – e.g. everything but Delete.
  • Removing a form crosses its row out; it disappears when you save. Until then the same button brings it back.
  • Procedures and reports: on their own tabs.
  • Use two-factor authentication: users of this level confirm the login with an authenticator app or an e-mail code.
  • The level's start form (nuBuilder's home form) is what its users see after signing in.
  • An access level with users cannot be deleted. Clone copies it with all rights – the quickest way to a similar level.
  1. Open Access levels and open sample_editor: see which forms and buttons it has.
  2. Clone it as tutorial_level, remove the Delete right on the customer form and save.

Access levels in the documentation

Creating and managing users

Users lists everybody who may sign in (active users by default; the filter shows expired and archived ones).

  • New user: full name (it fills first and last name), e-mail, login name (unique), access level and a password – the magic wand creates a strong one. Change password at next login makes the user choose his own.
  • Welcome e-mail (when e-mail is set up): instead of telling the user a password, send a personal link to set one. The password field can then stay empty.
  • Valid until: the login works through that day. Archive sets it to yesterday – the user can no longer sign in, but all data stays. Delete removes the user for good.
  • Language: the user's interface language (empty = browser). Position, department, team suggest values of the other users.
  • Reset 2FA removes the user's authenticator app – e.g. after a lost phone.
  • Import… in the users list creates many users at once from a CSV file, with the same checks as the user form; existing logins are skipped.
  • The View button switches the list's layout: Default, Compact, All columns or your own views – columns, order, filters and the cards on a phone. Shared views can be limited to access levels.
  1. Create a user tutorial_user with the access level tutorial_level from the last lesson (or sample_viewer) and a generated password.
  2. Archive the user, look at the list with the filter All, then clear Valid until again.

Permission items

Sometimes users of the same access level need different rights – one sales person may give discounts, the others may not. Permission items solve this:

  • An item has an ident (the name used in code, e.g. sales_discount) and a group.
  • Assign users on the item, or tick items at the bottom of the user form – both edit the same list.
  • Your code asks: PHP nuUserHasPermission('sales_discount'), JavaScript the same, SQL #USER_PERMISSIONS#. Used in code on the item shows where.
Always check on the server (e.g. in Before Save) – a check in the browser alone can be bypassed.

Seeing the application as a user

To check what a user really sees – menu, forms, buttons, rights – you do not need his password: Act as user (the icon in front of the name in the user form, or a row of Logged-in users).

  • View only: everything the user sees, but nothing can be changed. The bar on top is blue.
  • Full access: work as the user (red bar). Records are saved as this user; the log notes that the globeadmin acted.
  • Back to globeadmin (in the bar) returns to where you started – no new login.

Logged-in users

Logged-in users shows every active session: user, address, browser, login time and last activity (green = active in the last five minutes).

  • End session signs one user out at his next click – e.g. after changing his rights.
  • Log out all others before maintenance work; Log out everyone includes you.
  • The (i) next to the title shows the session timeouts ($nuConfigSessionTimeout, default 120 minutes; the globeadmin 12 hours).

Admin roles: sharing the administration

Nobody but the globeadmin should know the globeadmin password. When others need to help – a colleague who manages users, a developer, support – give them an admin role.

  • A role is a set of rights, one per tool, each view or change. A user gets at most one role (field Admin role in the user form).
  • Five default roles: Full administrator, Administrator without system, Developer, User manager, Support (read only) – editable and copyable.
  • A user with a role sees the tiles, menu entries, search results, help chapters and tutorial lessons of his rights. Pages he may only view show View only.
  • Rights marked full access (red) – Update, nuconfig.php, Database, forms, procedures, acting as another user … – lead to full control in the end. Give them only to people you would trust with the globeadmin password.

Open Admin roles and look at the default role User manager. Give tutorial_user this role, then act as that user and look at the start page.

Building forms

From a database table to a working form: the form builder, objects, layouts and run buttons.

Forms, tables and the forms list

A nuBuilder form shows the records of one table (or a view): the list (browse) shows some columns, the edit form all fields. Types: browse and edit, browse only, edit only, launch (a start page or a criteria form without table) and subform (rows inside another form).

The forms list shows all forms with group and status (Active, Draft, Archived). Click a form to open it as a user would; the button opens it in the form builder. nuBuilder's own forms (nu…) are read-only.

Open the forms list, filter by status, then open sample_order in the builder ().

Forms and the form builder

Creating a form

New form offers two ways:

  • Existing table: pick the table and its primary key – objects and list columns are generated from the columns.
  • New table: enter the columns (name, label, type, length, required). The table gets a nuBuilder-style text primary key and, if you like, audit columns (created / updated at / by) that are filled on every save.

Afterwards the form opens in the builder. Give your forms a meaningful code and a group – the forms list and the access level page filter by them.

A new form is not yet in any access level: only the globeadmin can open it until you add it to an access level.

Create a form tutorial_task with a new table tutorial_task and the columns tsk_title (text, required), tsk_due (date) and tsk_done (checkbox), with audit columns. Open it and add two records.

Creating a form

Working in the form builder

  • Left: the objects per tab – drag them to change the order. Middle: the preview – click an object to select it, drag to move, use the handle to resize. Right: properties of the selected object, the form's settings, list columns, tabs and code.
  • Layouts: absolute (pixel positions as in nuBuilder), auto (responsive rows worked out from the positions) and grid (12 columns). Auto and grid work well on phones.
  • List columns: what the browse list shows – title, column or SQL expression, width, alignment, format.
  • Save turns red while the open panel has changes; Ctrl+S saves. Undo / History keeps the last 100 states of the form – any of them can be restored.
  • If an object's ID has no column in the table yet, the builder offers to add it.
On any form page, Ctrl+Shift+A opens the builder to arrange objects, Ctrl+Shift+H to add an object, Ctrl+Shift+F the form properties.

Object types

Objects are the fields and elements of a form. The most important ones:

  • Input – text, number, date, checkbox, file, button, masks (IBAN, phone). Text area and WYSIWYG editor for longer texts.
  • Select – a list of values or SQL; searchable, also with multiple values.
  • Lookup – picks a record of another form (e.g. the customer of an order): type a code or search in a list.
  • Display and calculation – show a value from SQL or calculate from other fields (e.g. the order total).
  • Sub-form – rows of another table inside the record (order lines).
  • Run – a button or iframe that opens a form, runs a procedure or a report.
  • HTML, content box, image, chart, word (a label).

Every object has an access setting (editable, read only, hidden, hidden for users, globeadmin only) and a validation (none, required, unique, both) – checked on the server, too.

Open the sample form All objects and click through its tabs – every object type is there. Then open it in the builder to see how each is set up.

Object types · Run objects

Code: events, hash variables and the code editor

Forms come alive with code – exactly as in nuBuilder:

  • PHP events on the form's Code tab: Before Browse, Before Edit, Before Save, After Save, Before Delete, After Delete. Typical: check values in Before Save and stop with nuDisplayError('…').
  • JavaScript of the form and object events (onchange, onclick …) run in the browser.
  • Hash variables such as #RECORD_ID#, #USER_ID# or #cus_name# (a field of the record) are replaced before the code runs. In SQL always put them in quotes: WHERE cus_id = '#RECORD_ID#'.
  • Code fields open the code editor with a double-click: colours, search and replace, Format, full screen.
  • ⋮ → Hash variables on any form shows the values available there.
The Prompt generator builds a prompt for an AI tool with the right nuBuilder context (scopes, functions, your table columns) – useful when you write code for a new event.

In tutorial_task, add a Before Save event that refuses a due date in the past:

if ('#tsk_due#' !== '' && '#tsk_due#' < date('Y-m-d')) {
    nuDisplayError('The due date is in the past.');
}

Procedures, reports and dashboards

Server code, PDF reports and dashboards with key figures and charts.

Procedures

Procedures are PHP code stored in the database (zzzzsys_php). A run button, a tile or nuRunPHP('code') starts them – in a new tab (output visible) or hidden (background work, then a message).

  • Access levels tab: who may run it. Usage: which objects and code start it. History: every change with the code before and after.
  • Hidden / New tab on the page run the saved version as a test.
  • Some codes have a special meaning in nuBuilder: nu_before_save (for every form), nu_startup, nu_check_password_policy, nu_send_welcome_email.
  • Debug with nuDebug($value) – the output appears under Debug.

Create a procedure tutorial_hello with echo 'Hello ' . '#USER_ID#';, run it in a new tab, then write nuDebug('test'); into it, run it hidden and look at Debug.

Procedures in the documentation

Reports and the SQL builder

Reports produce PDFs in nuBuilder's format (they work in both). A report has:

  • A data source: a table or view, an SQL builder query, or a procedure that fills a temporary table #TABLE_ID#.
  • An optional launch form for criteria (e.g. a date range); its fields are available as hash variables.
  • The layout in the report designer: bands (report header, page header, groups, detail, footers) with fields, texts, lines, boxes and images.
  • Access levels that may run it.

The SQL builder creates queries graphically: add tables, tick columns, drag a column onto another to join, add conditions and sorting. Run shows the first rows.

The PDF needs TCPDF – taken from nuBuilder when nuBuilder Next sits in nuBuilder's folder. Without it the report pages say so.

Open the sample report sample_customers (customers by country) in the designer, look at its bands and run Preview. Then open the SQL builder query sample_orders.

Dashboards

Dashboards show key figures, charts and tables – on the start page of users (per access level) or inside any form.

  • A dashboard holds widgets: KPI tiles (value, change in %, colour by thresholds), charts (columns, bars, line, area, pie, donut …) and tables.
  • Data comes from one SELECT, an SQL builder query or a PHP procedure – always read-only.
  • #DATE_FROM# / #DATE_TO# add a date filter; on forms #RECORD_ID# and the record's fields filter the data.

E-mail: settings, test mail and templates

Password links, two-factor codes, welcome e-mails and your own mails need a mail server. E-mail → Settings uses nuBuilder's settings:

  • SMTP server, port (465 = SSL/TLS, 587 = STARTTLS), user, password and sender. The password is never shown again – leave the field empty to keep it.
  • Test mail shows the whole conversation with the server – the fastest way to find a wrong setting.
  • E-mail log: every mail with its status and error.
  • Templates: subject and body with placeholders (#cus_name#), per language. Clone nuBuilder's nu_send_welcome_email_template to write your own welcome e-mail.

Enter your mail server and send a test mail to yourself. If it fails, read the server conversation.

For messages inside the application use Notifications: the bell in the top bar turns red for the recipients – everybody, single users, departments, teams, positions or access levels – with read receipts and, if needed, a confirmation ("Got it") or an e-mail as well.

Running the installation

Settings, security, logs, updates and backups – what keeps an installation healthy.

Configuration: nuconfig.php and the setup wizard

nuconfig.php holds the database access, the globeadmin login and many settings – the same file and variable names as nuBuilder. nuBuilder Next's own settings start with $nuConfig… too (session timeouts, password length, two-factor login, base URL …).

  • The Setup wizard asks for the most important ones in four steps: language and time zone, look and tools, security, sample data.
  • Configuration file (nuconfig.php) edits the file directly. Saving checks the PHP, runs it and tests the database connection first; the old file is kept as a backup.
  • Important on a live server: $nuConfigBaseURL (the address in e-mail links), $nuConfigSecretKey (encryption key), $nuConfigTimezone.
A broken nuconfig.php stops the whole site – and nuBuilder too, if it reads the same file. The editor refuses to save a file that does not pass its checks; if something still goes wrong, copy a backup from _backup/ over it by FTP.

Configuration · nuconfig.php editor · Setup wizard

Settings (nuBuilder's settings table)

nuBuilder can keep its settings in a table instead of nuconfig.php. Settings edits that table; it is only used with $nuConfigSettingsFromDB = true (the page offers to switch it on).

  • A tag after each setting tells what it means for nuBuilder Next: Used, Not yet (only nuBuilder uses it for now) or Not needed (nuBuilder Next has its own solution).
  • Import copies the values set in nuconfig.php into the table.

Settings in the documentation

Security check and two-factor login

The Security check shows everything that matters for this installation as traffic lights – red: fix it soon, yellow: check it, blue: information – each with a link to where it is fixed: HTTPS, base URL, secret key, the globeadmin password and its two-factor login, debug output, files the web server must not hand out, library versions, users with old passwords, access levels with admin-equivalent rights.

  • Security settings on the same page: who grants admin rights, log retention, when to ask for the password again, old md5 passwords …
  • Two-factor login: $nuConfig2FAAdmin for the globeadmin, $nuConfig2FAUser plus Use two-factor authentication on access levels for users. Each person sets up an authenticator app under Security in the user menu, or gets codes by e-mail.
  • Built in: a login rate limit, signed update packages, strict security headers, masked secrets in the log.

Open the Security check and go through every red and yellow point. Set up an authenticator app for your own login under Security.

Log and debug results

  • The Log records logins and failed logins, two-factor events, password changes, changes to users, access levels, forms and settings, exports, imports and updates. Filter by event, user, date or text.
  • The Audit trail records every change made in the forms – one row per column with old and new value, also sub-form rows, deletes, clones and CSV imports. In a record, ⋮ → History of this record shows its changes; ↺ puts an old value or a deleted row back.
  • Debug collects what nuDebug() writes in PHP code – your main tool when a procedure or event does not do what it should.
  • Keep the log (days) in the security settings deletes old entries automatically (0 = keep for ever).

Updates and backups

New versions are installed on the Update page – no FTP needed:

  1. Choose nunext.zip and click Check package: version, changed files, what's new, database changes, and whether the package is signed by nuBuilder Next. Nothing changes yet.
  2. Install makes a backup (program files, nuBuilder Next's tables, optionally an SQL dump of the whole database), switches on maintenance mode, copies the files and runs the database steps. If copying fails, the backup is put back automatically.
  3. Roll back puts the program files of an earlier backup back. Backups can be downloaded – the SQL dump imports with phpMyAdmin.
  • The Change history card lists what changed in every version.
  • Back up now makes a backup by hand – before larger changes, choose the whole database.
  • Updates can also run unattended (command line or REST API) – see the documentation.

Open Update, read the change history of the installed version and make a backup with Back up now (database: nuBuilder Next tables).

System status and database tools

  • System status lists what needs a look: the time zone, a missing database tool or File Manager, tables that are not InnoDB, the demo mode. The badge on its tile counts these points.
  • Storage engine: older nuBuilder databases often still use MyISAM tables, which have no transactions. Convert all to InnoDB fixes that (make a backup first).
  • Database tools: phpMyAdmin and / or Adminer and Tiny File Manager open from the user menu and the start page, signed in through nuBuilder Next. They are not part of the package – System status says where to copy them.
phpMyAdmin, Adminer and the File Manager give full access to the database and the web folder. Use them with care, and only as globeadmin or with a role you fully trust.

System status and tools · Storage engine

Housekeeping and the live-server checklist

cron.php removes expired tokens and sessions, old log entries and temporary files. Run it every 15 minutes as the web server's user:

*/15 * * * * sudo -u www-data php /var/www/html/nunext/cron.php > /dev/null

Before users start working on a live server:

  • HTTPS only; $nuConfigBaseURL and $nuConfigSecretKey set.
  • A long globeadmin password and two-factor login for the globeadmin.
  • $nuConfigDebug = false; all Files on the web points of the Security check green.
  • Backups outside the web root ($nuConfigBackupPath), a log retention, cron running.
  • Admin-equivalent rights and admin roles only for people who may change code and users.

Advanced topics

Copies of the application, the REST API, demo mode, nuBuilder compatibility and where to go next.

App cloner: test and development copies

The App cloner copies the whole application – into another database on the same or another server, optionally with the files – e.g. for a test system:

  • Choose what is copied: system tables, your own tables, data, views, functions, procedures, triggers, events.
  • Dry run shows every step without changing anything; Run copies and compares the record counts at the end.
  • Download SQL exports the database as one file instead – for an import elsewhere.
  • Configurations are saved in nuBuilder's table, so nuBuilder's App cloner opens them too.
Set the environment label of a test copy in its nuconfig.php ($nuConfigEnvironmentLabel = "TEST";) – a label stored in the database would be copied along with it.

App cloner in the documentation

REST API

Other systems (an HR tool, a script) can manage users, access levels and permission items through the REST API (api.php/v1/…):

  • Switch it on with $nuConfigApi = true (the API clients page offers a button) and set a secret key.
  • Create a client: it gets a client_id and a secret shown once, a service user whose access level decides its rights, and scopes (e.g. users:read). Optional: allowed IP addresses, a request limit, an expiry date.
  • The API playground sends requests from the browser – ideal to learn the endpoints and copy a curl command.

REST API in the documentation

Demo mode

Demo mode lets visitors look at the whole application without being able to change anything – useful for presentations and evaluations.

  1. Create a user (e.g. demo) with any access level.
  2. Set $nuConfigDemoUser = "demo"; in nuconfig.php.

Demo users see all data and code of the application. Use demo mode only with a database that holds demo data.

Bringing a nuBuilder application to nuBuilder Next

An existing nuBuilder application usually works at once – the database is the same. Before opening it to users:

  1. Run the Compatibility check: it scans all JavaScript, events, procedures and SQL for nuBuilder functions and shows whether each one is supported, a stub or missing in nuBuilder Next.
  2. Fix the hash variables outside quotes it lists – WHERE id = #field# lets a user put SQL into a field; write '#field#'.
  3. Check System status (InnoDB, time zone) and the Security check.
  4. Act as a few typical users and click through their forms.
